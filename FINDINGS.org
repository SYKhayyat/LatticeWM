#+TITLE: The result of the experiment
#+SUBTITLE: What building the lattice from outside actually cost
#+DATE: 2026-07-31

* Why this file exists

DESIGN.org [[file:DESIGN.org::#d21][D21]] makes the project's central claim falsifiable, and
names the deliverable:

#+begin_quote
*The rule: no core edits.* Every time one appears necessary, stop and write
down what was missing and why. /That list is the actual result of this
project's central experiment/, whichever way it comes out — a short, mechanical
list means the thesis held; a lattice that cannot be expressed without surgery
means [[file:DESIGN.org::#extensibility][the honest claim]] was still too optimistic, and this document has to say
so.
#+end_quote

And [[file:DESIGN.org::#d21][D21]] again, on the obligation:

#+begin_quote
*Recorded consequence:* if step 4 turns out to require core surgery, /that is
the finding/ and it must be written down here rather than quietly absorbed by
editing the core.
#+end_quote

This is that list. It is written to be read against the code rather than
instead of it.

* The short version
:PROPERTIES:
:CUSTOM_ID: short
:END:

*The thesis held, with three qualifications and one bug.*

The lattice is 2,077 lines in six files, of which 28 are ~defmethod~ forms. It
specialises *twelve* policy generics and *two* persistence generics that the
core already declared, adds one new container class, and needed *two* edits
under =src/= to exist at all. Neither changed a behaviour; one was an omitted
export and one made a protocol operation total that had been partial.

A *third* core edit came later, from writing the worked examples rather than
from the lattice, and it is the most important of the three — see
[[#edit-3][core edit 3]]. A *fourth* came later still, from *using* the thing
for an afternoon rather than from writing it: the default shape of a new
workspace was not a decision anything could take part in, so the lattice
covered the workspaces that existed when it loaded and no others. See
[[#edit-4][core edit 4]], which is the sharpest of the four because nothing
failed.

A *fifth* came later still and is of a different kind: not a missing method on
a surface that worked, but a whole half of the surface that no check could see.
The *container* protocol — what a new container kind answers, as against what a
new policy answers — had no membership test, no generated document and no
documentation gate, and so it had a generic exported and never defined, two
members declared in the wrong package, and no statement anywhere of its size.
See [[#edit-5][core edit 5]]. It was found by asking what the project checks
about itself rather than by tripping over something.

And a *sixth*, which breaks the pattern the first five share and is the reason
this file needed a sixth heading rather than a footnote. Every edit above is
something the lattice *asked for* — it tried to do a thing, the surface would
not let it, and the request is what got written down. Core edit 6 is the
opposite: the core had already done the lattice's job for it, in
=src/policy/appearance.lisp=, by reading the extension's private property key
off a node and destructuring the extension's private representation of an
address inline. The lattice never had to ask, so nothing was ever written down,
and *the list you are reading was incomplete for two months without being
wrong about anything it contained*. See [[#edit-6][core edit 6]].

The first five are one species: the extension surface was correct for the author
and incomplete for a stranger, in ways that only being a stranger revealed. The
sixth is a second species, and a worse one, because being a stranger would not
have revealed it — the surface *worked*, and it worked because the core was
quietly doing the extension's half of it.

| Measure | Value |
|---------+-------|
| Lines in =lattice/= | 2,077 (427 model, 779 policy, 500 commands, 311 map and overlay, 60 package) |
| ~defmethod~ forms | 28 |
| Core generics specialised | 14 (12 policy, 2 persistence) |
| Container protocol members | 19, of which the lattice answers 13 |
| New container classes | 1 |
| *Core files edited* | *7* (two for the lattice, two for the examples, four for the workspace decision, one shared) |
| *Core behaviours changed* | *0* |
| Core bugs exposed by extending | 3 |
| *Core edits the extension never asked for* | *1* (see [[#edit-6][core edit 6]]) |

Gate 3 asks for the line and method counts precisely because it is satisfiable
in bad faith — push everything through ~props~ and ~&rest~ arguments and the
letter passes while the spirit dies. PLAN.org sets the reading: "A lattice that
is three hundred lines of methods is the thesis holding. One that is two
thousand lines re-implementing geometry is the thesis failing while wearing the
gate's uniform."

2,077 lines is well above three hundred, so the honest question is what the
extra lines are. They are: the plane's own data structure (427), which nobody
claimed would come free; the zoom, pan and jump *commands* (500), which are
user-facing verbs rather than layout mechanism; the coordinate overlay and the
minimap (311), which are two of the three orientation aids DESIGN names as the
mitigation for its own biggest risk and are drawing code, not layout; and 779
lines of policy of which the substance is twelve methods and the rest is the
reasoning behind them. *No geometry is re-implemented.* The lattice calls
~divide-rect~, ~tree-move~, ~tree-swap~, ~tree-transplant~, ~repair-path~,
~descend-to-leaf~ and ~find-motion-target~ and defines none of them.

* The twelve policy generics the lattice specialises
:PROPERTIES:
:CUSTOM_ID: twelve
:END:

This is the whole of the layout, navigation and workspace change.

| Generic | What the lattice makes it mean |
|---------+--------------------------------|
| ~layout-children~ | place the visible cells on a coordinate plane |
| ~step-address~ | move one cell, bringing empty cells into being on arrival |
| ~entry-address~ | arriving at a plane from outside lands per ~*workspace-entry*~ |
| ~motion-escapes-p~ | *never* — the plane has no edge (D6) |
| ~clip-rect~ | crop a cell overhanging the viewport, per ~set_content_clip_box~ |
| ~gaps~ | cell gaps are wider than split gaps |
| ~border-color~ | tint by coordinate hue, the cheapest orientation aid |
| ~border-width~ | thicken the cell holding the keyboard |
| ~keys-hint~ | teach the two facts about cells nothing else can |
| ~on-focus-change~ | remember which cell each plane was left standing in |
| ~make-workspace~ | *a workspace is a plane* — the entire Z axis, in one method |
| ~cursor-place-name~ | the status line says =3,-2= rather than =0.1.0= |

Plus ~serialize-node~ and ~deserialize-node~, so a plane survives a restart.

~cursor-place-name~ is the newest and is here for an unflattering reason: the
core used to answer it *for* the lattice. See [[#edit-6][core edit 6]].

~clip-rect~ is here for a worse one: this row was true of the *source* and false
of the *program* for the whole life of the method, because the bound it reads was
written nowhere. See [[#dead-property][the method that could not fire]] — which is
also where ~:fixed~ zoom stops being half-built.

~make-workspace~ is the one that arrived last and matters most, because it is
the difference between the lattice being an arrangement you set up and being
the shape of the system. See [[#edit-4][core edit 4]].

*It is also the one that costs the user something, and that went unrecorded for
the whole life of the extension.* It is a /total/ override — it wins wherever
the shipped method applied and never calls ~call-next-method~ — so the option
that method reads, ~*new-workspace*~, decides nothing at all while the lattice
is enabled. Nothing could see that: the reader still exists, so
[[file:PLAN.org::#gates-added][gate 11]] certified the option as read, and
~--list-options~ went on printing it. Two of the rows above are the same shape
narrowed to one container kind — ~gaps~ takes ~*gaps*~ away for cells, ~gaps~ on
a stack takes it away for tabs — and those are fine, because the option still
answers everywhere else. The unconditional one is the one that owes something
back, and it pays: ~*new-workspace-cells*~ is the same decision at the same
tier for somebody who will never write a ~defmethod~. Gate 15 is what makes
that a rule rather than a courtesy, and =latticewm --extension-surface= prints
the override under the option it switches off.

*And the cell override pays too, which only became visible later.* ~gaps~ on a
cell does not merely take ~*gaps*~ away, it reads ~*cell-gap*~ in its place — a
knob of the extension's own, at the same tier, for the same person. That was
true from the day the method was written and appeared in no document, because
the surface named the options an override *removed* and never the ones it
*added*. It does now: the generic's own entry reads =answered from: *cell-gap*,
*gaps*=, so a reader of a lattice image meets the extension's knob at the
generic it answers rather than having to know the extension has one. See gate
17 in [[file:PLAN.org::#gates-added][PLAN §gates-added]].

Plus twelve methods on the *container protocol* — ~container-addresses~,
~child-at~, ~(setf child-at)~, ~insert-child~, ~remove-child~,
~container-count~, ~default-address~, ~simplify-node~,
~container-alternatives-p~, ~container-splits-along-p~, ~copy-node-slots~,
~print-object~ — which is the cost of being a container at all and is the
number the experiment was really measuring.

*Twelve methods is what it costs to teach this window manager about an infinite
plane, and a thirteenth makes every workspace one.* Everything else — motion,
layout recursion, tree surgery, focus repair, persistence, the commands that
move windows between cells, and the fact that the workspace list was already
infinite — works without knowing the lattice exists.

* Core edit 1 — a missing export

*File:* =src/package.lisp=. *Change:* export ~default-address~ from
=LATTICEWM/CORE=.

~default-address~ is the structural half of entry resolution: the address a
descent into a container takes when nobody has a direction to offer. Focus
repair and ~first-leaf-path~ call it, a ~stack~ answers with its selected child
so that repair never lands on a hidden tab, and a ~grid~ has to answer with its
first *occupied* visible cell or focus repair lands in empty space.

The core defined it, documented it, and specialised it — and forgot to publish
it. A mechanical omission, and the least interesting possible finding, but it
is a finding: *the container protocol had a member that an outside implementor
could not reach*, and nothing would have detected that except trying.

* Core edit 2 — ~layout-children~ was partial

*File:* =src/policy/conventional.lisp=. *Change:* add a default method
specialised on ~container~, giving the whole rectangle to ~default-address~'s
child and hiding the rest — that is, behaving like a stack.

This one is real, and it is the finding worth having.

Before the edit, ~layout-children~ had methods for ~split~ and ~stack~ only. A
policy meeting a container kind it had never heard of signalled
~no-applicable-method~. So an extension author adding a container type was
silently obliged to *also* teach every other policy in the image about it —
including policies they had never seen and could not modify — or their
container would crash any policy but their own.

That is the exact failure mode DESIGN's §extensibility warns about, arriving
from an unexpected direction:

#+begin_quote
"CLOS means there is no hook set to guess wrong." Only true if the code is
written as fine-grained generics. […] *Extensibility is a property of the
decomposition, not of the language.*
#+end_quote

The decomposition was fine-grained. What it was not was *total*. A protocol
whose operations are partial functions is not an extension point; it is a set
of special cases with a docstring, and the obligation it creates is invisible
until somebody trips over it.

*The generalisable rule, which is the actual output of this experiment:* every
generic in the extension surface needs a method on the most general class it
dispatches on, and that method must be correct rather than merely present.
Behaving like a stack is correct for any container whatsoever — it shows
something, it shows only one thing, and it cannot overlap.

Checked against the rest of the surface after the fact: ~step-address~,
~entry-address~, ~motion-escapes-p~ and ~gaps~ already had ~container~-general
or ~t~-general methods. ~layout-children~ was the only gap.

* Core edit 4 — the *default shape of a new workspace* was not a decision
:PROPERTIES:
:CUSTOM_ID: edit-4
:END:

*File:* =src/policy/protocol.lisp=, =src/policy/structure.lisp=,
=src/runtime/verbs.lisp=, =src/policy/layout.lisp=. *Change:* a new generic,
~make-workspace (policy world index)~, and the four sites that grow the
workspace list now ask it instead of building a node.

*This is the sharpest finding in the file, because nothing failed.*

The requirement is "infinite workspaces of lattices one behind another". Both
halves looked done. The workspace list is a ~stack~ at the root of the tree and
a stack grows, so ~workspace 40~ on a machine with three makes forty — infinity
cost nothing, exactly as designed. And ~lattice:enable~ wraps every workspace in
a ~grid~, so the workspaces are planes. A test asserted a stack of grids
behaves. It passed. It had always passed.

What no test asked was whether the stack *stays* made of grids. It did not.
~enable~ wraps the workspaces that exist at the moment it runs; every workspace
created afterwards came from one of four places in =src/= that each wrote
~(c:make-leaf)~ inline. So on a machine that enables the lattice at startup and
then presses Super+7, workspace 7 is a plain pane on a system whose first six
are planes. No error. No log line. Zoom simply does nothing when you get there,
and the natural conclusion is that zoom is broken.

*The shape of the mistake:* a wrapper applied once was standing in for a
default. "Every workspace is a plane" and "every workspace that existed at 09:00
is a plane" are different claims, and the code could only express the second
while the documentation, the tests and the author all read it as the first.

*Why the extension could not fix it from outside.* There was no generic to
specialise. The lattice can change what a workspace *looks like*, how motion
crosses it, how it is drawn, saved, copied and clipped — but not what one *is*
when the core makes a new one, because the core did not make new ones through
anything. Four inline constructor calls are not an extension point, and they are
invisible as a gap precisely because each is one obviously-correct line.

*The generalisable rule, and it is the one this whole file keeps rediscovering
from new directions:* /a default that an extension cannot replace is not a
default, it is a hard-coded value with good manners./ Core edit 2 found a
protocol operation that was partial; this one found a decision that was never a
protocol operation at all. Partial operations announce themselves —
~no-applicable-method~ is loud. A missing one announces nothing, ever, and is
found only by someone using the system long enough to create a workspace after
startup.

*Two more things fell out of it, and both were latent bugs of the same
species.*

~send-to-workspace~ addressed the workspace *node*. Right for the empty leaf the
core ships, wrong for anything richer: sending a window to a lattice workspace
made the whole plane one half of a split — viewport, column widths and cell
names demoted to half a screen — and it had been that way for as long as both
features existed. It descends with ~descend-to-leaf~ now, which is the question
it was always asking, and which each container kind already knew how to answer.
The core path is unchanged to the character, because a leaf descends to itself.

~ensure-workspaces-for-outputs~ had the same inline constructor, so plugging in
a second monitor after startup produced a pane beside a plane.

*Cost:* one generic, one method, one option (~*new-workspace*~), four call sites
that got shorter. The lattice's half is a single ~defmethod~ — and that method,
not any amount of new machinery, is the entire Z axis.

* Core edit 3 — the shipped defaults were on the class users specialise

*File:* =src/policy/conventional.lisp= and =src/policy/lifecycle.lisp=.
*Change:* every default method moved from ~conventional-policy~ to ~policy~,
its superclass.  ~conventional-policy~ now has no methods at all.

*Found by writing the worked examples and running them*, which is the argument
for shipping examples as tests rather than as prose.

The failure is invisible until somebody writes the obvious thing:

#+begin_src lisp
(defmethod gaps ((policy conventional-policy) container) 8)
#+end_src

That does not *extend* the shipped method, it *replaces* it — same generic,
same specialisers — and any ~call-next-method~ inside it signals
~no-next-method~.  Two of the four examples hit this immediately, and the error
message is about CLOS rather than about the mistake.

This is the most serious of the three, for a reason PLAN.org states directly:

#+begin_quote
The code a cheap model needs to write here is
~(defmethod place ((p my-policy) node rect) …)~.  Small, formulaic, three
worked examples beside it, verified live at a REPL before it is committed.
That is the easiest possible target.
#+end_quote

That is only true if the formula *works*.  "Do what you were going to do, plus
this" is overwhelmingly the common shape of a real extension, and it needs
~call-next-method~, and ~call-next-method~ needs the shipped behaviour to live
on a strictly more general class than the one the user names.

*The generalisable rule:* the class a user is told to specialise on must never
be the class the defaults are defined on.  Ship a concrete subclass with no
methods, and put every default on its parent.  Cost: one class.  Benefit: the
obvious thing works, and the surface no longer requires understanding CLOS
method combination before it can be used at all.

*Recorded consequence, and it is uncomfortable:* the extension surface passed
gate 2, passed 416 unit tests, and ran a real window manager for three hours
while being unusable in its single most common mode.  No gate here could have
caught it.  What caught it was writing four extensions the way a stranger would
and running them, which is exactly the qualitative check PLAN.org §honest says
"there is nobody available to run".  There is a lesson in that about which
kinds of verification are worth the time, and it is not the one I would have
predicted.

* The bug the lattice found

Not a core edit but a core *fix*, and it would have been very unpleasant to
find any other way.

~tree-transplant~ re-derived its destination after detaching the moved subtree,
using ~node-path-to~ to check that the destination had survived. The path to
the *root* is the empty list, which is false, so the check reported the root as
missing — and the recovery branch returned the tree *without reinserting what
it had detached*.

For the conventional layer this was nearly unreachable: transplanting into the
root container means sending a window to a workspace, and the root is the
workspace stack, so the destination was always a child. For the lattice it is
the common case, because a grid *is* the container you transplant into. Every
"move this window to cell (3,2)" would have deleted the window.

Fixed with ~node-contains-p~, which answers the survival question directly
instead of inferring it from a path that can legitimately be empty. Both are
now exported, and the docstring says why one must not be used for the other.

*Recorded because it is evidence for the sequencing rather than against it.*
D21's argument for building the lattice second was that failure would be
discovered "in week three on a small codebase with a working conventional
window manager already in hand." This is precisely that: a latent core bug,
surfaced by the first extension that exercised the path, on a codebase small
enough that the fix took one function.

* What the lattice did *not* need
:PROPERTIES:
:CUSTOM_ID: free
:END:

Worth listing, because these are the things a "no core edits" claim usually
founders on, and each one is a place the container protocol turned out to be
drawn correctly.

- *Motion across the cell boundary.* Zero lines. Moving right from the
  rightmost pane of a split inside cell (0,0) lands on the leftmost pane of
  cell (1,0), entering through the edge it crossed, and it is involutive.
  ~find-motion-target~ ascends out of the split, asks the grid, and descends —
  and it does not know what a grid is. PLAN.org's Delta 1 predicted this and it
  is the single strongest result here.
- *Moving a window from a split into another cell's split.* ~tree-move~,
  unmodified.
- *Moving a whole cell, splits and all, to another coordinate.*
  ~tree-transplant~, unmodified (after the bug above).
- *Swapping two cells.* ~tree-swap~, unmodified.
- *Focus repair through a plane.* ~repair-path~, unmodified.
- *Workspaces of planes, one behind another.* A ~stack~ of ~grid~ s. Nothing
  was written; it is what the two container kinds compose to.
- *A plane nested inside a split, or inside another plane.* Also free, also
  untouched, and nobody asked for it. Its being free is the evidence the
  abstraction sits at the right level.
- *Persistence, floating, minimize, fullscreen, tabs.* Untouched.

* The protocol answered D19's open question, and the fallback was wrong

Not a core edit — a *design* finding, and the most useful thing measured
against the real compositor.

[[file:DESIGN.org::#d19][DESIGN D19]] makes typing in an empty pane conditional on one unverified fact,
and states the consequence of it going the wrong way:

#+begin_quote
*Unverified — this is a Week 1 check, and the design degrades if it fails.*
[…] 2. Does it carry the keysym, or only the fact that /a/ key was unbound?
*If it carries no keysym, only the single-default mode is possible* and the
table dies.
#+end_quote

*Measured against the shipped protocol: ~ate_unbound_key~ has no arguments at
all.* Not a keysym, not a keycode, nothing:

: <event name="ate_unbound_key" since="2"> … </event>

So the mechanism D19 rests on cannot support the table, exactly as feared. But
the fallback — "only the single-default mode is possible" — is *wrong*, because
the document considered only one route.

*The third option: bind the keys ourselves, and enable them only while they
apply.* ~river_xkb_binding_v1~ has ~enable~ and ~disable~ precisely so that a
binding can be conditional. Each key in the table gets a real binding, enabled
when the cursor is on an empty pane and disabled the rest of the time.

That is strictly better than the plan it replaces:

- the keysym arrives, because it is *our* binding, so the table survives whole;
- it composes better than ~ate_unbound_key~ would have, because an unmodified
  ~t~ is not intercepted when it would have gone to an application — the
  binding is not enabled then, rather than being enabled and then declined;
- ~ensure_next_key_eaten~ is left for the thing it is actually for, which is
  letting a chorded submap notice a key it does not bind. D19 worried these two
  uses would compete. They no longer share a mechanism, so they cannot.

*Verified end to end:* split a pane, land the cursor in the empty half, press
~t~, and a terminal opens *in that pane*.

The transferable lesson is about how the question was framed rather than about
keyboards. D19 asked "does this event carry what I need?", got the answer no,
and had a fallback ready for no — but the fallback assumed the event was the
only way in. It was worth ten minutes to ask what else the protocol offered.

* What only running it could find

Recorded separately from the core edits, because these are a different kind of
result: not "was the surface extensible" but "was any of it *right*". Fourteen
defects were found by running the window manager under a real compositor and
looking at it, and none of them was reachable from a unit test.

The pattern is worth more than the list. *Every one of them was invisible to
the model.* The tree was correct, the tests passed, and the thing on screen was
wrong — or was correct and unusable. A model is a claim about structure, and
none of these were structural.

| Defect | Why no test could see it |
|--------+--------------------------|
| Floating windows could never be focused | The model has no opinion about keyboard focus; it is derived |
| The screen was up to thirty seconds stale | ~wait-until-fd-usable~ restarts on EINTR, so the wakeup was delivered and ignored |
| Commands changed the model and not the screen | Only the key path asked for a manage sequence |
| ~request-manage~ hung when called off-thread | A race, and it did not error — it *hung*, holding the desktop |
| The zoom anchor showed empty space | +Y up means biasing the opposite way on Y from X |
| Multi-monitor drew every window twice | The model was fine; the *projection* of it was not |
| Binding ~wl_shm~ killed startup | An event nobody reads, about formats nobody asked for |
| The empty pane was invisible | Nothing in the model says what a person can see |
| The help screen truncated every line mid-word | Legibility is not a property of data |

The two that are worth naming individually, because they say something about
the architecture rather than about a bug:

*The sequence discipline paid for itself three times.* Enabling a keybinding, a
cross-thread relayout, and every window-management request in a command each
tried to reach the wire in the wrong protocol context, and each produced a
named, continuable error at the point of use instead of a dead connection and a
hang to bisect. That was the whole argument for building it, made on its first
contact with a real compositor.

*Half the fixes were structural rather than local.* Window-management requests
left the commands entirely and became state the emitter reconciles; ~mark-dirty~
became the single thing that pushes work to the screen; ~output-content~ became
a policy generic. In each case the bug was a symptom of a decision that had not
been made explicitly, and the fix was to make it.

* The first run on two outputs, and on a real panel
:PROPERTIES:
:CUSTOM_ID: two-outputs
:END:

Run 2026-08-06, nested inside a KWin session: river 0.4.6 on the Wayland
backend with =WLR_WL_OUTPUTS=2=, driven through the control socket, read back
through =grim= — which speaks =wlr-screencopy= to the nested river, so the
pixels are the ones river composited and not a photograph of somebody's desk.

*The two things README called unreachable were reachable, and one environment
variable was the whole difference.* The Status section said the layer-shell
path had "no headless layer-shell client to open a panel with" and that
multi-monitor "has been executed against one display". Both were true of the
build sandbox and false of any machine with a package manager on it. That is
worth stating as a shape: *an untested path is a claim about the harness, not
about the world, and the harness is the thing you control.*

** What ran for the first time and was right

- *The exclusive-zone arithmetic.* A real panel taking 34px at the top moves
  =outer-rect= from 0,0 1280x696 to 0,34 1280x662, and the window under it moves
  down by exactly that. Read and not run for two weeks; run now, correct on the
  first try.
- *One overlay per output.* Both outputs drew their own drawn-map surface,
  independently, at their own origin. This is the per-output work the Status
  section listed as written-but-unexercised.
- *A clean two-output start.* Two outputs, two workspaces, distinct nodes.
- *The capture announcement, against a real capture client.* =grim='s screencopy
  session raised =REC= in the status line, announced "recording started: screen
  WL-1", and cleared when grim exited. The integration suite could only assert
  this from constructed state; a screenshot tool is a real one.

** The multi-monitor collapse came back, through a door the fix did not cover — *fixed, and there were two more doors*
:PROPERTIES:
:CUSTOM_ID: collapse
:END:

The table above records *Multi-monitor drew every window twice*, and
=output-content='s docstring names the symptom precisely enough to quote:

#+begin_quote
Returning the same node for two outputs is a mistake with a specific and
confusing symptom, so it is worth naming: every window gets placed twice, the
second placement wins, and the whole layout silently collapses onto the last
output while the model insists everything is fine. That was the first
implementation.
#+end_quote

It is also the current implementation, under one condition: *a saved layout with
fewer workspaces than there are outputs at the next start.*

Measured, with a layout saved on one output and reloaded on two: two outputs,
*one* workspace, output props correctly assigned 0 and 1 — and
=output-content= clamping both to the last valid index, so the two outputs
return the identical node. The second monitor is entirely black. No window, no
empty-pane welcome, no focus border. Its status line says =workspace 1/1=,
=0,0=, =1 window=, which is the model insisting everything is fine, verbatim as
predicted.

Spawn a window while looking at the first monitor and it opens on the second,
and the cursor follows it there, because =current-output= derives from where the
cursor rests and the cursor went where the layout put it.

*Why the fix did not cover it.* =ensure-workspaces-for-outputs= exists for
exactly this and its docstring says so — "without it, a second monitor arrives,
finds only one workspace, and mirrors the first". It is called when an output
appears. Restoring a saved layout afterwards replaces the workspace stack with
the saved one, and nothing asks the question a second time. The two mechanisms
are each correct and their *order* is not, which is why every gate and both
suites pass: there is no state in which either one is wrong on its own.

*Why nothing could see it.* Gate 14 fires every declared hook during the
integration run, and =:layout-restored= fires — with one output, where a
one-workspace stack is the right answer. The integration suite runs a headless
river, whose backend announces one output. The unit suite constructs worlds and
so constructs their outputs. Every instrument was pointed at a one-monitor
world, and the defect needs two monitors *and* a restore to exist.

*** The fix, and the sentence above that was too kind to the design

"The two mechanisms are each correct and their /order/ is not" is the shape of a
scheduling mistake, and it named the door rather than the room. The room is
this: *nothing owned the invariant.* =ensure-workspaces-for-outputs= was named
after a moment — "called when an output appears" is the first line of its
docstring — and six places wrote =(prop output :workspace)= directly, each of
them individually right.

So the restore is one door of at least three, and the second one needs no
restore, no saved file and no unusual state at all:

#+begin_example
  clean two-monitor start:  (("HEADLESS-2" 0) ("HEADLESS-1" 1))  :distinct 2
  cursor is on: "HEADLESS-2"
  after (workspace 2):      (("HEADLESS-2" 1) ("HEADLESS-1" 1))  :distinct 1
#+end_example

*Two monitors, one keystroke, and the layout has collapsed.* ~show-workspace~
set the property with no reference to what the other screen was showing. The
third door is ~focus-window-anywhere~ in =runtime/tags.lisp=, which does the
same thing when you follow a tagged window to its workspace.

The repair is three things, and the middle one is the one that generalises:

- ~ensure-workspaces-for-outputs~ states the *property* rather than the moment:
  every output shows a workspace, no two show the same one, and the stack is
  grown until that is possible. It repairs a duplicate assignment and an index
  that has fallen out of range, neither of which it used to look at.
- *It is asserted before every layout.* =RELAYOUT= is the one path to a screen,
  it is idempotent, and in the case where nothing is wrong it is a ~length~, a
  comparison and one pass over the outputs. No door into the workspace stack has
  to remember any more, because there is nothing to remember.
- ~show-workspace-on~ is the single writer of the property, and the two screens
  *trade*: the other monitor takes the workspace this one was showing. Moving
  the keyboard to the monitor that already has it — what i3 does — is a
  defensible reading of the same request and is not this one, because here the
  cursor is a place in a model rather than a consequence of which screen is
  active.

And ~output-content~'s clamp stays, demoted to a guard: it is what an extension
that writes the property itself gets instead of a black screen. When two outputs
do come back with the same node, the emitter now says so once, in the log,
naming the symptom — which is the one thing that never happened in the whole
history of this bug.

*Measured both ways, on two real outputs, through the control socket.* Before:
one workspace, both outputs on it, one distinct node between two screens, and
two nodes placed twice each. After: two workspaces, two distinct nodes, nothing
placed twice — and the clean-start switch above trades to =(("HEADLESS-2" 1)
("HEADLESS-1" 0))= instead of collapsing. Six unit tests, in the case nobody had
constructed: *a world with two outputs in it.*

** The drawn map paints over the echo area — *fixed*
:PROPERTIES:
:CUSTOM_ID: map-echo
:END:

=draw-map-on= lays its cells out in =outer-rect= — which respects reserved space,
correctly — and then sizes and commits its canvas at =output-rect=, the whole
screen. So the background fill covers the strip the layout deliberately left
alone, and the status line is blank for as long as the map is up.

It is *not* a layer-shell problem: a panel sits on a higher layer and survives
the map intact, which is what made the first reading of this wrong. It is the
window manager covering its own echo area.

The tell is internal to the function: =area= and the canvas rect disagree, and
the code already knows which one is right, because it used it for the cells.
And the contrast is instructive — =overlay-wanted-p= suppresses the *coordinate*
overlay under the map and spends four lines explaining why. Nothing says the
status line should go, because nothing decided it should.

Confirmed rather than inferred: with the map up, =echo-content= still returns
all five segments and =map-mode-p= is true, and the bar renders empty. The
policy is right and the screen is wrong, which is this section's whole subject.

*The fix is the sentence above.* The canvas is sized and committed at =area=,
the rectangle the cells were laid out in — three expressions, all of them
replacing =output-rect= with the value the same function had already computed
two lines earlier.

Two things are worth adding. The first is that *the same mismatch was in
=overlay.lisp= too*, where it is invisible: the coordinate overlay also takes a
full-screen canvas and commits it at the whole output, and gets away with it
only because its labels are small and everything between them is transparent.
It is fixed as well, because a latent copy of a bug that has already been paid
for once is worth removing rather than leaving for whoever gives it a
background.

The second is what now checks it, since the reason this survived is that
*nothing could*. It is a screen fact — two rectangles overlapping — so a unit
test cannot reach it and neither can a gate. The integration suite runs the
lattice against a real river, so it raises =*map-threshold*= above the width of
the screen, which makes every cell too small by definition, and asks river's own
two surfaces where they are:

#+begin_example
  ok    the drawn map has an overlay of its own
  ok    and it does not touch the echo area's strip: map 0..696, status line 696..720
  ok    because it is exactly the area the cells were laid out in
#+end_example

Verified by breaking it on purpose, which is the only way to know a check works:
with the old canvas rectangle the same three lines read =map 0..720= and fail.

** ~quit~ does not always quit, about one run in three — *withdrawn: it always quit, and the check failed when it quit fastest*
:PROPERTIES:
:CUSTOM_ID: quit-flake
:END:

*This finding was wrong about its subject and right that something was wrong.*
What follows is what was recorded on the day; the diagnosis is underneath it,
and it inverts the claim. =quit= has never once failed to end the session. The
*assertion* failed, and it failed on precisely the runs where the shutdown was
quickest.

*** What was recorded on the day

=make check= was run seven times over the session. Twice, the last check of the
integration suite failed:

#+begin_example
---- shutting down
  ok    the shutdown hooks run once however many times shutdown is asked for (1 run)
  ok    and the layout was written on the way out
  FAIL  and QUIT ends the session
#+end_example

Two failures in seven runs, with nothing else changed between them and no
leftover processes — the four-run sequence that produced the second failure
started from a clean tree. The budget is not the problem: =poll-until= waits ten
real seconds for =server-running= to go false, which is not a tight assertion
about a shutdown.

So *=quit= sometimes does not end the session within ten seconds*, and this is
the first defect in this file that was found by running the suite repeatedly
rather than by running it once. It matters twice over: it is a window manager
that sometimes does not exit when told, and =make check= now requires the
integration suite, so CI is red about a third of the time on a tree where
nothing is wrong with the change under test — which is the condition under which
people learn to re-run a build instead of reading it.

Not diagnosed here, and worth *not* guessing at: the shape resembles the lost
wakeup in the table above, where =wake-event-loop= set a flag and threw into a
CATCH that was not on the stack, and the loop then sat in a thirty-second wait
with work already queued. That one was hit about one run in five. The
resemblance is a place to look and not a finding.

*** What it actually was

Reproduced first — two failures in four runs, then two in six — and then
instrumented rather than reasoned about, because the previous paragraph is what
reasoning about it produced. The probe printed =*server*= and the state of the
window manager's thread at the moment the check ran. Every failing run says the
same thing:

#+begin_example
PROBE: server=NIL thread=NIL
PROBE after poll: answer=NIL server=NIL thread=NIL
  FAIL  and QUIT ends the session
#+end_example

On the failing runs the window manager was *entirely gone*: the event loop had
returned, =START='s ~unwind-protect~ had run the shutdown, closed the
connection, set =*server*= to ~NIL~ and returned, and the thread had finished —
all inside the few hundred microseconds between =quit= answering and the next
line of the test. The passing runs are the *slower* ones, where the check
sampled while the teardown was still in flight.

The check read ~(server-running *server*)~. With =*server*= ~NIL~ that is a
type error, not an answer — and =poll-until= wrapped every call in
~ignore-errors~, so for ten full seconds a broken predicate was indistinguishable
from a condition that had not yet come true. The report then said the one thing
that was not so.

*** The two repairs, and the second is the one that generalises

- *The check now asks a fact that survives the teardown.* The session ending is
  =START= returning, and =START= returning is its thread finishing. That is
  monotonic — once true it stays true — which is what an assertion about a
  shutdown has to be made of. Reading a slot off a live object to detect that
  the object is being torn down cannot be made reliable by waiting longer.
- *=poll-until= no longer swallows the difference between "no" and "broken".*
  Tolerating an error is right: half the predicates in that suite read state
  that is being built while they read it. Discarding it is not. It keeps the
  last condition now and prints it when the wait times out having never once
  answered — one line, on the run where it happens, saying what the predicate
  said instead of an answer. That line is the whole finding, and it would have
  been there on 2026-08-06.

*Verified:* six consecutive runs of =make integration=, six passes, against two
failures in four and two in six on the same tree before the change.

*What it says about the eight defects in [[#two-outputs][the table above]].* Every one of them was
a case of the *model* being right and the *screen* being wrong. This is the
third species: the model was right, the screen was right, and the *instrument*
was wrong — and it accused the program. A check that fails when the program is
fastest is worse than no check, because the story it tells is coherent: a
shutdown that sometimes hangs is a completely believable bug, and a page of this
document was written about one that never existed.

** Smaller, from the same sitting

- *The status line is hard-clipped mid-word at the right edge*, with nothing to
  say it was clipped. =echo-content= ends "...Super+- zoom out"; the screen ends
  "...past a cell edge = next cel". The help screen had this bug once already —
  it is the ninth row of the table above.
- *=tools/hardware-check.lisp= names a function that does not exist*,
  =current-viewport=, and so warns on every startup that loads it.
- *One 67-second stall*, in the first screencopy after a panel first appeared;
  steady state is 0.05s and it did not reproduce in a dozen attempts. Recorded
  because *The screen was up to thirty seconds stale* is in the table above and
  was a lost wakeup, not because this is known to be the same thing.

* Found by looking at the machine instead of at the program
:PROPERTIES:
:CUSTOM_ID: spin
:END:

Every defect above was found by running the window manager and *watching the
screen*. This one was found by running ~ps~ for an unrelated reason.

Six LatticeWM processes, left over from an earlier session, at 95% of a core
each. Load average 7.7 on an idle machine. Their river had been dead for an
hour. Not one of them had written a line to its log since the moment it was
orphaned, and not one of them had exited.

: PID     ELAPSED     TIME %CPU STAT
: 103407 01:18:54 00:59:21 75.2 Rsl
: 106681    59:56 00:54:12 90.4 Rsl
: 108281    54:18 00:53:14 98.0 Rsl

*The mechanism is exact and it is nobody's bug in particular.* A stream socket
whose peer has closed is *readable* — a read would return zero rather than block
— so ~sb-sys:wait-until-fd-usable~ returns immediately, every time, for ever.
wayflan's ~wl-display-listen~ then asks whether a message is available, and its
~%read-once~ gets ~0~ back from ~recvmsg~ for end of file and ~0~ for "nothing
yet, try later", and cannot tell the caller which, because both are the same
integer. So ~dispatch-events~ reads nothing, signals nothing, and answers ~t~.
Wait, read nothing, answer ~t~, wait. A busy loop with no error anywhere in it,
which is the one shape that leaves no trace.

*And it is the failure the design already knew about, reached from the other
side.* ~display-fd~ exists at all because polling would cost "a laptop that runs
hot and flat while apparently sitting idle" — its own words. That fix made the
*idle* case free and left the *dead* case spinning, and the difference between
the two is one question nobody asked the kernel.

poll(2) answers it. =POLLHUP= is set in the reply whether or not it was asked
for, and it is the direct statement of what ~select~ structurally cannot say:
this descriptor is readable /because the other end is gone/. One syscall per
wakeup, asked after the events have been dispatched so that a compositor exiting
cleanly — a last message and a hangup in the same read — is drained before it is
declared dead. The alternative is to infer the hangup from "we woke up and there
was nothing there", which is an inference where an answer is available.

*Verified:* river killed with =SIGKILL=, and again with =SIGTERM=. Both times
the window manager logs "compositor closed the connection", runs its shutdown
hooks, saves the layout and exits within a second — against for ever, silently,
before.

*The transferable part is the third method this file has now collected.* The
first was write an extension and trip over something. The second was ask what
the project checks about itself. The third was distrust a green build. This is a
fourth and it is the cheapest of all: *look at the machine the program is
running on.* Six processes at 95% of a core is not a subtle signal, and nothing
inside the program — no test, no gate, no log line, no screen — was ever going
to produce it, because from the inside the loop was doing exactly what it was
told.

It is also why two integration runs failed that afternoon on checks about how
long a client takes to exit. A machine under load is an instrument out of
calibration, and the noise was the bug.

* Where the honest claim now stands

DESIGN's §extensibility settled on a deliberately modest claim:

#+begin_quote
We are building a plugin API either way. In Common Lisp it costs zero days of
boundary code, it is not a wall when you need to go past it, and an AI can
extend it later without rebuilding anything.
#+end_quote

That survives, and this experiment adds one thing to it that the document could
not have known: *the boundary was crossed twice, and both crossings were
repairs to the surface rather than exceptions to it.* Neither edit changed a
behaviour, neither required understanding the conventional layer, and both make
the *next* extension cheaper rather than being paid again.

What has *not* been demonstrated, and should not be claimed:

- The lattice was written by the same author as the core, on the same night,
  with the whole design in mind. That is the easiest possible case, and
  PLAN.org's §honest already says the only real check on decomposition quality
  is qualitative and there is nobody available to run it.
- Two edits is a small number, but the *rule* they produced — every surface
  generic needs a correct method on its most general class — was learned by
  tripping over it, not by design. There may be more of them, and the way to
  find out is a second extension by somebody else.
- Gate 3 remains satisfiable in bad faith and this result does not change that.
  It is reported here as raw numbers so that a reader can disagree with the
  interpretation.

** And on one of the two install paths, the extension was not in the package

Every number above is about an extension somebody has to be able to *get*.
=flake.nix= kept its own list of what ships, beside =install.sh='s, and that
list did not include =lattice.asd= or =lattice/= — so a =nix build= produced a
window manager whose shipped sample configuration loads an extension that was
not there, on the one path that reaches a user who never ran =make=. Gate 9
exists precisely to prevent that and had been reading the other installer.

The lattice is compiled into the image, so this was not visible as a crash;
what was missing is the half the argument above rests on — *the sources beside
the machine that runs them*, and =(load-extension "lattice")= working in an
image built without it. A reader who wanted to see the 28 methods this document
counts had the package and not the code.

There is one installer now. See [[file:PLAN.org::#gates][PLAN §gates]], gate 9.

* Core edit 5 — one of the two protocols could not describe itself

:CUSTOM_ID: edit-5
:END:

*File:* =src/model/surface.lisp= (new), =src/model/node.lisp=,
=src/package.lisp=, =tools/gates.lisp=. *Change:* the container protocol
became introspectable, generated and gated, the way the policy protocol already
was. *Behaviour changed:* none. *Found by:* nobody, for the life of the
project, which is the finding.

*This is the fifth of the same species and the largest.* The first four were
each one missing thing on a surface that otherwise worked. This one is a whole
half of the surface that no check could see, and the tell is that its
consequences had all four shapes at once:

- ~replace-child~ was exported from =latticewm/core=, listed in
  =src/package.lisp= under the comment "the container protocol", and *defined
  nowhere at all* — a ~defgeneric~ that does not exist, on the advertised

  says nothing about what the protocol contains. The generated document is
  built from the live image, so a name with nothing behind it simply does not

  check that catches this is a *test* and not a document.
- ~serialize-node~ and ~deserialize-node~ were declared in
  =src/runtime/state.lisp=. They are as much a part of the contract as
  ~child-at~ — a kind that skips them loses the user's layout on every restart,
  silently — and being in the runtime package put them outside every statement
  of what the protocol is. They are declared in =model/node.lisp= now, beside
  the other seventeen, with their methods left where the file format is.
- *Nothing anywhere said how many members there are.* This file's own
  [[#free][what you get for free]] list is the closest thing, and it lists what a
  kind /inherits/ rather than what it must answer. The number is *nineteen*.

  #+CLAIM: (= 19 (length (container-protocol-generics)))

  Six of them have defaults that are correct for a dense integer-addressed
  container and wrong for anything else, which is what makes skipping them
  silent: a grid written with the source open answered the obvious six, loaded
  without complaint, and broke on copy, on save and on focus repair.

*The generalisable rule, and it is the one this file keeps rediscovering in a
new place each time:* an extension surface that cannot describe itself is not a
surface, it is a convention. The policy protocol had ~policy-generics~, a
generated document and a documentation gate from Week 1, and every finding
above about it was a *missing method* — a small, local, fixable thing. The
container protocol had none of the three, and its findings are missing
definitions, misplaced declarations, and an unstated size. The difference is
not that one protocol was designed more carefully. It is that one of them was
checked.

*Cost:* one new file (~180 lines, of which about half is the reasoning),
three helpers moved out of =policy/surface.lisp= so both surfaces share one
formatter, one flag (~--container-surface~), ten lines in gate 2, and a new
test suite. Zero behaviour changes, zero source files moved.

*What it says about the four above:* they were all found by writing an
extension and tripping over something. This one was found by asking what the
project checks about itself and noticing an asymmetry. Those are different
methods and the second one is cheaper — but it only works on a project that
already has one good half to compare the other against.

* Core edit 6 — the core doing the extension's job for it
:PROPERTIES:
:CUSTOM_ID: edit-6
:END:

*File:* =src/policy/appearance.lisp=, =lattice/policy.lisp=,
=src/package.lisp=, =tools/gates.lisp=. *Change:* the echo area asks a generic
where the cursor is instead of reading the lattice's property key itself.
*Behaviour changed:* none, with or without the lattice loaded. *Found by:*
auditing why gate 6 passed, which is the least likely place anybody would have
looked for it.

*The edit that was already there.* The shipped ~echo-content~ built its
"place" segment like this:

#+begin_src lisp
(place (or (and node (c:prop node :lattice/address)
                (format nil "~d,~d"
                        (car (c:prop node :lattice/address))
                        (cdr (c:prop node :lattice/address)))))
#+end_src

Two things about the extension are compiled into the core there: the property
key =:lattice/address=, and the fact that an address is a cons of x and y. Both
are ~lattice/grid.lisp~'s private business, and the second one is the kind of
private that breaks silently — the day an address becomes a struct, the status

*Why this one is not on the list above.* Every core edit in this file exists
because the lattice tried to do something and could not. This one is the
inverse and it is worth stating as a rule, because it generalises past this
project:

#+begin_quote
*An extension point can be defeated by the core using it correctly.*
~echo-content~ was made a generic — in ~4fe8811~, explicitly so that "a lattice
policy would sensibly add the viewport" — and then the *default method* did the
lattice's part of the job, so the lattice never overrode it and the generic was
never exercised from outside. A seam is only a seam if somebody on the other
side has to reach for it.
#+end_quote

Every check the project has was satisfied. Gate 2 saw a documented generic.
The generated extension surface listed it. Gate 3 asked whether the lattice
touches the core, and it does not — this was the core touching the *lattice*,
which nothing asked. Gate 6, as it then was, counted lines by directory and
would have counted these four lines as *policy*, which they are, in the sense
that has nothing to do with the question. And the behaviour was right: load the
lattice and the status line shows =3,-2=, because the core had already written
the code to make it.

*The repair, and the two checks it comes with.* ~cursor-place-name (policy
world)~ is a generic on the appearance surface; its shipped default answers the
cursor path, which is the one name every layout model has; the lattice answers
~cell-string~, four lines, on the outside. Nothing else moved.

Then the checks, because a repair without one is a coincidence:

- *Gate 3 gained the direction it never had.* No file under =src/= may name an
  extension's private namespace. It scans code with comments and string bodies
  blanked, so the docstrings that explain the rule — including the one above —
  cannot satisfy or trip it. That distinction is not pedantry: gate 3's own
  first version failed on being told it passed.
- *Gate 6 became the count of generics answered from outside =src/=.* This edit
  moves it by one, which is the smallest possible demonstration that the number
  measures the right thing: a boundary correction that changes no behaviour and
  moves no file still shows up, because a method got written on the outside that
  was not there before.

*Cost:* one generic, two methods, one export, and about forty lines of gate.
Zero behaviour changes, zero source files moved.

*What it says about the five above:* they are all things a stranger found by
being a stranger. This one a stranger could not have found, because from the
outside the surface worked perfectly — the lattice's status line said the right
thing. It was only visible from inside, by asking why a *gate* was passing.
That is the third distinct method in this file, after "write an extension and
trip over something" and "ask what the project checks about itself", and it is
the most expensive of the three: it needs somebody to distrust a green build.

* The method that was on the right generic and could not fire
:PROPERTIES:
:CUSTOM_ID: dead-property
:END:

*File:* =lattice/policy.lisp=, =lattice/map.lisp=, =src/policy/layout.lisp=,
=tools/gates.lisp=. *Change:* the plane records the rectangle it was laid out in,
so ~clip-rect~ can crop against it; ~:fixed~ zoom honours the column and row
sizes it was dropping; the core's unreachable third render tier is deleted; gate
13 is the check that would have found all three on the day. *Behaviour changed:*
yes, and it is the point. *Found by:* reading the table at the top of this file
against what the program actually does.

*~clip-rect~ is a row in [[#twelve][the twelve]] and it did nothing at all.* It is
river's ~set_content_clip_box~, which [[file:DESIGN.org::#feasibility][DESIGN §feasibility]] calls
the best find in the whole protocol: a cell half over the viewport edge is
cropped /and its border is redrawn at the crop edge/, free, by the compositor,
where the alternative was "a week of bad approximation". The lattice's method for
it read =:lattice/viewport-bounds= off the node. Nothing wrote
=:lattice/viewport-bounds=. The key occurred exactly twice in the tree — that
read, and a docstring — so the bound was always ~nil~, the method always fell
through to ~call-next-method~, and ~call-next-method~ is the core's "nothing
overhangs here, clip nothing".

*Nothing could see it, and the list of what looked at it is the finding.* An
absent property is a legal answer and ~nil~ is a legal return, so there was
nothing to signal. Gate 3 saw an extension answering a generic. Gate 6 counted a
method answered from outside =src/=. Gate 2 saw a documented generic. The unit
suite had a test named
~fixed-zoom-keeps-cells-the-same-size-and-crops-the-trailing-one~ which asserted
where the trailing track /starts/, called that "to be cropped by the clip box",
and never asked ~clip-rect~ anything. Every instrument agreed, and each of them
was answering a question about the /shape/ of the code.

*And underneath it, the mode itself was half-built.* ~:fixed~ is the zoom mode
[[file:PLAN.org::#delta-3][Delta 3]] exists to provide and the one
~resize-column~'s own first-use warning tells you to switch to when ~:fit~'s
panning cost becomes intolerable. Three things were wrong with it:

- ~fixed-tracks~ took a /count/ and gave every track exactly ~*cell-width*~, so
  *~resize-column~ and ~resize-row~ did nothing whatsoever under ~:fixed~*. The
  advice sent you to the mode where the thing you had just done stopped working,
  silently. D8's ruling is that a size belongs to a column and spans every row;
  under ~:fixed~ the weight scales the absolute size, which is what it does now.
- a cell whose track had run *entirely* past the edge was still placed, at a
  position off the screen, and river shows a window unless it is explicitly
  hidden. Omitting it is what hides it, and that is one clause.
- ~map-mode-p~ decided whether cells were too small to render by dividing the
  output width by the column count, which is the ~:fit~ answer and nothing at all
  under ~:fixed~ — so eight columns of a 960-pixel lattice computed 240 pixels
  and put the drawn map up over cells that were full size. Both callers ask
  ~cell-tracks~ now, which is the one place that knows how big a cell is.

#+CLAIM: (let ((lattice:*zoom-mode* :fixed) (lattice:*cell-width* 500)
#+CLAIM:       (lattice:*cell-height* 600) (lattice:*cell-gap* 0))
#+CLAIM:   (let* ((grid (lattice:make-grid
#+CLAIM:                :cols 3 :rows 1
#+CLAIM:                :cells (list (cons (lattice:cell 2 0) (make-leaf)))))
#+CLAIM:          (policy (make-instance 'lattice:lattice-policy))
#+CLAIM:          (placed (layout-children policy grid (make-rect 0 0 1200 600)))
#+CLAIM:          (box (cdr (assoc (lattice:cell 2 0) placed :test #'equal)))
#+CLAIM:          (clip (clip-rect policy (child-at grid (lattice:cell 2 0)) box)))
#+CLAIM:     (and clip (= 1000 (rect-x clip)) (= 200 (rect-w clip)))))

*The core had the same bug, in the same week, with nothing in common but the
mechanism.* ~render-order~'s shipped method sorted tiled nodes, then floats,
"then anything marked as overlay" — a third tier for a node carrying an
=:overlay= property. Nothing has ever written that property, and nothing was ever
going to: every overlay in this program — the echo area, the help page, the
cursor, the lattice's coordinate labels and its map — is a *surface* rather than
a node, made by =runtime/surface.lisp=, and none of them is in a render list. A
documented tier with no way in. It is deleted rather than wired up, because the
tier a policy actually wants is the method: ~render-order~ is the extension
point, an override of it is obeyed for the whole list, and a property key
standing in for a generic is the mistake ~*smart-gaps*~ made with an option.

*Gate 13 is the half of this that matters.* Props is the third way to keep state
here, and it was the unchecked one. An option is registered and gate 11 asks
whether anything reads it; a hook is declared and gate 7 asks whether anything
runs it; a property key is neither registered nor declared — it is a keyword
somebody types in two places, and nothing compared the two. So the gate reads
=src/=, =lattice/= and =examples/= with the *reader* rather than grepping them: a
key is found by symbol identity against ~prop~, so every nickname the tree uses
is the same function, a docstring naming a key is a string and cannot make it
pass, and a ~setf~ place is distinguished from a read structurally rather than by
looking left for a bracket. One forwarder — ~node-window-prop~, the bridge a
window rule's colour crosses to reach a generic handed a node — is named in the
table rather than special-cased.

*It fails one direction and reports the other, and that asymmetry is the
argument.* A key that is read and never written is provably dead: the read is
~nil~, the branch never runs, nothing signals, and there is no arrangement of the
program in which that was the intent. A key that is *written* and never read is a
different animal, because [[file:DESIGN.org::#d20][D20]] is that props exists for
exactly this — state hung on an object for a reader the core does not know about.
Four are in that position today and the build prints all four:

: label -- written in src/policy/lifecycle.lisp
: locked -- written in src/runtime/session.lisp
: pid -- written in src/runtime/windows.lisp
: presentation-hint -- written in src/runtime/windows.lisp

=:pid= and =:presentation-hint= are facts river's events carry and a status bar
would want; =:locked= is the session-lock state. Failing on those would be a gate
ordering the program to grow a consumer, which is a check writing the design.
*=:label= is the one worth a decision*, and it is not made here: it is a
documented ~window-rule-for~ override key, it is honoured into a property, and
nothing displays it — so a rule that names a window names it to nobody. That is
~*smart-gaps*~'s species again and the fix is not obvious, because it wants a
ruling on what a window's name is /for/ before it wants code.

deleted ~cond~ branch, about a hundred lines of gate, five unit tests and the
first section in the integration suite that runs the extension against a real
compositor — which is where the remaining question lived, because a clip box
outside the window's content is river's ~invalid_clip_box~ error and it takes the
connection down rather than returning anything. It sends one now, for a cell
overhanging by 638 pixels, and river keeps talking to us.
