* The decision: what we are building
:PROPERTIES:
:CUSTOM_ID: decision
:END:

An *external window manager for the river Wayland compositor* implementing a spatial
model that does not currently exist anywhere:

- Each workspace is an *infinite 2D lattice of cells* addressed by integer
  coordinates.
- Each cell contains an *Emacs/i3-style split tree* — leaves are windows, internal
  nodes are horizontal or vertical splits, nestable arbitrarily.
- The *viewport* is an N×M rectangle over the lattice. *Zoom is the choice of N×M*:
  1×1 shows one cell fullscreen, 2×1 shows two, 2×2 shows four, 3×2 shows six.
- *Panning* moves the viewport over the lattice.
- Windows and whole cells can be *moved between cells* easily.
- There are *many lattices* — infinite workspaces, each its own plane.

** Why this is the idea

Zoom is normally a *mode* you enter and leave (GNOME overview, niri's Overview).
Here zoom is a *continuous layout control*: one knob replaces both workspace-switching
and tiling-layout-selection. That collapse of two concepts into one is the novel part.

Every half of this exists somewhere. The combination does not:

| Existing thing | What it has | What it lacks |
|----------------+-------------+---------------|
| niri / PaperWM | Infinite strip, overview zoom, drag between workspaces | Only 1D; vertical axis is discrete workspaces; overview is a mode |
| i3 / sway | Exactly this cell split-tree model | One root per workspace, no plane, no zoom |
| Notion / Ion3 | Static frames split like Emacs, tabs in frames | X11, no plane, no zoom |
| Material Shell (GNOME) | An explicit 2D grid (workspaces=rows, windows=columns) | Fixed axis semantics, not pannable or infinite, GNOME-bound |
| Eagle Mode, Pipeworld | True zooming UIs | Continuous planes, not daily-driver WMs |

** Why it survives the ZUI curse

Historically, zooming user interfaces die because users get lost — Pad++, Raskin's
Archy, Eagle Mode. That failure mode belongs to *continuous* planes.

This design uses a *lattice with integer coordinates*. Cells have addresses. That
buys: jump-to-(3,−2), jump-to-named-cell, relative movement by one cell, and a
minimap that is a finite grid rather than a fog. Discrete geometry is dramatically
more memorable than continuous space.

*This is still the single biggest design risk.* Two dimensions is more than twice as
hard to hold in your head as niri's one. Design against it from day one: minimap,
named cells, and seriously consider a *bounded* lattice rather than a truly infinite
one.

* Feasibility verdict: river can do all of it
:PROPERTIES:
:CUSTOM_ID: feasibility
:END:

Verified against the actual protocol XML (=river-window-management-v1=, version 5,
and =river-xkb-bindings-v1=, version 3), not summaries.

*Every element of the spec maps to an explicit protocol feature. There are no gaps.*

| Requirement | Protocol mechanism |
|-------------+--------------------|
| Infinite lattice, arbitrary coordinates | ~river_node_v1.set_position(x, y)~ — "The x and y coordinates may be positive or negative." |
| Z-order between overlapping cells | ~place_top~, ~place_bottom~, ~place_above(other)~, ~place_below(other)~ |
| Park distant cells cheaply | ~river_window_v1.hide~ / ~show~ |
| Arbitrary cell sizes | ~propose_dimensions(width, height)~, ~set_dimension_bounds(max_w, max_h)~ |
| Clean viewport edges | ~set_clip_box~ / ~set_content_clip_box~ (see below — this is the good one) |
| Cell borders | ~set_borders(edges, width, r, g, b, a)~ |
| The lattice, split trees, workspaces | *Nothing in the protocol.* Entirely our data structures. |
| Keybindings | ~river_xkb_bindings_v1.get_xkb_binding(seat, id, keysym, modifiers)~ → ~enable~ |
| Emacs-style key sequences | ~ensure_next_key_eaten~ / ~ate_unbound_key~ |
| Hold-Super-to-zoom-out | ~modifiers_watch~ / ~modifiers_update~ |
| Multi-monitor | ~river_output_v1.position(x,y)~ + ~dimensions(w,h)~ in logical space |
| Minimap / overview UI | ~get_shell_surface(id, surface)~; shell surfaces get their own ~get_node~ |
| Drag windows between cells, drag-to-pan | ~op_start_pointer~ → ~op_delta(dx,dy)~ (cumulative) → ~op_release~ → ~op_end~ |
| Driving our own animation | ~manage_dirty~ |
| Restoring layout across WM restart | ~river_window_v1.identifier~ event |

The decisive design fact, from river's changelog:

#+begin_quote
"The compositor will no longer have any knowledge of window management concepts such
as tags, workspaces, output focus, etc. The window manager will have full control
over window positioning, sizing, keyboard focus, keybindings, pointer move/resize
operations, and more."
#+end_quote

There is *no existing spatial model to fight*. That is what makes an unusual model
feasible at all.

** The best find: content clipping

~set_content_clip_box~ clips window content /excluding/ borders and decorations, and:

#+begin_quote
"Borders drawn by the compositor (see set_borders) are placed around the intersection
of the window content (as defined by the dimensions event) and the content clip box
when content clipping is enabled."
#+end_quote

So a cell half-scrolled off the viewport edge is clipped *and its border redraws at
the clip edge*. It reads as a cleanly cropped cell rather than a window sliced in
half. Proper viewport boundaries, free, from the compositor. Budget zero time for
this; it was expected to cost a week of bad approximation.

Note there are two: ~set_clip_box~ clips the window *including* borders and
decorations; ~set_content_clip_box~ excludes them. Both may be enabled at once. Both
are ignored while a window is fullscreen.

* The protocol, in the detail that matters
:PROPERTIES:
:CUSTOM_ID: protocol
:END:

** The manage/render state machine

This is the core of the protocol and the source of its worst bug class.

Two disjoint categories of state:

- *Window management state* — influences compositor↔window communication. Window
  dimensions, fullscreen, keyboard focus, keyboard bindings.
  *May only be modified during a manage sequence.*
- *Rendering state* — affects only rendered output. Position, render order, hide/show,
  borders, clip boxes.
  *May be modified during a manage or a render sequence*, and is applied at the next
  ~render_finish~.

Violating this is a hard protocol error: ~river_window_manager_v1.error.sequence_order~.

The loop, from the spec:

#+begin_example
1. Server sends all state changes since last manage sequence, then manage_start.
2. Client modifies window-management state and/or rendering state, then manage_finish.
3. Server sends new state to windows and waits for responses.
4. Server sends new window dimensions to client, then render_start.
5. Client modifies rendering state, then render_finish.
6. If dimensions change, loop to 4.
   If manage-requiring state changes, or client sends manage_dirty, loop to 1.
#+end_example

A manage sequence is *always* followed by at least one render sequence. Multiple
render sequences may occur consecutively without an intervening manage sequence
(e.g. a window changes its own dimensions).

*** Which requests belong to which category

Window-management state (manage sequence only):
- ~river_window_v1~: ~close~, ~propose_dimensions~, ~use_csd~, ~use_ssd~, ~set_tiled~,
  ~inform_resize_start~/~inform_resize_end~, ~set_capabilities~,
  ~inform_maximized~/~inform_unmaximized~, ~inform_fullscreen~/~inform_not_fullscreen~,
  ~fullscreen~, ~exit_fullscreen~, ~set_dimension_bounds~
- ~river_seat_v1~: ~focus_window~, ~focus_shell_surface~, ~clear_focus~,
  ~op_start_pointer~, ~op_end~, ~pointer_warp~
- ~river_pointer_binding_v1~: ~enable~, ~disable~
- ~river_xkb_binding_v1~: ~set_layout_override~, ~enable~, ~disable~
- ~river_xkb_bindings_seat_v1~: ~ensure_next_key_eaten~,
  ~cancel_ensure_next_key_eaten~, ~modifiers_watch~

Rendering state:
- ~river_node_v1~: ~set_position~, ~place_top~, ~place_bottom~, ~place_above~, ~place_below~
- ~river_window_v1~: ~hide~, ~show~, ~set_borders~, ~set_clip_box~, ~set_content_clip_box~
- ~river_decoration_v1~: ~set_offset~, ~sync_next_commit~
- ~river_shell_surface_v1~: ~sync_next_commit~
- ~river_output_v1~: ~set_presentation_mode~

*** OPEN QUESTION: a contradiction in the spec

The ~river_window_manager_v1~ interface description says rendering state "may be
modified by the window manager during a manage sequence or a render sequence."

But individual rendering-state requests (~set_position~, ~hide~, ~show~, ~set_borders~,
~set_clip_box~) each say "may only be made as part of a render sequence, see the
river_window_manager_v1 description" — pointing back at the description that
contradicts them.

The interface description is more detailed and explicitly addresses the question, so
it is probably authoritative and the per-request wording is shorthand. *Verify against
river's implementation before relying on setting positions during a manage sequence.*
This matters: doing position updates in the manage sequence would halve the round
trips for animation.

** Gotchas that the online summaries hid

1. *Windows do not take the dimensions you propose.* ~propose_dimensions~ is
   advisory; the spec explicitly calls out terminal emulators that quantize to cell
   size. The real size arrives in a ~dimensions~ event, possibly several render
   sequences later.
   *Design decision required:* when a window is smaller than its cell, do we center
   it, top-left it, or letterbox it? This visibly defines how the whole WM looks.
   Decide before writing layout code.

2. *Render order is undefined by default.* "The initial position of a node in the
   render list is undefined, the window manager client must use the place_above or
   place_below request to guarantee a specific rendering order." Every node must be
   explicitly ordered. Matters most during zoom transitions when cells overlap.

3. *There is no frame or timer event.* To animate a zoom, drive it from our own event
   loop using ~manage_dirty~, which forces a manage sequence, which is always
   followed by a render sequence. That is a full manage round trip per animation
   frame — heavier than a pure render loop. *Prototype smooth zoom early; do not
   assume it.* (See the open question above — if rendering state really is legal in
   manage sequences, this gets cheaper.)

4. *A slow WM means laggy input, and can be fatal.* There is an ~unresponsive~
   protocol error, and the spec says the compositor should wait for the manage
   sequence to complete before processing further input events. Respond promptly.

5. *New windows are not displayed* until the WM makes a ~propose_dimensions~ or
   ~fullscreen~ request in a manage sequence, the server replies with a ~dimensions~
   event, and that render sequence finishes. Newly created windows are considered
   *shown* unless explicitly hidden — so offscreen cells must be hidden deliberately.

6. *~pointer_position~ alone never starts a manage sequence* ("This state is special
   in that a change in pointer position alone must not cause the compositor to start
   a manage sequence"). Pan-follows-mouse cannot be driven from pointer position
   alone; use an interactive op or ~manage_dirty~.

Decoration render order, bottom to top:
1. decorations from ~get_decoration_below~
2. window content
3. borders from ~set_borders~
4. decorations from ~get_decoration_above~

** ~identifier~ — the key to persistence

~river_window_v1.identifier~ (since v4): up to 32 printable ASCII bytes, non-empty,
uniquely identifies the window, *never reused*, matches
~ext_foreign_toplevel_handle_v1.identifier~ if that protocol is implemented. Sent once
at window creation.

This is what lets the lattice survive a WM restart or hot-swap: serialize
identifier → (workspace, cell coordinate, position in split tree) on shutdown, restore
on startup.

** Chorded keybindings are a first-class feature

~ensure_next_key_eaten~ exists precisely for this. From the spec's own rationale:

#+begin_quote
"the window manager may wish to implement 'chorded' keybindings where triggering a
binding activates a 'submap' with a different set of keybindings. Without a way to eat
the next key press event, there is no good way for the window manager to know that it
should error out and exit the submap when a key not bound in the submap is pressed."
#+end_quote

Emacs-style ~C-x C-f~ sequences, supported by the protocol. Given how many commands
this WM needs (jump to cell, move to cell, split, resize, zoom, workspace switch),
this is likely to be central to the keymap design. ~cancel_ensure_next_key_eaten~
handles submap timeouts.

* Language: Rust
:PROPERTIES:
:CUSTOM_ID: language
:END:

*Decision: Rust, using =wayland-client= + =wayland-scanner= (the =wayland-rs= project).*

Reasons, in order of weight:

1. *Bindings maturity.* =wayland-scanner= generates Rust from custom protocol XML
   (=generate_interfaces!=, =generate_client_code!=). ~4.7M downloads/month, used by
   2,939 crates. Nothing in any other language is close.
2. *Proven for this exact task.* =canoe= is a complete, working window manager for
   this exact protocol, written in Rust on =wayland-client=. See [[#prior-art][Prior art]].
3. *The type system prevents this protocol's worst bug class.* See below.
4. *LLM authorship.* Large, current training corpus; ~cargo~ + ~clippy~ give a tight
   correctness loop, which matters more than usual when the author is not reading
   every line.

Performance is explicitly a non-issue. From Isaac Freund's design notes: the protocol
avoids a per-frame compositor↔WM roundtrip, so "having a garbage collector in the
window manager does not really matter." Language choice is about correctness and
tooling, not speed.

** Why not the others

- *Zig* — the "native" choice (river is Zig; =zig-wayland= is by river's own author).
  Rejected: =zig-wayland= uses =0.major.patch= versioning with *API-breaking changes
  expected until Zig 1.0*, requires zig 0.16, and "does not currently do extensive
  verification of Wayland protocol XML or provide good error messages." Decisively:
  Zig's training data is thin *and stale* — the language changes faster than models
  learn it. Worst possible fit for LLM-written code.
- *Python* — =pywayland= describes itself as "highly experimental" with "usage likely
  to change between releases." Not acceptable under a daily-driver WM, despite GC
  being fine here.
- *C* — reference =wayland-scanner=, entirely viable, but manual memory, listener
  structs, and zero type-level help with the sequence state machine.
- *A Lisp* — an embedded Lisp (Steel, Janet, Rhai) as a *config/policy layer inside*
  the Rust binary remains a live option for later. It is explicitly *not* needed on
  day one. See [[#live][Live reconfiguration]].

** Day-one architecture decision: type-state for manage/render

The protocol's most dangerous rule is the manage/render split, and it is easy to get
wrong because some requests are legal in both contexts. Encode it in the type system
so the compiler makes the bug unrepresentable:

#+begin_src rust
/// Only obtainable inside a manage sequence.
pub struct ManageCx<'a> { /* ... */ }
/// Only obtainable inside a render sequence.
pub struct RenderCx<'a> { /* ... */ }

/// Rendering state is legal in both — pending verification of the spec
/// contradiction noted above.
pub trait RenderScope {}
impl RenderScope for ManageCx<'_> {}
impl RenderScope for RenderCx<'_> {}

impl Window {
    // window-management state: manage sequence only
    pub fn propose_dimensions(&self, cx: &mut ManageCx, w: i32, h: i32) { /* ... */ }
    pub fn close(&self, cx: &mut ManageCx) { /* ... */ }

    // rendering state
    pub fn hide<S: RenderScope>(&self, cx: &mut S) { /* ... */ }
    pub fn set_content_clip_box<S: RenderScope>(
        &self, cx: &mut S, x: i32, y: i32, w: i32, h: i32,
    ) { /* ... */ }
}
#+end_src

If the spec contradiction resolves against us, drop the trait and make rendering
requests take ~&mut RenderCx~ only. Either way the protocol error becomes a compile
error.

* Live reconfiguration
:PROPERTIES:
:CUSTOM_ID: live
:END:

Three tiers. *Build tiers 1 and 3 first. Tier 2 is optional and later.*

** Tier 1 — config file with live reload (hyprland-style)

Plain-text config, reloaded without restart. =canoe= already implements exactly this:
=~/.config/canoe/canoe.toml=, reloaded on ~SIGHUP~ (=pkill -HUP canoe=), refreshing
theme, desktop, window rules and key bindings live. Copy the pattern.

** Tier 3 — hot-swap the entire window manager

River's headline capability, and it is *strictly better than hyprland's config
reload*, which hyprland structurally cannot match because there the WM and compositor
are the same process.

The WM is an ordinary Wayland client. Kill it, recompile, relaunch — the compositor
and every application keep running. The dev loop becomes: edit Rust → ~cargo build~ →
swap → still logged in, same session, same windows.

The catch: a fresh WM process has no memory of the lattice. Windows are re-advertised
via ~window~ events with undefined positions. Hence the persistence layer keyed on
~identifier~. *Get this working early — it makes the entire development cycle
pleasant.*

** Tier 2 — embedded scripting (optional, later)

An embedded Lisp/Scheme (Steel, Janet, Rhai) so layouts are functions redefinable at
runtime. Real power, real work. Not required for the first version, and explicitly
deprioritized given the time budget.

** canoe — use this as the reference implementation

[[https://github.com/roblillack/canoe][github.com/roblillack/canoe]] — a stacking WM for river, in Rust.

- Rust 99.9%, =wayland-client=, protocol XMLs vendored in-repo (=protocol/=, at v3),
  =build.rs= generating bindings.
- Active: v0.5.1, last commit ~2026-06, 91 stars, 1 contributor (Robert Lillack).
- CI via GitHub Actions incl. Linux/ARM64, lint, test, build.
- *Has a =shell.nix=* — drops straight into a NixOS workflow.
- Proves end-to-end: shell surfaces, server-side decorations, titlebars, shadows,
  menus, font rendering, per-window rules, multihead, interactive move/resize.
- Config at =~/.config/canoe/canoe.toml=, ~SIGHUP~ to reload live.
- Installed with =cargo install canoe=, run with =river -c canoe=.

*This is the single most valuable artifact for the project.* Read it for the event
loop, the manage/render cycle in practice, binding setup, and the config-reload
pattern.

** orilla — read, do not build on

[[https://sr.ht/~hokiegeek/orilla/][sr.ht/~hokiegeek/orilla]] — a Rust WM library for river, XMonad-inspired.

Three crates: =orilla-core= (the ~Layout~ trait, ~LayoutMessage~, ~OutputGeometry~,
~WindowInfo~), =orilla= (library: built-in layouts, keybindings, tags, event loop),
=orilla-run= (TOML-config binary). Configured in Rust via a =cargo-generate= template;
your config is a normal Rust binary building an ~Orilla~ instance and calling ~run()~.
Launched from =~/.config/river/init=.

*Verdict: probably the wrong abstraction for us.* Its model is XMonad's — /arrange N
visible windows inside one output rectangle/. LatticeWM needs most windows hidden,
positioned outside output bounds, clipped at a moving viewport boundary, in per-cell
split trees. That is not a layout function.

*Action:* spend ~20 minutes reading =orilla-core= to confirm or kill this judgement.
Its keybinding and event-loop plumbing may be worth stealing even if the ~Layout~
trait is not.

- *Arcan* — a "desktop engine" where the desktop is a Lua script; Durden and Pipeworld

  existing answer to "programmable desktop." Not a dependency.
- *Project Oberon* — Wirth's complete system in ~25k lines; free online. One
  transferable idea: /commands are text, text is everywhere, therefore commands are
  everywhere/. Worth considering for the command model.

** Ecosystem timing

The =river-window-management-v1= protocol landed in river's main branch on
*2025-12-10*. Release 0.4.0 will remove all window-management behavior from the
compositor, making an external WM *mandatory*; =river-classic= is a hard fork
preserving 0.3.x for those who don't want that.

Consequence: *there is an active vacuum for river window managers right now.* Being
early is an advantage here. Risks: the protocol is new and may still shift, and the WM
will be river-only (not portable to sway or hyprland).

** Data model

#+begin_src rust
struct Lattice {           // one per workspace
    cells: HashMap<CellCoord, Cell>,
    viewport: Viewport,
}

struct CellCoord { x: i32, y: i32 }

enum Cell {                // an i3/Emacs-style split tree
    Leaf(WindowId),
    Split { dir: Dir, ratio: f32, a: Box<Cell>, b: Box<Cell> },
}

struct Viewport {
    origin: CellCoord,     // top-left visible cell
    cols: u16, rows: u16,  // the zoom level: 1x1, 2x1, 2x2, 3x2 ...
}
#+end_src

** Questions to settle before coding

- [ ] *Window smaller than its cell* — center, top-left, or letterbox? (Forced by
      ~propose_dimensions~ being advisory. Affects the entire look.)
- [ ] *Bounded or truly infinite lattice?* Bounded is far more navigable. Strongly
      consider bounded-but-growable.
- [ ] *Zoom levels* — a fixed ladder (1×1, 2×1, 2×2, 3×2, 4×3) or arbitrary N×M?
- [ ] *Non-uniform cells?* Should a cell be able to span two grid positions?
- [ ] *Do cells persist when empty*, or are they created on demand?
- [ ] *What happens at the viewport edge* — hard clip, or partial cells visible via
      ~set_content_clip_box~? (The protocol makes partial cells cheap; they may be
      the better UX, showing you what's adjacent.)
- [ ] *Navigation model* — jump to coordinate, jump to named cell, relative motion,
      minimap. Which are primary?
- [ ] *Keymap* — flat bindings or Emacs-style submaps via ~ensure_next_key_eaten~?
- [ ] *Persistence format* — identifier → (workspace, coord, tree path). Where stored,
      when written?

* Implementation plan
:PROPERTIES:
:CUSTOM_ID: plan
:END:

Four weeks, assuming the spike succeeds.

** Week 0 — the spike (one day, do this first)

Get =canoe= building and running under NixOS via its =shell.nix=; run =river -c canoe=
from river's main branch (*not* the packaged 0.3.x, *not* =river-classic=). This proves
the entire toolchain — river main, protocol version, Rust bindings, NixOS integration —
before a line is written. If it fails, diagnose before doing anything else.

** Week 1 — core client

Connect, bind globals, handle the manage/render loop with the type-state design.
Place windows in a fixed 2×2. Verify:
- offscreen positioning + ~hide~/~show~ behave as expected
- keybindings work via =river-xkb-bindings-v1=
- whether rendering state is genuinely legal in manage sequences (the open question)

** Week 2 — the lattice

Lattice, viewport, zoom levels, panning, cell↔window mapping, ~set_content_clip_box~
at viewport edges, explicit node ordering. Config file + ~SIGHUP~ reload.

** Week 3 — structure

Intra-cell split trees (i3-style), moving windows between cells, moving whole cells,
multiple workspaces, persistence keyed on ~identifier~ so hot-swap is seamless.

** Week 4 — navigation and polish

Jump-to-coordinate, named cells, minimap as a shell surface, zoom animation (prototype
this earlier if possible — see gotcha 3), documentation, packaging.

* Ideas considered and rejected

:CUSTOM_ID: rejected
:END:

*Do not re-propose these without addressing the stated reason.*

| Idea | Why rejected |
|------+--------------|
| Rewrite Emacs in Rust | Decade-scale. Remacs died at =xdisp= and elisp GC — "things couldn't be updated piecemeal." Rune is one person, 0.1.0, and its author says it won't be a usable replacement. Would leave 100k lines of unmaintainable Rust when Max expires. |
| Multithreaded Emacs (worker pool) | The month-sized version *already exists and was ignored*: =session-async.el= is a persistent stateful Emacs session on MELPA, one author, dormant since 2023. Org's own subprocess async (~org-export-in-background~) demonstrates the fatal structural problem — the worker needs your config, and reproducing it is fragile. Async ~org-agenda-redo~ was proposed in 2019 by Org's current maintainer and never landed on the data-transfer problem. Live buffers are structurally off-limits (buffer mutex). Most heavy Emacs work is already subprocesses. |
| Windows programmable/Lisp WM | Superseded — Shaul chose Linux. Was genuinely a real gap (no StumpWM/EXWM-class WM exists for Windows; komorebi is scriptable, not programmable), and remains a viable *future* project. Blockers were: cannot replace DWM, elevated windows untouchable, UWP/Electron need a permanent app-rules database, virtual-desktop APIs undocumented and break on Windows updates. |
| Declarative/plain-text photo editing | GUI feel dominates the value; competing with 15 years of darktable colour science. Worst possible ground for a code-first approach. Shaul's own assessment, correct. |
| Unified reading environment | Rejected outright. |
| Standalone org tangler (no Emacs) | Weak: Emacs is already available everywhere Shaul works, so there is no real use case. |
| Local search across everything | ~rg~ covers content search. Everything (voidtools) is unbeatable on NTFS filename search because it reads the MFT directly. Remaining gap too narrow to be a project. |
| Live-coding audio environment | Shaul does not do audio. |
| Typst/DOCX converter, SQL Server client, screenshot automation, release pipeline, structured terminal, filesystem time-travel, programmable spreadsheet | Various — mostly failed the "would you use it daily" or "could it become the standard" bars. See conversation history if resurrecting one. |
| Contributing to Arcan | Possible but means advancing someone else's 13-year vision; Linux/BSD only; the hard parts are graphics plumbing where there's no advantage. |
| Building on Smithay (own compositor) | Not rejected — held as *fallback*. Order of magnitude more work than a river client. |
| LiNix work | Off-limits by Shaul's explicit instruction: "if I wanted to make LiNix better, I would ask you to help me with that." |
