#+TITLE: LatticeWM
#+AUTHOR: Shaul Khayyat
#+OPTIONS: toc:2 num:nil

An extensible window manager for the [[https://codeberg.org/river/river][river]] Wayland compositor, written in Common
Lisp, whose layout model is a *replaceable policy layer* rather than the program
itself.

[[file:doc/echo-area.png]]

It tiles the way you expect — recursive splits, tabs, workspaces, floating,
multi-monitor, pointer drag-and-resize, panels and status bars — and then lets
you change any of it while it is running, without a restart and without a
rebuild.

#+begin_quote
There has never been a Common Lisp Wayland window manager. This is one.
#+end_quote

* The one idea to read first

*A pane may deliberately hold no window, and that is not a degenerate case —
it is how you place slack.*

This is genuinely unlike i3, sway, dwm or Hyprland, where a pane without a
window does not exist. Here:

- you split a pane and leave one side empty, and the window occupies the rest.
  That is the resize idiom;
- focus is a *place*, not a window. It can rest on an empty pane, and Wayland
  keyboard focus is *derived* from where it rests rather than stored;
- so =close= (take the pane with it) and =clear= (empty it, leave it standing)
  are two different verbs rather than one verb with a mode;
- and standing in an empty pane, typing =t= opens a terminal, =e= an editor.
  The empty pane is a spawn menu with no menu.

Everything else in the model follows from that, including a few things that
look surprising until you have read it. It is worth the thirty seconds.

* Install

You need *river 0.4.6* and *SBCL*. That river release specifically: the window
management protocol changes within a version number, so LatticeWM checks and
refuses rather than misbehaves — [[file:INSTALL.org][INSTALL.org]] explains it and says how to move to
a later river. Any Linux — nix is one supported route, not a requirement.
Per-distribution package names are in [[file:INSTALL.org][INSTALL.org]].

#+begin_src sh
git clone https://github.com/SYKhayyat/LatticeWM && cd LatticeWM
./bootstrap.sh     # fetch the Lisp dependencies into ./.deps/   (or: nix-shell)
make               # build, fourteen gates, 1600+ checks
make check         # the above, plus a real river driven headlessly -- and it
                   # fails rather than skips when river or a terminal is absent
make run           # river nested in the session you are already in — try it here first
#+end_src

Once you like it:

#+begin_src sh
./install.sh       # binary, a session entry, a launcher and a man page
#+end_src

=install.sh= adds a =wayland-sessions= desktop entry, so *LatticeWM appears at
your login screen* like any other desktop. =--prefix /usr/local= installs
system-wide; =--uninstall= takes it back out. It never overwrites an existing
=init.lisp=.

In a session you are already running river in: =river -c latticewm=.

* The first thing to press

*=Super+/=* draws the entire keymap on screen, with what each binding does —
built from the *live* bindings and each command's own docstring, so it includes
anything you bound five minutes ago and it cannot go stale.

You will also get a short *welcome overlay the first time it starts*, listing
the half-dozen keys that matter. Any key dismisses it, it never appears again,
and =M-x welcome= brings it back. To stop it appearing at all:

#+begin_src lisp
(setf *welcome-on-first-run* nil)   ; in ~/.config/latticewm/init.lisp
#+end_src

* Keys

Every binding below is generated from =*modifier*=, which defaults to =Super=.
Change that one value and the whole keymap moves with it.

Both the vi letters and the arrow keys are always bound. That is deliberate
rather than indecisive: the arrows are what you use on your first day and the
letters are what you use on your hundredth.

Minimize leaves the tiling tree rather than collapsing it, so restoring puts
the window back where it was. Floating and unfloating do the same, so looking
at something and putting it back is symmetric.

*Undo is a layout undo.* It restores the arrangement, and it cannot un-quit an
application — a window that has closed since is simply absent from the tree
that comes back. =Super+? u= lists what it would walk through.

** The pointer

| =Super=+drag        | move a window (a tiled one floats first) |
| =Super=+right-drag  | resize it, from the corner you grabbed   |
| click               | focus, and raise if it is floating       |
| a titlebar drag     | honoured, for clients that draw their own |

No *unmodified* button is bound, deliberately: a window manager that grabs
plain left-click cannot be used with any application.

** Workspaces

| =Super+1= … =Super+0=       | go to workspace 1–10        |
| =Shift+Super+1= … =Shift+Super+0= | send this window there |
| =Super+n=                   | a new workspace             |
| =Super+PageUp= / =PageDown= | previous / next workspace   |

#+CLAIM: (every (lambda (row) (equal (rest row) (lookup-key *keymap* (kbd (first row)))))
#+CLAIM:        '(("Super+1" "workspace" 1) ("Super+0" "workspace" 10)
#+CLAIM:          ("Super+Shift+1" "send-to-workspace" 1)
#+CLAIM:          ("Super+Shift+0" "send-to-workspace" 10)
#+CLAIM:          ("Super+n" "new-workspace")
#+CLAIM:          ("Super+Prior" "previous-workspace")
#+CLAIM:          ("Super+Next" "next-workspace")))

Workspaces are one-based, so the key and the number on it agree.

*There is no limit and there is no configured count.* The workspace list is a
stack at the root of the layout tree, and a stack grows: asking for one that is
not there makes it, and every one before it. =Super+x workspace 40= works on a
machine that has three. What a new workspace *contains* is a setting
(~*new-workspace*~) and, more usefully, a policy decision — which is how the
lattice makes every workspace a plane rather than only the ones that existed
when it loaded.

* The lattice

Optional, and off by default. Add to =~/.config/latticewm/init.lisp=:

#+begin_src lisp
(load-extension "lattice")
(lattice:enable)
#+end_src

Each workspace becomes an *infinite plane of cells* addressed by integer
coordinate. Zoom is the choice of how many cells you can see — 1, 2, 4, 6, 8 —
and past that it becomes a drawn map. Motion runs straight through a cell
boundary as though it were not there.

| [[file:doc/coordinate-overlay.png][Cells and coordinates]] | [[file:doc/drawn-map.png][The drawn map at deep zoom]] |

*Infinitely many planes, one behind another.* Every workspace is a plane — not
just the ones open when you enabled it — so the workspace keys are a third axis
through a stack of infinite planes, and =Super+PageUp= / =PageDown= walk it.
Four settings say what that feels like:

| ~*new-workspace-zoom*~   | a new plane's zoom. ~:inherit~ — the one you were on |
| ~*new-workspace-origin*~ | where its view starts. ~:inherit~ — *directly behind* the plane you left |
| ~*new-workspace-cells*~  | cells it is born with. ~nil~ — one, in view |
| ~*workspace-entry*~      | which cell you land on: ~:remembered~ (where you left that plane), ~:aligned~ (the coordinate you are on now), ~:origin~, ~:occupied~ |

The defaults read the phrase literally: same zoom, same window of coordinates,
and you keep your place. Set ~*workspace-entry*~ to ~:aligned~ and
~*new-workspace-origin*~ to ~:inherit~ for pure Z-axis movement — X and Y never
change, only which plane is under you.

*Two ways for zoom to make room*, and it matters once you resize a column.
~*zoom-mode*~ is ~:fit~ by default: the visible cells stretch to fill the screen
exactly. That is free while every column is the same width, and the moment one
is not, panning changes the width of every window on screen — which is what
~:fixed~ is for.

| ~:fit~   | cells stretch to tile the screen exactly. Panning a *non-uniform* plane resizes windows |
| ~:fixed~ | a cell is ~*cell-width*~ by ~*cell-height*~ pixels wherever it sits; the plane scrolls under the screen and the trailing cell is *cropped at the edge*, border redrawn there by the compositor |

Under ~:fixed~ a column you widen is that much wider in pixels, always, and
panning resizes nothing. The crop is river's ~set_content_clip_box~ and it is
the reason the partial cell at the edge reads as a cleanly cut cell rather than
a window sliced in half.

The lattice is the project's own experiment on itself: it is a *separate ASDF
system* that depends on the policy package and nothing else, and a CI gate
asserts on every build that it touches no core file. What that cost is written
up in [[file:FINDINGS.org][FINDINGS.org]] — read that first if you want to know whether the premise
holds.

* Configuring it

#+begin_src sh
latticewm --write-config      # a commented starter ~/.config/latticewm/init.lisp
latticewm --list-options      # every setting, its value, its default, and why
latticewm --list-keys         # every binding
latticewm --list-commands     # every command
#+end_src

Anything you can set in the file you can also set live with =Super+? s=, and
=Shift+Super+c= reloads the file without restarting.

** Your keyboard, mouse and touchpad

On river there is nothing else on the machine that configures input — no
settings daemon, no =xinput=, no compositor config file. The window manager
owns it, so this is where tap-to-click and your keyboard layout live.

#+begin_src lisp
(setf *xkb-layout* "de")             ; what the keys do, for every application
(setf *xkb-options* "ctrl:nocaps")   ; caps lock becomes control

(setf *tap-to-click* t)              ; on by default
(setf *natural-scroll* t)
(setf *repeat-rate* 50)              ; key repeats per second
(setf *repeat-delay* 300)            ; ms held before repeating starts
(setf *accel-speed* 0.3d0)           ; -1 slowest, 0 default, 1 fastest
#+end_src

A laptop has a touchpad *and* a mouse and they want opposite things, so rules
match per device. Later rules win, which makes a rule for =t= a default and a
rule naming a device an override:

#+begin_src lisp
(setf *input-rules*
      '(("Touchpad"   :natural-scroll t :click-method :clickfinger)
        ("TrackPoint" :scroll-method :on-button-down :scroll-button 274)
        ("Logitech"   :accel-profile :flat)))
#+end_src

=(list-inputs)= prints every device with its name, its kind, everything
settable on it and what is currently in force — which is where those names come
from. =(set-input "Touchpad" :natural-scroll t)= tries one without writing it
down. =(keyboard-layout "fr")= switches layout now;
=(next-keyboard-layout)= cycles through the layouts of a multi-layout keymap
and can go on any key you like.

Setting =*xkb-layout*= needs =xkbcli=, which ships with libxkbcommon and is
therefore already installed on any machine running river. Without it the layout
stays as river started it, and one log line says so.

*** Shift maps, which are a different thing with a similar name

River does the xkb work and does not tell us the *shifted* keysym, so the
window manager cannot derive what =Shift+9= produces — it has to be declared
per layout, or its own prompt inserts American punctuation on a German
keyboard.

Setting =*xkb-layout*= adopts the matching table automatically, so in the
ordinary case there is nothing to do. To set one by hand:

#+begin_src lisp
(setf *keyboard-layout* "de")   ; us, uk, de, fr, dvorak, colemak
#+end_src

=(shift-map-names)= lists what is registered, and =register-shift-map= adds one
in three lines.

** Panels, bars and lockers

Anything using =wlr-layer-shell= works: waybar, yambar, mako, swaybg, swaync,
and every screen locker. LatticeWM binds river's layer-shell protocol, lays
windows out inside the area panels have left themselves, and stops sending
keyboard focus while a locker holds it.

That last part is not a nicety. Without it a window manager re-focuses a window
underneath the lock screen on every manage sequence, forever.

** Fonts

It ships with Terminus, and it will use any PSF console font — which means the
few dozen already under =/usr/share/kbd/consolefonts/= on your machine, with
nothing to find, convert or install.

: M-x load-font  /usr/share/kbd/consolefonts/ter-124n.psf.gz

That takes effect immediately. To make it stick, or to use different fonts in
different places:

#+begin_src lisp
(register-font (load-psf "/usr/share/kbd/consolefonts/ter-124n.psf.gz"))
(setf *ui-font* "ter-124n")

;; Or per role — :echo, :minibuffer, :help, :hint, :overlay, :map.
(defmethod font-for ((policy conventional-policy) (role (eql :map)))
  (find-font "ter-112n"))
#+end_src

Widths up to sixteen pixels and any height. =(font-names)= lists what is
registered.

* Extending it

The point of the project. Changing behaviour means writing one =defmethod= in
your own file — no core edit, no rebuild, and it takes effect immediately:

#+begin_src lisp
(defmethod p:gaps ((policy p:conventional-policy) container) 8)
#+end_src

#+begin_src sh
latticewm --extension-surface   # every policy generic you can specialize
latticewm --container-surface   # every generic a new container kind must answer
latticewm --hooks               # every hook, what it is called with, and when
#+end_src

*There are three surfaces, and they answer different questions.* The extension
surface is what the window manager *decides*; the container surface is what it
can *hold*; the hooks are what it *notices*. All three are generated from the
running image, so none of them can drift, and the first two list the methods
you added — which is how you check that your configuration file was loaded.
Gate 2 requires every member of both protocols to be documented.

The container surface exists because its absence had consequences. A grid
written against the source alone answered the six obvious members of the
protocol, loaded without complaint, and broke on copy, on save and on focus
repair; a generic was exported from the core under the comment "the container
protocol" and defined nowhere at all; and the two generics whose failure mode
is silent data loss on restart were declared in the wrong package, so no
document named them. None of that was visible while only one of the two
protocols could describe itself.

The hook surface exists for the third version of the same absence. A hook is
the mechanism for *noticing* — a status bar, a recording indicator, a script
that starts something per screen — and its list lived in a paragraph of
=doc/EXTENDING.org= that named thirteen of the program's seventeen. Fourteen of
those seventeen had never been attached to by anything at all, so nothing had
ever executed what a hook's contract actually is: the arguments its functions
receive and the moment they receive them. Three were wrong. Gate 14 now
requires every declared hook to be attached to and watched firing by the unit
suite, the integration run or the session recorder, whichever tier can produce
the event at all.

Four worked examples are in =examples/=, including a whole alternate layout
model in one method and a new *container kind* — niri's scrolling strip — in
sixty lines. [[file:doc/EXTENDING.org][doc/EXTENDING.org]] walks through them.

* Scripting it
:PROPERTIES:
:CUSTOM_ID: scripting
:END:

There is a control socket — a Unix socket in =$XDG_RUNTIME_DIR=, mode 0600 —
and the binary is its own client:

#+begin_src sh
latticewm --eval '(workspace 3)'
latticewm --eval '(setf *gaps* 8)' --eval '(relayout :force t)'
latticewm --eval '(mapcar #'window-app-id (all-windows))'
#+end_src

Forms run in the window manager's own thread, so they may touch the compositor.
The protocol is *write a form, read a line*, so anything that can open a socket
can drive it.

A SWANK server is available too and is *off by default*: it offers arbitrary
code execution over TCP with no authentication step, which is right for a
development tool and wrong for something that starts before you have done
anything. Turn it on with =--swank-port 4005=, and it binds to loopback.
=tools/wmeval= speaks SWANK's wire protocol directly rather than the socket, so
it is the one thing here that needs that flag.

#+CLAIM: (null (option-default :swank-port))

#+begin_src sh
latticewm --check-config    # load your init.lisp, report problems, exit
#+end_src

Run that *before* logging out. A configuration error otherwise manifests as a
failed session, which is the worst possible moment to find one.

* Development

#+begin_src sh
make          # build, gates, tests
make test     # the unit suite alone
make integration  # a real river, headless, driven for a few seconds
make check    # all of the above -- what CI should run
make run      # river nested inside your current session
make image    # dump ./latticewm
make surface  # regenerate the docs under doc/
#+end_src

Fourteen gates run on every build — and, since there is a [[file:.github/workflows/check.yml][workflow]] now, on every push
as well, which is what "CI" ought to have meant when this line first claimed
it: zero compiler warnings under =safety 3=; every
policy generic and command documented; the lattice touching no core *and no
core file naming the lattice*, within a line budget and above a method floor;
the core running with the lattice absent;
codegen counts *and the protocol versions the program binds* matching the
pinned XML; how many policy generics have ever been answered from *outside*
=src/= staying above a floor; every declared hook run and every run hook declared; every
event handled existing on the interface it is handled for; the image, the
installer and the shipped configuration agreeing about where an extension
lives; no container kind named by class outside its own definition; every
registered option read by something; every claim these documents make
about the program still being true of it; every node property the program
*reads* being written by something; and every declared hook being attached to
by a suite that runs it. The
reasoning behind each is in [[file:PLAN.org::#gates][PLAN.org §gates]].

Gate 14 is the newest, and it is the one the other thirteen could not ask. All
of them read the program or the documents; a hook is neither, because a hook
that nothing has ever attached to is *correct* by every static measure and
untested by construction. Fourteen of seventeen were in that state, and the
three that were checked first were all wrong — ~:startup~ ran before the
compositor connection existed while its docstring said it ran after,
~:output-added~ ran before the monitor had a name or a size, and
~:focus-changed~ was skipped by the commonest focus change there is, a window
closing. So every declared hook must now be attached to and watched by tests/,
by the integration run, or by the session recorder, depending on which of the
three can produce the event at all; the integration run keeps a recorder on
every hook for the whole session and fails on one that neither fired nor is
named as one a headless backend cannot fire.

Gate 13 is gate 11's question asked of the mechanism next
door. A node property is a keyword you type in two places — the write and the
read — and nothing registers it, declares it or checks it, so a key with only
one of the two is invisible: ~prop~ answers ~nil~, the branch behind it never
runs, and nothing ever fails. Two had shipped that way. The lattice's
~clip-rect~ — the cropped trailing cell above, river's best request, a row in
FINDINGS' list of what the extension overrides — read a bound that nothing
wrote, so it returned "clip nothing" for its entire life; and the core's
~render-order~ had a third render tier above the floats that no node could ever
be put into. The gate reads the source with the *reader* rather than grepping it,
so a key is found by symbol identity and a docstring naming one cannot make it
pass. It fails on a key that is read and never written, and *reports* the
converse rather than failing: ~props~ exists precisely so that state can be hung
on an object for a reader the core does not know about, and a gate that demanded
an in-tree consumer for =:pid= would be a check writing the design.

Gate 12 came before it and it is the only one that reads a sentence. Eleven
gates point at the code and none of them can see a paragraph, so when SWANK
was turned off by default — correctly; it was unauthenticated code execution
started before the user had done anything — the first instruction in the
extension guide became false and every check passed. The same had already
happened three times over: this file said the layer-shell and HiDPI paths were
"exercised by the test suite" when nothing referenced them, =*smart-gaps*= was
documented as working while nothing read it, and the plan's own written
ceiling of thirty policy generics went on saying thirty while the count
reached sixty-five. So a document is now declared *current* or *historical*,
every option a current document names must exist, and any sentence can be
pinned to the image with a =#+CLAIM:= line that the build evaluates. It cannot
find a false sentence nobody annotated, and nothing honest can; what it can do
is make one pinnable for the cost of a line, and refuse to let a document
arrive unclassified.

Gate 11 came before it and is a question the other ten could not ask.
=*smart-gaps*= was registered, exported, documented, printed by
=--list-options= and described as working in a generated document — and read
by nothing, from the commit that added it until the one that added the gate.
Gate 2 asks whether every generic is documented; gate 9 asks whether the
installer and the image agree about the option *list*; a unit test asks whether
each option's symbol is the one a configuration file would set, which is the
check that found twenty-four unsettable options. All of them ask the registry
about itself. Being registered, documented, installable and settable are four
promises an option makes, and it makes a fifth: that somebody looks. Gate 11
asks SBCL's own cross-reference data who reads each one, so it is a fact about
the compiled program rather than about its spelling — a docstring mentioning
the name does not satisfy it and a read inside a macro expansion does not
escape it.

Gate 6 used to be the runtime-to-policy *line ratio*, and deleting it is the
one gate change worth mentioning in a README. A ratio of directory line counts
can be satisfied by moving files, and over four commits it was: the number was
walked from 0.82 to 1.17 largely by relocation, two of those commits reproduce
92–100% of the moved lines verbatim and add no dispatch point, and the floor
was set after the position had been arranged. What it stood for — that most of
the system's behaviour should live above the boundary — is right, so gate 6 now
asks it directly and unmovably: *how many policy generics has anybody outside
=src/= ever specialised?* The answer today is 15 of 65, which is a much less
flattering number than 0.99 and is the actual state of the extension surface.

#+CLAIM: (= 65 (length (policy-generics)))

=make integration= is the one that is different in kind. It runs river on a
headless backend, connects to it as the ordinary Wayland client this program
is, opens windows, drives the real commands from outside a protocol sequence,
and asserts on what came back — because every other check in the project
*constructs* state, and the bugs that survive live exactly where constructed
state cannot reach.

It has found five. Four are fixed: pointer bindings enabled through the wrong
interface, so Super+drag did nothing; a window that left the tree — by being
minimized, or by being on the workspace you walked away from — never being
hidden, so the model was right and the screen was wrong; =new-workspace= moving
the cursor to a workspace it never put on the screen; and =op_start_pointer=
sent outside the manage sequence that is the only place it is legal, so
Super+drag did nothing for a second time and a different reason. Not one of them
is visible to a test that builds its own world.

The fifth was a packaging decision rather than a bug to patch, and it is now
made. *=nix build= failed, and should have.* River bumped
=river_window_manager_v1= from 4 to 5 in a patch release, the flake pins a
channel rather than a river, and the vendored protocol was version 4 — so the
flake was building a session entry that could not start, and succeeded, because
nothing in that build had ever connected to the river it pins.

All six river protocols have been re-vendored from 0.4.6 rather than pinning
river back to 0.4.5, because every 4 → 5 change is additive: two new
=capture_sessions= events and five clarifications of prose, nothing removed and
nothing renamed. The version check refuses in both directions, so pinning back
would have left the program unable to start on any river a user installs today.
=src/protocol/PINNED= carries the diff and the argument; [[file:PLAN.org::#log8][PLAN.org §log8]] carries
the decision. =nix build=, =nix-shell=, =make check= and CI are green.

Both of those new events are now handled, which they were not when that
paragraph was written. The window manager knows how many screen capture
sessions are reading each window and each screen: it says so when one starts or
stops, the status line carries a standing =REC= for as long as one lasts, =M-x
captures= says what is being recorded — including a window you minimized and
can no longer see — and =:capture-changed= is the hook for a status bar, a
keyboard light or a script that mutes a microphone. Nothing about placement
changes; being recorded is information, not a policy.

* Status

Working, and used on bare metal.

Verified on real hardware: keybindings including shifted keys, the minibuffer,
spawning, closing, splits, floating, the empty-pane spawn, persistence, and
the lattice — walking cell to cell across an infinite plane, carrying windows
between cells, and zooming out to a grid.

Verified against a *headless river* on every run of =make check= — a hundred
and fifty-odd assertions in twenty-one sections, none of which can pass without
a compositor having agreed: connecting and version negotiation; an output with
the name and size river gave it; the manage and render sequences; the
shared-memory overlay path and its HiDPI arithmetic; the echo area's own
surface and the space it reserves; every key in the keymap becoming a real
binding object, and a key bound at runtime becoming one more; the pointer
bindings; a client window announced, placed, sized and focused; the emitter's
diff re-sending nothing when nothing changed; two windows in disjoint
rectangles; a dozen commands driven from outside a protocol sequence the way a
script drives them; floating, drag-move, drag-resize, fullscreen and minimize;
workspaces, tags, named scratchpads, undo and redo; the saved layout written
and read back with a real window's tags in it; and the control socket
answering one line per form.

=make check= fails when river or a terminal emulator is missing rather than
skipping and exiting 0 — see =REQUIRE_INTEGRATION= in the Makefile. What it
still cannot reach is named out loud in its own output every run: a physically
scaled output, libinput devices, and a layer-shell client, none of which a
headless backend has.

*Input configuration* — device enumeration, key repeat, and compiling and
installing a keyboard layout — has been driven end to end against a real river
running nested, which is where the devices exist. The libinput half of it
(tap-to-click, acceleration, click and scroll method) is written and unit-tested
as a decision, and cannot be exercised without real hardware behind it; the
integration test says =skip= there rather than passing quietly.

*Multi-monitor is written and has been executed against one display.* The
per-output work — deriving the current output from the cursor's rectangle
rather than its window, one overlay per output rather than one globally, and
hotplug releasing what an unplugged monitor held — is done and is unit-tested,
and the two-monitor arrangement itself has not been sat in front of. Nothing is
claimed here that is not either tested or stated as untested;
[[file:PLAN.org::#log7][PLAN.org §log7]] is the current list of which is which.

Other things that are honestly newer than the rest. *HiDPI scaling of what the
window manager draws itself* is exercised against a real =wl_shm=: a 2x canvas
is allocated at twice the device size, reports its logical size unchanged, and
takes text and fills in logical coordinates. What is not exercised is a display
that is actually scaled, because a headless backend is 1x. *Pointer
drag-resize* is exercised as far as the arithmetic goes — a cumulative delta
moves the window exactly that far and repeating it does not move it again — and
the bindings river made are counted, but no physical pointer is ever pressed.
*The layer-shell path that panels and screen lockers use* is exercised only as
far as the global binding and an empty reservation: there is no headless
layer-shell client to open a panel with, and the exclusive-zone arithmetic has
been read and not run.

That paragraph used to say all three were exercised by the test suite. They
were not: there was no test reference to =surface.lisp=, =layer.lisp=,
=pointer.lisp= or =outputs.lisp= of any kind.
