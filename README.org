** Status: built, and it runs

#+begin_quote
An extensible window manager for the river Wayland compositor, in Common Lisp,
whose layout model is a replaceable policy layer rather than the program itself.
#+end_quote

[[file:doc/echo-area.png]]

*Quickstart.* Needs river 0.4.x and SBCL. *Any Linux* — nix is one of the
supported ways, not the required one. Full details in [[file:INSTALL.org][INSTALL.org]].

: git clone … && cd LatticeWM
: ./bootstrap.sh      # fetches the Lisp dependencies into ./.deps/  (or: nix-shell)
: make                # build, six gates, 566 tests
: make run            # river nested inside the session you are already in
: ./install.sh        # and it appears at the login screen like any desktop

Or, in a real session: =river -c latticewm=. =latticewm --write-config= drops a
commented starter configuration in =~/.config/latticewm/=.

*The first thing to press is =Super+/=*, which draws the whole keymap with what
each binding does. =Super+x= is M-x — every command, including the ones that
take arguments, which it asks for. =Super+;= evaluates a Lisp form in the
running window manager. =Super+?= asks about anything: a key, a command, a
configuration value. =Super+Return= is a terminal.

*What it does.* Recursive splits like Emacs and hyprland, tabs, workspaces,
per-window floating, minimize that leaves the tiling tree, multi-monitor, an
echo area with a real minibuffer in it, and persistence across a restart.
Then, opt-in:

: (asdf:load-system "lattice")
: (lattice:enable)

and each workspace becomes an *infinite plane of cells*, addressed by integer
coordinate, with zoom as the choice of how many cells you can see — 1, 2, 4, 6,
8 — and a drawn map once they get too small to render. Motion runs straight
through the cell boundary as though it were not there.

* What this must do
:PROPERTIES:
:CUSTOM_ID: requirements

Distinct from the constraints above: these are the *properties the finished thing must

** The governing requirement

#+begin_quote
"You will notice that my model is Emacs, where you can do anything."
#+end_quote

Everything below is downstream of this. Concretely it means:

- *Any behaviour can be changed from inside, while it is running.* Not "there is a
  config file with the options we anticipated" — the ability to redefine a function
  and have the running window manager start using it. This is the requirement that
  chose the language.
- *No designated extension points.* The reason Neovim with Lua and Helix with Steel
  are still not Emacs is that they expose a curated API surface and keep the
  interesting internals unreachable. Extensibility must not be limited to whatever
  someone thought to expose.
- *Where a fork is situational rather than principled, both options ship and
  configuration picks the default.* Recorded as [[#p1][P1]] below.

** Functional requirements

- *Moving things must be easy and intuitive* — both with and without shifting the
  surrounding row.
- *Swapping must be easy.* Two things trade places, in one gesture.
- *Pulling must be easy* — bring a window from elsewhere into the current cell as a
  split, without first navigating to it.
- *Resizing must be simple*, including the degenerate case: "split with nothing,"
  which is how you give a window less than a full cell.
- *Holes are allowed and are not automatically filled.* Compaction happens because
  the user asked for it.
- *Things can be glued together* so they travel as a unit.
- *You get to pick which of several near-equivalent behaviours is the default* — for
  spawn placement, for clear-vs-close, for shift scope.
- *Windows can be picked out to float*, individually, rather than floating being a
  property the window manager decides for you.
- *Minimized windows leave the tiling tree entirely* and the remaining windows retile
  without them. Minimize is not "hide it somewhere," it is "take it out of the layout."

* The decision: what we are building
:PROPERTIES:
:CUSTOM_ID: decision
:END:

*An extensible window manager for the river Wayland compositor, written in Common Lisp,
whose layout model is a replaceable policy layer rather than the program itself.*

This is [[#requirements][the governing requirement]] taken literally: a substrate you change from inside
while it runs. The layout model is the first thing built on that substrate — not the
thing the substrate exists to serve.

** Two layers

*Layer 0 — the core.* Protocol client, manage/render sequencing, window and node
bookkeeping, keybinding plumbing, split trees, focus, persistence, the drawing surface.
Deliberately *over-decomposed*: every decision a user might plausibly want to change is
a named, documented generic function rather than an inlined branch. See
[[#extensibility][The extensibility surface]] — that decomposition *is* the product, and it has to be
budgeted for rather than hoped for.

*Layer 1 — the layout policies.* Two of them, in this order:

1. *Conventional* — arbitrary Emacs/hyprland-style splits, per-window floating,
   minimized windows dropping out of the tiling tree. Ships first. It is not novel and
   is not trying to be; it is the smallest thing that is a usable daily driver, and
   therefore the smallest thing that proves the core works.
2. *The lattice* — the design below. Built on top, from outside, without editing
   layer 0. This is [[#d21][D21]], and the reasoning for the ordering is there.

** The lattice, which is still the point

A spatial model that does not currently exist anywhere:

- Each workspace is an *infinite 2D lattice of cells* addressed by integer
  coordinates.
- Each cell contains an *Emacs/i3-style split tree* — leaves are windows (or
  deliberately empty), internal nodes are horizontal or vertical splits, nestable
  arbitrarily.
- The *viewport* is an N×M rectangle over the lattice. *Zoom is the choice of N×M*:
  1×1 shows one cell fullscreen, 2×1 shows two, 2×2 shows four, 3×2 shows six.
- *Panning* moves the viewport over the lattice.
- Windows and whole cells can be *moved between cells* easily.
- There are *many lattices* — infinite workspaces, each its own plane.

*** Why this is the idea

Zoom is normally a *mode* you enter and leave (GNOME overview, niri's Overview).
Here zoom is a *continuous layout control*: one knob replaces both workspace-switching
and tiling-layout-selection. That collapse of two concepts into one is the novel part.

Every half of this exists somewhere. The combination does not:

| Existing thing | What it has | What it lacks |
|----------------+-------------+---------------|
| niri / PaperWM | Infinite strip, overview zoom, drag between workspaces | Only 1D; vertical axis is discrete workspaces; overview is a mode |
| i3 / sway | Exactly this cell split-tree model | One root per workspace, no plane, no zoom |
| Notion / Ion3 | Static frames split like Emacs, tabs in frames | X11, no plane, no zoom |
| Material Shell (GNOME) | An explicit 2D grid (workspaces=rows, windows=columns) | Fixed axis semantics, not pannable or infinite, GNOME-bound |
| Eagle Mode, Pipeworld | True zooming UIs | Continuous planes, not daily-driver WMs |

*** Why it survives the ZUI curse

Historically, zooming user interfaces die because users get lost — Pad++, Raskin's
Archy, Eagle Mode. That failure mode belongs to *continuous* planes.

This design uses a *lattice with integer coordinates*. Cells have addresses. That
buys: jump-to-(3,−2), jump-to-named-cell, relative movement by one cell, and a
minimap that is a finite grid rather than a fog. Discrete geometry is dramatically
more memorable than continuous space.

*This is still the single biggest design risk.* Two dimensions is more than twice as
hard to hold in your head as niri's one. Design against it from day one: minimap,
named cells, and the coordinate overlay (D5).

*** Why the lattice is built second

Because it is the *test* of the thesis rather than an application of it.

If the lattice can be added as an extension — new methods, new state on ~props~, a new
renderer, no core surgery — then the extensibility claim is true, there is proof of it,
and the thing actually worth having got built. *If it cannot, the claim was false* — and
that is discovered in week three on a small codebase with a working conventional window
manager already in hand, rather than in month six on a large one.

This document previously asserted extensibility and never tested it. The sequencing
tests it against the hardest case available.

*The failure mode, named so it can be watched for:* the conventional layer turns out to
be pleasant enough, and the lattice never gets built. In that case a month was spent
rebuilding hyprland, worse. The only defence is treating the lattice extension as *the
deliverable* rather than as a stretch goal — which is why it is week 3 in [[#plan][the plan]] and
not "later."

*The counter-argument that was weighed and rejected:* build the conventional layer and
stop. That fails on a simple asymmetry — a novel design can be worse than hyprland and
still worth running, because it does something hyprland cannot; a conventional design
that is worse is merely worse. Without the lattice there is no reason for this to exist,
and =hyprland= (already configured on this machine) is the correct answer instead.

* Feasibility verdict: river can do all of it

Verified against the actual protocol XML (=river-window-management-v1=, version 5,
and =river-xkb-bindings-v1=, version 3), not summaries.

*Every element of the spec maps to an explicit protocol feature. There are no gaps.*

| Requirement | Protocol mechanism |
|-------------+--------------------|
| Infinite lattice, arbitrary coordinates | ~river_node_v1.set_position(x, y)~ — "The x and y coordinates may be positive or negative." |
| Z-order between overlapping cells | ~place_top~, ~place_bottom~, ~place_above(other)~, ~place_below(other)~ |
| Park distant cells cheaply | ~river_window_v1.hide~ / ~show~ |
| Arbitrary cell sizes | ~propose_dimensions(width, height)~, ~set_dimension_bounds(max_w, max_h)~ |
| Clean viewport edges | ~set_clip_box~ / ~set_content_clip_box~ (see below — this is the good one) |
| Cell borders | ~set_borders(edges, width, r, g, b, a)~ |
| The lattice, split trees, workspaces | *Nothing in the protocol.* Entirely our data structures. |
| Keybindings | ~river_xkb_bindings_v1.get_xkb_binding(seat, id, keysym, modifiers)~ → ~enable~ |
| Emacs-style key sequences | ~ensure_next_key_eaten~ / ~ate_unbound_key~ |
| Hold-Super-to-zoom-out | ~modifiers_watch~ / ~modifiers_update~ |
| Multi-monitor | ~river_output_v1.position(x,y)~ + ~dimensions(w,h)~ in logical space |
| Minimap / overview UI | ~get_shell_surface(id, surface)~; shell surfaces get their own ~get_node~ |
| Drag windows between cells, drag-to-pan | ~op_start_pointer~ → ~op_delta(dx,dy)~ (cumulative) → ~op_release~ → ~op_end~ |
| Driving our own animation | ~manage_dirty~ |
| Restoring layout across WM restart | ~river_window_v1.identifier~ event |
| Dialogs and transients | ~river_window_v1.parent~ — "might be a dialog, file picker, or similar" |
| Knowing a window will refuse to shrink | ~dimensions_hint~ (min/max w/h, advisory both ways) |
| Declaring what we honour | ~set_capabilities~ (window_menu=1, maximize=2, fullscreen=4, minimize=8) |
| Spawn-to-cell by launched process | ~unreliable_pid~ (since v2) — match the PID we launched, not app_id guessing |

The decisive design fact, from river's changelog:

#+begin_quote
"The compositor will no longer have any knowledge of window management concepts such
as tags, workspaces, output focus, etc. The window manager will have full control
over window positioning, sizing, keyboard focus, keybindings, pointer move/resize
operations, and more."
#+end_quote

There is *no existing spatial model to fight*. That is what makes an unusual model
feasible at all.

** The best find: content clipping

~set_content_clip_box~ clips window content /excluding/ borders and decorations, and:

#+begin_quote
"Borders drawn by the compositor (see set_borders) are placed around the intersection
of the window content (as defined by the dimensions event) and the content clip box
when content clipping is enabled."
#+end_quote

So a cell half-scrolled off the viewport edge is clipped *and its border redraws at
the clip edge*. It reads as a cleanly cropped cell rather than a window sliced in
half. Proper viewport boundaries, free, from the compositor. Budget zero time for
this; it was expected to cost a week of bad approximation.

Note there are two: ~set_clip_box~ clips the window *including* borders and
decorations; ~set_content_clip_box~ excludes them. Both may be enabled at once. Both
are ignored while a window is fullscreen.

** Popups do not exist as far as we are concerned

The string ~popup~ appears *zero times* in the 1,911 lines of
=river-window-management-v1.xml=. xdg_popups — menus, dropdowns, tooltips — are
handled entirely by the compositor and are invisible to the window manager. This
deletes an entire category from the original open-questions list.

*One residual check, cheap, do it in Week 1:* does a menu opened in a cell that
straddles the viewport edge get sliced by our ~set_clip_box~? The spec says clipping
applies to the window "including borders and decoration surfaces"; whether river's
scene graph counts an xdg_popup child surface as part of that node is not stated.

** Size and shape of the surface we must implement

Measured directly from the XML on 2026-07-29. This turned out to matter a great deal
for the language decision, because it is much smaller than assumed.

| | =river-window-management-v1= | =river-xkb-bindings-v1= |
|-+-+-|
| Version | 5 | 3 |
| Lines of XML | 1,911 | 314 |
| Interfaces | 8 | 3 |
| Requests | 57 | 8 |
| Events | 44 | 4 |
| Enums | 10 | 2 |

*Complete list of argument types used across both protocols:*

: int   uint   string   object   new_id   destructor

There is *no ~fd~, no ~array~, and no ~fixed~ anywhere in either river protocol.* That
is the simplest possible Wayland argument profile — no fixed-point conversion, no
array marshalling, and no SCM_RIGHTS except where we ourselves choose to use ~wl_shm~
for the minimap surface.

Three events carry ~new_id~ (server-created objects): ~window~, ~output~, ~seat~ on
=river_window_manager_v1=. Every window we ever manage arrives this way, so
server-side ~new_id~ handling is on the critical path and is the first thing to verify
in any binding library.

** River does the xkb work; we do not

=river_seat_v1= has *no keyboard binding mechanism*. Line 1505 of the XML says:

#+begin_quote
"For keyboard bindings, see the river-xkb-bindings-v1 protocol."
#+end_quote

That protocol is 314 lines and takes only ~uint~/~object~/~new_id~. We declare a
binding as a keysym plus a modifier bitfield and receive ~pressed~ / ~released~ /
~stop_repeat~ events.

*Consequence: no libxkbcommon, no keymap file descriptor, no xkb state machine, no
~wl_keyboard~ plumbing at all.* This is a substantial chunk of work that earlier
estimates assumed and that simply does not exist. It is language-independent good
news, but it disproportionately helps a language with a thinner FFI ecosystem.

** The manage/render state machine

This is the core of the protocol and the source of its worst bug class.

Two disjoint categories of state:

- *Window management state* — influences compositor↔window communication. Window
  dimensions, fullscreen, keyboard focus, keyboard bindings.
  *May only be modified during a manage sequence.*
- *Rendering state* — affects only rendered output. Position, render order, hide/show,
  borders, clip boxes.
  *May be modified during a manage or a render sequence*, and is applied at the next
  ~render_finish~.

Violating this is a hard protocol error: ~river_window_manager_v1.error.sequence_order~.

The loop, from the spec:

#+begin_example
1. Server sends all state changes since last manage sequence, then manage_start.
2. Client modifies window-management state and/or rendering state, then manage_finish.
3. Server sends new state to windows and waits for responses.
4. Server sends new window dimensions to client, then render_start.
5. Client modifies rendering state, then render_finish.
6. If dimensions change, loop to 4.
   If manage-requiring state changes, or client sends manage_dirty, loop to 1.
#+end_example

A manage sequence is *always* followed by at least one render sequence. Multiple
render sequences may occur consecutively without an intervening manage sequence
(e.g. a window changes its own dimensions).

*** Which requests belong to which category

Window-management state (manage sequence only):
- ~river_window_v1~: ~close~, ~propose_dimensions~, ~use_csd~, ~use_ssd~, ~set_tiled~,
  ~inform_resize_start~/~inform_resize_end~, ~set_capabilities~,
  ~inform_maximized~/~inform_unmaximized~, ~inform_fullscreen~/~inform_not_fullscreen~,
  ~fullscreen~, ~exit_fullscreen~, ~set_dimension_bounds~
- ~river_seat_v1~: ~focus_window~, ~focus_shell_surface~, ~clear_focus~,
  ~op_start_pointer~, ~op_end~, ~pointer_warp~
- ~river_pointer_binding_v1~: ~enable~, ~disable~
- ~river_xkb_binding_v1~: ~set_layout_override~, ~enable~, ~disable~
- ~river_xkb_bindings_seat_v1~: ~ensure_next_key_eaten~,
  ~cancel_ensure_next_key_eaten~, ~modifiers_watch~

Rendering state:
- ~river_node_v1~: ~set_position~, ~place_top~, ~place_bottom~, ~place_above~, ~place_below~
- ~river_window_v1~: ~hide~, ~show~, ~set_borders~, ~set_clip_box~, ~set_content_clip_box~
- ~river_decoration_v1~: ~set_offset~, ~sync_next_commit~
- ~river_shell_surface_v1~: ~sync_next_commit~
- ~river_output_v1~: ~set_presentation_mode~

*** OPEN QUESTION: a contradiction in the spec

The ~river_window_manager_v1~ interface description says rendering state "may be
modified by the window manager during a manage sequence or a render sequence."

But individual rendering-state requests (~set_position~, ~hide~, ~show~, ~set_borders~,
~set_clip_box~) each say "may only be made as part of a render sequence, see the
river_window_manager_v1 description" — pointing back at the description that
contradicts them.

The interface description is more detailed and explicitly addresses the question, so
it is probably authoritative and the per-request wording is shorthand. *Verify against
river's implementation before relying on setting positions during a manage sequence.*
This matters: doing position updates in the manage sequence would halve the round
trips for animation.

*Note: this is why canoe remains valuable even after the language reversal.* The spec
is ambiguous here; canoe is evidence of what river actually accepts. Read it as a
specification, not as code to copy.

** Gotchas that the online summaries hid

1. *Windows do not take the dimensions you propose.* ~propose_dimensions~ is
   advisory; the spec explicitly calls out terminal emulators that quantize to cell
   size. The real size arrives in a ~dimensions~ event, possibly several render
   sequences later. ~dimensions_hint~ tells us the client's min/max in advance, so we
   often know before proposing.
   *Design decision required:* when a window is smaller than its cell, do we center
   it, top-left it, or letterbox it? Partly answered by [[#d17][D17]] — the empty pane gives an
   explicit place to put slack — but the default gravity is still open.

2. *Render order is undefined by default.* "The initial position of a node in the
   render list is undefined, the window manager client must use the place_above or
   place_below request to guarantee a specific rendering order." Every node must be
   explicitly ordered. Matters most during zoom transitions when cells overlap.

3. *There is no frame or timer event.* To animate a zoom, drive it from our own event
   loop using ~manage_dirty~, which forces a manage sequence, which is always
   followed by a render sequence. That is a full manage round trip per animation
   frame — heavier than a pure render loop. *Prototype smooth zoom early; do not
   assume it.* (See the open question above — if rendering state really is legal in
   manage sequences, this gets cheaper.)

4. *A slow WM means laggy input, and can be fatal.* There is an ~unresponsive~
   protocol error, and the spec says the compositor should wait for the manage
   sequence to complete before processing further input events. Respond promptly.
   /This is the one place where a GC pause could theoretically matter; see
   [[#language][Language]] for why it does not in practice./

5. *New windows are not displayed* until the WM makes a ~propose_dimensions~ or
   ~fullscreen~ request in a manage sequence, the server replies with a ~dimensions~
   event, and that render sequence finishes. Newly created windows are considered
   *shown* unless explicitly hidden — so offscreen cells must be hidden deliberately.

6. *THE BIG ONE: there is no scaling primitive. Anywhere.* Re-verified against the
   full XML. The protocol has *no* request or event for scale, transform, matrix,
   buffer_scale, or fractional scaling. ~river_node_v1~ has exactly six requests:
   ~destroy~, ~set_position~, ~place_top~, ~place_bottom~, ~place_above~,
   ~place_below~. ~set_clip_box~ and ~set_content_clip_box~ *crop* — they restrict the
   visible region and do not scale what is inside it.

   *Consequence: "zoom out" cannot mean "draw the same windows smaller." It can only
   mean "give every window smaller dimensions."* Every zoom change is a
   ~propose_dimensions~ to every visible window, i.e. a genuine re-layout: terminals
   rewrap, Emacs reflows, browsers reflow.

   Two things follow immediately, and both are forced, not chosen:
   - *Animated zoom is off the table.* It would resize every window every frame.
     (Animated /panning/ is still cheap — that is ~set_position~ only, no resize.)
   - *Deep zoom cannot use real windows.* At 4×3 on a 1080p display a cell is
     480×360; a browser at that size is useless, and reflowing it merely to check
     where things are is unacceptable. Past some threshold, zoom must be drawn by us
     rather than by the applications. Still awaiting a ruling — see [[#open][open questions]].

7. *~pointer_position~ alone never starts a manage sequence* ("This state is special
   in that a change in pointer position alone must not cause the compositor to start
   a manage sequence"). Pan-follows-mouse cannot be driven from pointer position
   alone; use an interactive op or ~manage_dirty~.

8. *Fullscreen suspends the lattice for free.* ~fullscreen(output)~ makes the window
   the only thing rendered on that output; clip boxes are ignored and borders are not
   drawn while fullscreen. Honouring a fullscreen request therefore costs nothing to
   enter and nothing to leave — no relayout either way.

9. *~minimize_requested~ is entirely ours to define.* The spec: the WM is "free to
   ignore this request, hide the window, or do whatever else it chooses."

*declare* these; CSD titlebar buttons appear based on what we declare.

Errors: ~river_window_manager_v1~: sequence_order=0, role=1, unresponsive=2.
~river_window_v1~: node_exists=0, invalid_dimensions=1, invalid_border=2,
invalid_clip_box=3.

Decoration render order, bottom to top:
1. decorations from ~get_decoration_below~
2. window content
3. borders from ~set_borders~
4. decorations from ~get_decoration_above~

** ~identifier~ — the key to persistence

~river_window_v1.identifier~ (since v4): up to 32 printable ASCII bytes, non-empty,
uniquely identifies the window, *never reused*, matches
~ext_foreign_toplevel_handle_v1.identifier~ if that protocol is implemented. Sent once
at window creation.

This is what lets the lattice survive a WM restart or hot-swap: serialize
identifier → (workspace, cell coordinate, position in split tree) on shutdown, restore
on startup.

*Note the limit:* identifiers are not reused, so they survive a WM hot-swap but *not*
a reboot. Spawn rules are what restore layout across reboots.

** Chorded keybindings are a first-class feature

~ensure_next_key_eaten~ exists precisely for this. From the spec's own rationale:

#+begin_quote
"the window manager may wish to implement 'chorded' keybindings where triggering a
binding activates a 'submap' with a different set of keybindings. Without a way to eat
the next key press event, there is no good way for the window manager to know that it
should error out and exit the submap when a key not bound in the submap is pressed."
#+end_quote

Emacs-style ~C-x C-f~ sequences, supported by the protocol. Given how many commands
this WM needs — and [[#p1][P1]] guarantees there will be many — this is likely to be central
to the keymap design. ~cancel_ensure_next_key_eaten~ handles submap timeouts.

* Language: Common Lisp
:PROPERTIES:
:CUSTOM_ID: language
:END:

*Decision: SBCL, using =wayflan= for the Wayland client layer. No Rust, no embedded
scripting layer, no FFI boundary — the implementation language and the extension
language are the same language.*

*This reverses the Rust decision of 2026-07-24.* That decision was not unreasonable
given what was known at the time; it was made without knowing the size of the protocol
or the state of Common Lisp Wayland tooling, and before Shaul's governing requirement
("my model is Emacs, where you can do anything") had been stated explicitly and
followed to its consequences.

** Why

*** 1. Extensibility is the project's thesis, and it is not close

The requirement is not "a config file with good options." It is that any behaviour can
be redefined from inside, while the system is running. Common Lisp delivers this
natively:

- *Live redefinition via SLIME/SWANK.* Connect to the running window manager,
  redefine a function, it takes effect. No rebuild, no restart, no lost session.
- *CLOS generic functions.* Adding a ~defmethod~ to an existing generic function from
  outside the file that defined it is Emacs's ~advice~ mechanism, except structural
  and first-class rather than a hack. This is the concrete mechanism for "no
  designated extension points."
- *Macros.* You can extend the language, not merely call it.

The alternative — a compiled core with an embedded scripting layer — is extensible
exactly as far as the script layer reaches and no further. That is precisely why
Neovim with Lua and Helix with Steel are not Emacs, despite having the same two-layer
shape. *The shape is not what makes Emacs extensible; the absence of a privileged
unreachable layer is.*

*** 2. The protocol is small enough that binding maturity stops being decisive

The original decision's strongest argument was ~wayland-rs='s maturity (4.7M
downloads/month, 2,939 dependent crates) against an unknown Common Lisp situation.
Having measured the actual surface — 11 interfaces, 68 requests, 49 events, 11 enums,
and *six argument types with no fd/array/fixed anywhere* — the gap matters far less than
assumed. This is not a protocol that stresses a binding library.

/(Recount, 2026-07-29: this line previously said 65 requests and 48 events. Counted from
the XML and cross-checked against generated code, it is 68 and 49 — 57+11 requests and
44+5 events across the two protocols. Probably some of the eight ~destroy~ requests were
skipped. See [[file:SPIKE-WEEK0.org::#corr-counts][spike §corr-counts]].)/

*** 3. The work estimate favours it

Rough, order-of-magnitude, for the same feature set:

| | all-CL | Rust + embedded Lisp |
|-+-+-|
| Protocol bindings | ~0.5d (wayflan scanner) | ~0.5d (wayland-scanner) |
| Connection, registry, globals | 1d | 0.5d (canoe as reference) |
| manage/render sequencing | 2–3d | 2d (canoe as reference) |
| Lattice + verbs (tree surgery) | 3–4d | 5–7d |
| *Core/script boundary + FFI + embed* | *0d* | *2–3d* |
| *Command registry / script plumbing* | *0d* | *2d* |
| Minimap (shm + cairo) | 2–3d | 2d |
| Keybindings | 0.5d | 0.5d |
| Persistence | 1d | 1d |
| Library contingency | +2–3d | — |
| *Total* | *~12–16d* | *~15–19d* |

The compiled path spends four to five days building a boundary and a script layer
whose entire purpose is to reconstruct what one language provides for free.

*** 4. Tree surgery is the dominant operation, and it is Lisp's best case

Every verb in this design — move, swap, pull, split, close-and-collapse, bond —
detaches a subtree and reattaches it elsewhere. Reparenting is a borrow-checked
language's worst ergonomic case (~Box~, ~mem::replace~, ~Option::take~ gymnastics,
with the checker fighting hardest at exactly the reattachment step). In Lisp it is
four lines.

*** 5. Errors do not kill the session

An unhandled error in a compiled binary unwinds and the process dies. In Common Lisp
it signals a condition: the process is still running, the socket is still open, the
lattice is intact, and you can fix the function and continue. This is why StumpWM
users run the same image for months.

*Hard requirement that follows:* a daemon with no controlling terminal *must* install
a top-level handler / ~*debugger-hook*~, or an unhandled condition will hang waiting
on a ~stdin~ that isn't there. StumpWM does exactly this. This is not free and must be
in the Week 1 skeleton.

** What Rust would still have been better at

Recorded honestly so the decision can be overturned knowingly rather than drifted away
from.

1. *Fewer authored bugs.* The compiler catches wrong arity, nil-where-a-number-goes,
   and typos in cold branches before they ship. Common Lisp finds them when that
   branch is first executed. Given that Claude writes this code and Shaul does not
   read every line, *this is the single strongest remaining argument against the
   reversal.* The mitigation is real but partial: conditions make such errors
   recoverable and live-fixable rather than fatal.
2. *canoe as a same-language reference.* Worth roughly two days. Mitigated by reading
   it as a specification — the sequencing logic translates even though the code does
   not.
3. *Raw speed and memory.* An SBCL image is ~40–60 MB RSS against ~10 MB for a
   compiled binary, and SBCL lands within roughly 1–3× on general code. Both are
   irrelevant here for a structural reason: *we are not in the render path.* River
   draws; we send coordinates. Per update sequence we recompute placements for ≲100
   windows and emit a few hundred protocol messages — microseconds either way. GC
   pauses on a few-megabyte heap are sub-millisecond to low-millisecond, and the worst
   case is a window move landing a frame late, not a dropped frame. This was already
   the doc's position, from Isaac Freund's design notes: the protocol avoids a
   per-frame compositor↔WM roundtrip, so "having a garbage collector in the window
   manager does not really matter."
4. *Employability.* Rust reads better on a CV. Irrelevant to this project's goal.

*Known gap, and the fix:*

~%find-proxy!~ (=client.lisp=:144) signals ~wl-message-error~ when a message arrives
for an unknown object id. libwayland's zombie-proxy machinery exists to swallow events
that were in flight when the client destroyed something — wayflan has a
~wl-destroyed-proxy~ marker class but no guard. In a window manager, windows are
created and destroyed constantly, so this *will* be hit.

*It is a five-line fix in our code, not a fork.* ~%call-with-message~ (=wire.lisp=:487)
reads the header, then fully drains the message body into a separate foreign buffer
*before* invoking the handler. So when the handler throws, the socket stream is
already positioned at the next message. A ~handler-case~ on ~wl-message-error~ in the
dispatch loop is a complete, desync-free fix.

*Honest risk assessment:*

- *Bus factor 1.* The original author disappeared in November 2025; the project was
  adopted by the Guix packager, who implemented the missing ~new_id~ event handling,
  fixed bugs, and packages it upstream (=sbcl-wayflan= 0.1.0).
- *But it is ~1,750 lines you can read in an afternoon and own if you must.* Forking
  ~wayland-rs~ is not something a person does; forking wayflan is a Tuesday. "Small
  enough to own" is a genuinely different risk category from "small enough to be
  scary."
- *It is not C-free.* No libwayland, but =wire.lisp= is heavy CFFI straight to libc
  syscalls (~foreign-alloc~, ~msghdr~, ~sendmsg~, ~cmsghdr~).
- *Single-threaded client only.* SWANK runs in another SBCL thread and marshals into
  the WM thread — the StumpWM pattern.
- *No non-trivial window manager has ever used it.* Unknown unknowns exist.

** Day-one architecture: dynamic sequence discipline

The protocol's most dangerous rule is the manage/render split, and it is easy to get
wrong because some requests are legal in both contexts. The Rust plan encoded this in
the type system. The Common Lisp equivalent is *generated* and therefore covers all 68
requests for about twenty lines:

#+begin_src lisp
(defvar *sequence* nil)  ; NIL | :manage | :render

(define-condition sequence-violation (error)
  ((request :initarg :request) (actual :initarg :actual)))

(defun check-sequence (required request)
  "Window-management state is manage-only. Rendering state is legal in both."
  (unless (or (eq *sequence* required)
              (and (eq required :render) (eq *sequence* :manage)))
    (cerror "Send it anyway." 'sequence-violation
            :request request :actual *sequence*)))

;; Annotate manage-only requests in the scanner; every generated
;; wrapper then calls CHECK-SEQUENCE before marshalling anything.

(defmacro with-manage-sequence ((wm) &body body)
  `(let ((*sequence* :manage))
     (manage-start ,wm) (unwind-protect (progn ,@body) (manage-finish ,wm))))

(defmacro with-render-sequence ((wm) &body body)
  `(let ((*sequence* :render))
     (render-start ,wm) (unwind-protect (progn ,@body) (render-finish ,wm))))
#+end_src

This catches the violation *at the point of use, before the bytes reach the wire*, and
offers a restart. That is arguably better than a compile-time check given that the
architecture already makes WM restarts cheap — and unlike the type-state design, it
does not have to be hand-written per request.

*The ~:render~-legal-inside-~:manage~ clause depends on the spec contradiction above.*
If it resolves against us, delete that clause. One line.

*Mechanical constraint confirmed by the spike: this has to be a wrapper layer.* wayflan
generates requests as *plain functions* named ~interface.request~ — e.g.
~river-window-v1.set-clip-box~ — in one flat package, not as generic functions. So the
discipline cannot be bolted on with ~defmethod~, and redefining a generated function in
place would work while also being a maintenance crime, because the next scanner run
silently reverts it. Two consequences:

1. Every generated request gets a hand-or-macro-generated wrapper. The twenty-line plan
   above is still viable exactly as written; it just lives in wrappers rather than in
   advice.
2. *Policy code must never call a generated request directly.* This document already
   organises that way ([[#runtime-vs-policy][Runtime versus policy]]) for conceptual
   reasons — it now has a mechanical one.

The flat ~RIVER~ package exports 91 symbols, 68 of them callable requests. The wrapper
layer should export a deliberately smaller vocabulary and leave ~RIVER~ as plumbing that
Layer 1 never sees.

** Code organisation: runtime versus policy
:PROPERTIES:
:CUSTOM_ID: runtime-vs-policy
:END:

There is no enforced boundary — that is the point. But the *conceptual* split is still
worth keeping, because it identifies what stabilises early and what you live in:

- *Runtime* (stabilises by Week 2, then rarely touched): wire protocol, generated
  bindings, sequence discipline, event loop, the placement emitter, ~wl_shm~ drawing.
- *Policy* (where you live): the lattice, every verb, focus, keymaps, zoom, workspaces,
  compaction, bonds, persistence.

Keep the manage/render distinction *inside* the runtime. It is a protocol artifact and
should never appear in policy code: policy says where things go, the runtime decides
which sequence each call belongs in.

** Why not the others

- *Rust* — the previous decision. See [[#language][above]] for the full reversal argument and the
  honest list of what it would still have done better.
- *Rust core + embedded Lisp (Steel / ECL / Janet / Rhai)* — *specifically rejected.*
  It is defined by having a boundary, and the boundary is exactly the property that
  makes Neovim and Helix not-Emacs. Steel additionally fails the maturity bar that was
  used to doubt wayflan (one maintainer, still an unmerged experiment in Helix), and
  ECL means accepting a materially slower Lisp *and* a hand-written C FFI — the worst
  of both.
- *Zig* — the "native" choice (river is Zig; =zig-wayland= is by river's own author).
  Rejected: =zig-wayland= uses =0.major.patch= versioning with *API-breaking changes
  expected until Zig 1.0*, requires zig 0.16, and "does not currently do extensive
  verification of Wayland protocol XML or provide good error messages." Decisively:
  Zig's training data is thin *and stale* — the language changes faster than models
  learn it. Worst possible fit for LLM-written code.
- *Python* — =pywayland= describes itself as "highly experimental" with "usage likely
  to change between releases." Not acceptable under a daily-driver WM.
- *C* — reference =wayland-scanner=, entirely viable, but manual memory, listener
  structs, and zero help with either the sequence state machine or extensibility.
- *Other Lisps* — =cl-wayland= (libwayland bindings, also Guix-packaged, also
  maintained) is the fallback if wayflan fails. Scheme options exist (=wayland-scm=
  for R7RS, =guile-wayland= which is "raw, WIP" and crashes) but give up CLOS and
  SLIME maturity for nothing in return.

** The tiers

| Tier | What it takes | Restart? | Available to a non-programmer? |
|------+---------------+----------+--------------------------------|
| *0 — a value* | edit a ~defparameter~ | no | *yes* |
| *1 — a behaviour* | ~defmethod~ on an existing generic | no | with an example to copy |
| *2 — behaviour + state* | ~defmethod~ + data on ~props~ ([[#d20][D20]]) | no | no |
| *3 — new machinery* | real code written against the core | no | no |
| *4 — structural* | edit the core; a fork of the design | maybe | no |

** What the original argument got wrong

*"CLOS means there is no hook set to guess wrong."* Only true if the code is written as
fine-grained generics. A 200-line ~relayout~ that inlines every decision has nothing to
specialize; the only available move is to redefine all 200 lines, which requires
understanding all 200 lines. *Extensibility is a property of the decomposition, not of
the language.* Lisp raises the ceiling and does nothing whatsoever for the floor.

*And the schedule fights the decomposition.* A working monolith is faster to write than
a factored surface with documented contracts, and an AI writing to a three-week deadline
optimises for working. Left alone, the default outcome is a Common Lisp program about as
unextendable as the Rust one would have been, minus the type checker. *This conflict is
real and the plan must pay for it in features.*

*Tier 1 is not "flipping a switch."* Writing a ~defmethod~ requires knowing the generic's
argument list, the slots of what it is handed, the invariants that must not break (focus
repair, node ordering, manage/render), and what to return. Mechanically trivial;
cognitively it is reading the source of a window manager. Emacs has precisely this gap —
~advice-add~ is trivial, and knowing what to advise is not.

*Live redefinition has a failure mode nobody wrote down.* Redefine a placement function
wrong and the window manager is placing windows wrong while you are using it. Conditions
and restarts make that survivable, not pleasant — you debug the window manager from
inside the window manager.

*The image drifts from the source.* Anything redefined live and not written back to the
config is gone at the next restart. StumpWM users hit this constantly. The REPL is a
workflow with a discipline attached, not a free feature.

*The wayflan risk mitigation assumes a programmer.* "1,750 lines — forking it is a
Tuesday" is true for someone who writes code. Shaul does not, and the premise of the
project is that the AI budget expires.

** The honest claim that survives

#+begin_quote
We are building a plugin API either way. In Common Lisp it costs zero days of boundary
code, it is not a wall when you need to go past it, and an AI can extend it later
without rebuilding anything.
#+end_quote

That is real and it is *much smaller* than what this document claimed before. It does
not demolish "Rust with a large config and a plugin system" — especially given the type
checker, and given that river's hot-swap already removes most of the restart pain that
usually justifies a live image.

*What still decides it:* a plugin API's coverage is fixed at design time by the person
who will not be there. When a hook turns out to be missing, the compiled path needs a
rebuild — exactly the resource that expires. The Lisp path needs a ~defmethod~.

** Therefore it is a deliverable, not a property

The tiers realistically available to Shaul are 0, and 1 with an example to copy.
*Therefore the config surface and the decomposition determine whether this project
survives Claude access expiring — more than any window-management feature does.*

Standing rules, and they cost feature time:

- *Every [[#p1][P1]] fork is exposed as a tier-0 value*, with both implementations reachable.
- *Policy code never inlines a decision a user might plausibly want to change.* Where a
  ~cond~ would choose between two behaviours, it is a generic function instead.
- *The extension surface is a written document* derived from the source: every policy
  generic, its arguments, its contract, its default method.
- *Ship one example extension per tier*, so that tier 1 is copy-and-modify rather than
  read-the-source.

** What is genuinely not extensible, at any tier

- The manage/render discipline. Protocol law.
- Anything requiring the protocol to do what it cannot — above all, *scaling*.
- Focus as a place rather than a window ([[#d18][D18]]). Structural; everything downstream assumes
  a cursor exists.
- *And decomposition is not free at the bottom.* Generic dispatch per window placement is
  irrelevant at ~100 windows, but "hooks everywhere" should stop at the placement
  emitter's inner loop rather than being applied dogmatically.

* Live reconfiguration
:PROPERTIES:
:CUSTOM_ID: live
:END:

The three-tier model from the Rust plan collapses. Tier 2 was "add an embedded
scripting layer, optional, later" — that is no longer a tier, it is the language.

** Tier 1 — a live SLIME connection to the running window manager

The primary mechanism. SWANK runs in a thread inside the WM image; you connect from
Emacs and redefine anything. This is StumpWM's model and the reason this project is in
Common Lisp at all.

*Implication for Week 1:* start SWANK in the skeleton, before anything interesting
exists. It is how everything after Week 1 gets debugged.

** Tier 2 — a config file, for the things that are genuinely settings

Still worth having for the ~P1~ defaults (which spawn mode, clear-vs-close, shift
scope) so that a fresh install is usable without opening a REPL. It is a Lisp file
loaded at startup, not a separate configuration language.

** Tier 3 — hot-swap the entire window manager

River's headline capability, and *strictly better than hyprland's config reload*,
which hyprland structurally cannot match because there the WM and compositor are the
same process.

The WM is an ordinary Wayland client. Kill it, relaunch — the compositor and every
application keep running.

*Note this matters less than it did.* Under the Rust plan, hot-swap was the entire
development loop. With a live image, most changes never require a restart at all;
hot-swap becomes the recovery path for the rare change that does, plus the crash-and-
restart story. The persistence layer keyed on ~identifier~ is what makes it seamless.
*Still get it working early.*

** Data model

Sketch, not final. Note that leaves may be *empty* — see [[#d17][D17]].

#+begin_src lisp
(defclass lattice ()                    ; one per workspace
  ((cells       :initform (make-hash-table :test #'equal) :accessor cells)   ; (x . y) -> cell
   (col-widths  :initform (make-hash-table) :accessor col-widths)            ; x -> width   (D8)
   (row-heights :initform (make-hash-table) :accessor row-heights)           ; y -> height  (D8)
   (bonds       :initform nil :accessor bonds)                               ; coordinate sets (D16)
   (names       :initform (make-hash-table :test #'equal) :accessor names)   ; name -> (x . y)
   (viewport    :initarg :viewport :accessor viewport)
   (props       :initform nil :accessor props)))                             ; extension bag (D20)

;; A cell is a split tree. A leaf holds a window or NOTHING —
;; an empty pane is first-class and is how slack is placed (D17).
(defclass node () ((props :initform nil :accessor props)))
(defclass leaf (node)                                    ; WINDOW may be NIL
  ((window :initarg :window :initform nil :accessor window)))
(defclass split (node)                                   ; :horizontal | :vertical
  ((direction :initarg :direction :accessor direction)
   (ratio     :initarg :ratio     :accessor ratio)
   (a :initarg :a :accessor a)
   (b :initarg :b :accessor b)))

(defclass viewport ()
  ((origin    :initarg :origin :accessor origin)   ; (x . y) top-left visible cell
   (base-cols :initarg :base-cols :accessor base-cols)   ; the k=1 layout
   (base-rows :initarg :base-rows :accessor base-rows)
   (k :initform 1 :accessor k)))  ; zoom (D10): covers k*base-cols by k*base-rows

;; The lattice cursor (D18). One per seat. Wayland keyboard focus is
;; derived from this and never stored: occupied leaf -> focus_window,
;; empty leaf -> clear_focus.
(defclass focus ()
  ((workspace :initarg :workspace :accessor workspace)
   (coord     :initarg :coord     :accessor coord)
   (path      :initarg :path      :accessor path)))  ; list of :a / :b into the split tree
#+end_src

*Ruling, revised 2026-07-29 after the spike: ~defclass~ for all core state, not
~defstruct~.* This reverses the earlier "structs for the hot data" sketch.

The spike verified the thing that decides it
([[file:SPIKE-WEEK0.org::#ext-3][spike §ext-3]]): a slot was added to a live class by
re-evaluating ~defclass~, and an instance created *before* the redefinition then had the
new slot — initialized, readable, writable, no restart, no migration code. ~defstruct~
cannot do that. Choosing ~defstruct~ for the core data model would have manufactured, by
hand, exactly the limitation the language decision exists to avoid, in order to save an
optimisation nobody has measured a need for.

*The cost, stated honestly:* slot access through ~standard-object~ is slower than a
~defstruct~ slot, and CLOS instances carry more overhead. At ~100 windows this is not
plausibly the bottleneck; the renderer and the wire are.

*The hook that swaps it:* if profiling ever shows node-slot access in the hot layout path
is material, convert *that one class* to ~defstruct~ then, and eat the redefinition pain
locally and knowingly. Do not pay for it project-wide, up front, on speculation.

*~props~ survives the change, with a different justification.* It is no longer a
workaround for ~defstruct~'s immobility — it is the right place for extension state that
has no business becoming a core slot, since a third-party extension tagging nodes should
not be editing a core ~defclass~. See [[#d20][D20]].

** Meta-principle
:PROPERTIES:
:CUSTOM_ID: p1
:END:

*** P1 — where a fork is situational rather than principled, ship both and let config pick the default

Recurring pattern across the 2026-07-29 session. Repeatedly, a design question turned
out to have two answers that are each right in different circumstances (row-shift vs
plane-shift, clear vs close, three spawn placements). Rather than pick one, both ship
as separate commands and configuration selects which holds the primary binding.

*The cost, stated explicitly:* Emacs affords "you can do anything" through a small set
of orthogonal primitives plus a composition language — not through hundreds of
hand-written commands. P1 is only affordable if the verbs are genuinely orthogonal
(verb × direction × scope, composed) rather than enumerated. *If a P1 ruling ever
requires writing two unrelated implementations rather than one primitive with a
parameter, that is the signal that the abstraction is wrong.*

This principle is why the language decision was reopened, and it is satisfied by it.

** Settled decisions

:END:

These are *rulings*, not suggestions. Each records the reasoning so it can be

*They no longer all describe the same program.* Since [[#d21][D21]], the decisions split by layer:

|-------+-----------+--------|
| *Core* | D9, D17, D18, D19, D20, and D14's split-the-focused-container mode | *Live.* These are what gets built first. |
| *Lattice layer* | D1–D8, D10, D12, D13, D15, D16, D22, and D14's /next-to/ and /outer-edge/ modes | *Parked but binding.* Not re-openable as fresh ideas — they are the specification of the extension, built in week 3. |

| *Cross-cutting* | P1, D20's ~props~ ruling, D21 | Apply everywhere. |

*** D1 — Addressing is four-layered; coordinates are read, not typed

Absolute coordinates are the escape hatch, not the interface. Four layers, in order of
how often they are used:

1. *Relative motion* — arrows / ~hjkl~. The overwhelming majority of real navigation.
2. *Ephemeral labels* — avy / ace-window style: press the jump key, every occupied
   cell gets a 1–2 letter overlay, press it, you are there. /Marked tentative/ — build
   it once the minimap exists and see whether it earns its keep.
3. *Durable names on cells* — ~code~, ~mail~, ~scratch~. This is the layer humans
   actually remember. Names, not numbers.
4. *Signed ~(x, y)~ coordinates* — displayed everywhere, directly typeable as a jump
   target (see D4), but never the primary interface.

Rationale: spreadsheet-style ~A1~ has no column left of ~A~, so it cannot express
negatives; making labels relative to the occupied bounding box fixes that but causes
labels to renumber whenever the lattice grows left or up, which destroys exactly the
spatial memory the lattice exists to provide.

*** D2 — Origin ~(0,0)~; +X is right, +Y is *up*

Mathematical convention, deliberately *not* Wayland's screen convention (+Y down).
Chosen because it matches how a person reads a map, and the lattice is a map.

*Cost, accepted knowingly:* one sign inversion at the boundary where lattice
coordinates become surface positions for ~river_node_v1.set_position~. That is a
single line in a single function. *Do not "fix" this by flipping the axis* — it is
intentional.

*** D3 — Two motion speeds; raw step is the default

- *Plain motion* (e.g. ~Super+←/→/↑/↓~) moves *exactly one cell*, whether or not that
  cell is occupied.
- *Modified motion* (e.g. ~Super+Shift+←/→/↑/↓~) *skips to the next occupied cell*,
  crossing any run of empty cells in a single press.

This is the spreadsheet ~Ctrl+Arrow~ idiom (jump to the edge of the data).

Rationale for raw-step being the default: zoom-out is the primary orientation tool, so
motion does not need to defend against getting lost in empty space — the user can
simply zoom out and see where everything is. Keeping the default motion
*distance-predictable* preserves muscle memory ("two cells left"), and the skip motion
remains one modifier away when crossing a gap.

Cost: the skip motion is content-dependent — the same keypress travels a different
distance depending on what is occupied. Acceptable, because it is the non-default.

*** D4 — Direct coordinate jump

A command that accepts a typed coordinate — ~5,0~ / ~-3,2~ — and moves focus there,
whether or not the cell is occupied. Complements, and does not replace, layers 1–3 of
D1.

*** D5 — Coordinate overlay

Cells display their coordinate (~0,0~, ~5,-2~) as an overlay. This is what makes the
lattice legible and is a direct countermeasure to the ZUI get-lost failure mode.

Open sub-question: whether the overlay is always on, appears only when zoomed out past
1×1, or is summoned on a key. Leaning: *on whenever the viewport shows more than one
cell, plus a hold-to-show key at 1×1.*

*** D6 — The lattice is genuinely infinite

No hard bound, no growable-but-bounded compromise. D3's skip motion, D5's overlay, and
zoom-out together supply the navigability that a bound would have provided.

*** D7 — Three verbs: zoom, resize, pan. They never overlap.

The central usability ruling. Most tiling WMs feel muddy because widening a window
also changes what is visible, and the user cannot tell which thing they asked for.
Here they are three separate commands answering three separate questions:

| Verb | User question | Does it change the layout? |
|------+---------------+----------------------------|
| *Zoom* | "How much of my world am I looking at?" | No. Pure view control. Stepping back and forward again returns to exactly the previous state. |
| *Resize* | "How much room does this thing get?" | *Yes.* Persists. |
| *Pan* | "Where am I standing?" | No. Same amount visible, different part of the lattice. |

*** D8 — Spreadsheet geometry: columns have widths, rows have heights

Cells are resizable, but *not* independently. Resizing a cell widens its entire
*column* or heightens its entire *row* — exactly like a spreadsheet. Cell ~(2,-1)~ is
where column 2 crosses row −1.

Rationale: this is what lets cells be non-uniform *without* the lattice going ragged.
Freely-sized independent cells would destroy the alignment that makes integer
coordinates describe anything real, and with it the entire spatial-memory argument
that justifies the lattice over a continuous plane. Spreadsheet geometry keeps every
address exactly where the user left it no matter what has been resized.

*** D9 — Cells contain recursive split trees (Emacs-style)

Flagged here because Shaul identifies it as critical *from the user's perspective*, not
merely as an implementation detail: a cell can be broken up recursively into any
arrangement of splits, arbitrarily nested, like Emacs windows or i3 containers.

*Consequence — resize has two scopes, and both exist:*

1. *Resize a column or row* — moves the boundary between cells, per D8.
2. *Resize within a cell* — moves a divider inside that cell's split tree.

Whether these are one context-sensitive command or two distinct bindings is part of
the [[#keymap][keymap grid]] question, still open; that both operations exist is not.

*** D10 — Zoom is an integer multiplier on the layout, not an absolute cell count

*Zoom level k means: the viewport covers k times as many columns and k times as many
rows.* Cell count therefore goes as k².

Because both axes scale by the same factor, *cells never distort.* This is the whole
reason zoom is a multiplier rather than "add one column" — adding a column alone would
make cells portrait, adding a row alone would make them landscape.

The ladder is *derived from your layout*, not fixed:

| Your layout at k=1 | k=1 | k=2 | k=3 |
|--------------------+-----+-----+-----|
| 1 column × 1 row (default) | 1 cell | 4 cells | 9 cells |
| 2 columns × 1 row | 2 cells | 8 cells | 18 cells |

*** D11 — Pan snaps to the grid; neither pan nor zoom ever resizes a window

*OVERTURNED 2026-07-29 — replaced by [[#d22][D22]], which takes the option rejected below.
Retained in full because D22 is only intelligible as a reversal of it, and because the
costs listed here are exactly what D22 accepts.*

The viewport covers a *fixed extent of lattice space* at a given zoom level. Panning
moves that rectangle so its leading edge aligns to a column or row boundary — a whole
number of cells at a time.

Consequences, all intended:
- Panning *never* changes the scale factor, so a window that stays on screen across a
  pan never resizes.
- Zooming scales both axes identically, so nothing ever distorts.
- The *only* thing that changes a window's size is an explicit resize (D8/D9) or a
  zoom level change. Nothing changes size as a side effect of navigation.

**** The snap-vs-fit conflict, and its resolution

Because the viewport covers a fixed extent while columns may have unequal widths, the
viewport edge will not always land exactly on a cell boundary. There are only two ways
out, and they cannot both be had:

1. *Resize cells so they fit the viewport exactly.* Every edge is always clean. But
   navigating would silently resize windows — violating the core invariant.
2. *Keep snapping, and let the trailing cell be partially visible.* Nothing ever
   resizes. But the trailing edge shows a sliver of the next cell.

*Ruling: always snap, never resize. Option 2.* When snapping and fitting conflict,
snapping wins and the partial cell stays. *The window manager never resizes anything
to make it fit.*

Notes:
- The *leading* edge is always clean, because pan snaps to a boundary. Only the
  trailing edge can be partial.
- With a uniform lattice this never arises at all. It appears only once columns or rows
  have been resized away from uniform.
- The partial is arguably a feature: a sliver at the trailing edge is peripheral
  vision, telling you something is over there.
- ~set_content_clip_box~ renders these partials cleanly — cropped, with the border
  redrawn at the clip edge. Free from the compositor.

*** D12 — Bulk resize

Resizing must work on more than one thing at a time: resize *all* cells, or a selected
range of rows, or a selected range of columns. Not just one boundary at a time.

*** D13 — Opening and closing never shift anything; ~compact~ is an explicit command

Closing a window leaves a *hole*. Cells never move on their own, in either direction,
for any reason.

An explicit ~compact~ command exists to close up gaps deliberately.

Rationale, and it is D8's own argument reused: the entire point of spreadsheet geometry
is that *every address stays where you left it no matter what has been resized*.
Automatic shifting on close would violate that far more aggressively than resizing
ever could — it would move things you were not touching. D6 made the lattice infinite,
so there is no scarcity to compact *for*; and D3's skip motion already exists precisely
to cross gaps cheaply.

*Parked sub-decision:* the ~compact~ family — which edge it compacts toward (up, down,
left, right, diagonal) and at what scope (row, column, region, whole plane). See
[[#open][open questions]].

*** D14 — Spawn placement: all three modes exist; config picks the default

A new window can be placed three ways, and all three ship as commands:

1. *Split the focused cell* — Emacs-style. Takes an orientation (horizontal/vertical)
   *and* which side the new window lands on.
2. *Next to* — the adjacent cell in a given direction.
3. *Outer edge* — the edge of the occupied region in a given direction.

Each takes a direction. *Which is the default is configuration* ([[#p1][P1]]).

*Loose end: the shipped default still has to be chosen.*

*** D15 — Shift semantics: row-local is the default, plane-wide is an explicit command

These are literally Excel's two separate commands, and the analogy is exact:

| | "Insert cells, shift right" | "Insert column" |
|-+-+-|
| Scope | The row only | The whole plane |
| What travels | Content slides through fixed columns | The column travels with its width |
| Can windows resize? | *Yes*, when columns are non-uniform | No |
| Default? | *Yes* | No, explicit command |

The resize consequence is forced, not chosen, and follows directly from D8: because a
*width belongs to a column and spans every row*, sliding content along a row moves it
into differently-sized columns. Example — columns 2, 3, 4 are 800px, 400px, 800px; a
window shifted from column 2 to column 3 gets 400px wide.

On a uniform lattice this is invisible, which is why row-local is the safe default. It
becomes visible only after D8/D12 resizing, at which point it is arguably correct
behaviour: the column is the thing with the width, so occupying a different column
means being a different width.

*Bonus: the ~compact~ family (D13) is the inverse pair* — "delete cells, shift left"
and "delete column". That keymap comes free.

*** D16 — Glue means bond, not merge
:PROPERTIES:
:CUSTOM_ID: d16
:END:

Cells can be *glued* so they travel together. Glued cells keep their own coordinates,
their own split trees, and their own borders — they are not fused into one larger
cell. A bonded group *displaces as a unit* under both D15 shift commands.

Rationale: merging would create a cell spanning multiple grid positions, which breaks
the addressing invariant that makes the lattice legible.

*Recorded cost:* "can a cell span two grid positions?" stays open. The workaround —
a wide column containing an in-cell split — puts the divider on a tree divider that
aligns with nothing in the other rows.

*** D17 — Closing collapses; clearing does not; the empty pane is first-class
:PROPERTIES:
:CUSTOM_ID: d17
:END:

Two *separate commands*, not one command with a mode:

- *~close~* — closes the window and takes its pane with it. The sibling grows to fill
  the space. If it was the cell's only window, the cell is gone (leaving a hole per
  D13).
- *~clear~* — empties the pane but leaves it. You are now standing in an empty pane,
  which still occupies its space.

*Which one holds the primary binding is configuration* ([[#p1][P1]]).

**** The empty pane

An *empty pane is a first-class object*, created deliberately by "splitting into
nothing." This is the resize idiom Shaul asked for — you split a cell and leave one
side empty, and the window occupies the rest.

It also answers most of the "window smaller than its cell" question by giving an
explicit, user-controlled way to place the slack, rather than a global gravity policy.
A default gravity is still needed for the case where a client simply refuses the
proposed size.

Consistent with D13: empty space never appears on its own — only on request.

*** D18 — Focus is a place, not a window
:PROPERTIES:
:CUSTOM_ID: d18
:END:

Focus is a *lattice cursor*: ~(workspace, cell, path-in-split-tree)~. Wayland keyboard
focus is /derived/ from it — if the focused leaf holds a window, that window gets
focus; if the leaf is empty, ~river_seat_v1.clear_focus~. Focus may rest on an empty
leaf, and on an entirely empty cell.

*This was already forced by D3, before the question was ever asked.* D3's plain motion
moves exactly one cell "whether or not that cell is occupied" — a command with no
referent unless focus is a place. Under the window model, plain motion and D3's skip
motion collapse into the same command, and D17's ~clear~ ("you are now standing in an
empty pane") is a category error. *The window model cannot be adopted without repealing
both D3 and D17.*

The governing payoff, stated as one property: *nothing ever moves the viewport except
the user.* Under the window model, closing a window forces focus onto some other
window; MRU can be anywhere on the plane, so a close can teleport the viewport across
it. Here the cursor stays at the coordinate it was already at, and D13's hole is simply
where you are now standing.

**** The focus-repair rule — written once, called by every verb

The cursor points into a tree that every verb mutates (close-collapse, split, pull,
move, bond). *After any tree surgery, focus lands on the deepest surviving node along
its previous path, then on that node's first leaf.*

This is Emacs's marker-adjustment problem: known, bounded, and not free. It must be a
single function that every verb calls. Improvised per-verb repair is how you get
fifteen subtly different behaviours and a bug class where focus points at a node that
no longer exists.

**** What is structural, and what is policy

*The model is structural, not a setting* — everything downstream assumes a lattice
cursor exists. But *every behaviour someone would want from the window model is
reachable as policy on top of this one*, and the reverse is not available. That
asymmetry is the whole argument for choosing this direction:

- focus behaviour after a close — stay put (default), or follow to nearest / MRU
- *whether plain motion skips empty cells* — turn this on and you have the window
  model's entire /feel/ (D3's plain motion behaves like its skip motion) without
  unwinding anything
- whether spawning takes focus
- how entering a cell resolves to a pane within it

These are ~defmethod~-able generic functions, not a fixed option list — which is the
extensibility requirement doing real work rather than being asserted.

**** Cost, accepted

- A focused *empty* cell has no window to hang ~set_borders~ on, so the cursor needs a
  small shell surface of our own. Same machinery as the minimap.
- You can stand somewhere that typing does not reach. Mitigated by [[#d19][D19]], and by the
  cursor being unmissable — that is not optional polish, it is what stops an empty pane
  reading as a broken keyboard.
- No borrowed intuition exists anywhere in the WM world. This is the novelty and the
  onboarding cost in the same sentence.

*** D19 — Typing in an empty pane can spawn something there
:PROPERTIES:
:CUSTOM_ID: d19
:END:

Configurable, and this is what gives the empty pane something to /be/. While the cursor
rests on an empty leaf, unbound keypresses are captured and run through a *keysym →
command table*: ~e~ opens Emacs in that pane, ~t~ a terminal, ~b~ a browser. A mode
where /any/ printable key spawns one configured default also ships ([[#p1][P1]]); the table is
the default.

*Why the table rather than the single default:* the keystroke is consumed as a trigger
and *cannot be replayed into the application that opens*. Nothing in either river
protocol synthesises input, and a virtual-keyboard protocol is a separate,
security-gated global we should not assume exists. So under a single-default policy the
character is silently eaten — type ~ls~ at an empty pane and the terminal opens showing
~s~. Under the table the keypress was a *choice* rather than content, and nothing is
lost. The empty pane becomes a spawn menu with no menu.

*Unverified — this is a Week 1 check, and the design degrades if it fails.* The
mechanism rests on ~ate_unbound_key~:

1. Does it fire at all when the seat has no keyboard focus (~clear_focus~)? If not,
   capture has to be driven some other way.
2. Does it carry the keysym, or only the fact that /a/ key was unbound? *If it carries
   no keysym, only the single-default mode is possible* and the table dies.

Note also that this competes with chorded bindings: holding an empty pane in capture
mode is a standing ~ensure_next_key_eaten~ loop, and submap entry must take precedence
over it.

*** D20 — Entry into a cell resolves geometrically; there is no focus memory
:PROPERTIES:
:CUSTOM_ID: d20
:END:

A cell is a split tree ([[#d9][D9]]), so arriving at a cell does not name a destination. The
rule:

- *Directional motion* enters through the edge it crossed and lands on the leaf
  adjacent to that edge — Emacs and i3 behaviour.
- *Non-directional jumps* (durable name, typed coordinate, ephemeral label) land on the
  cell's *first leaf*. No memory of what was focused there before.

*Why not last-focus memory: it makes windows unreachable.* Cell ~(1,0)~ is split with a
terminal left and an editor right, and the editor was last focused. Press ~→~ from
~(0,0)~ and memory drops you on the editor; press ~→~ again and you leave for ~(2,0)~.
*The terminal cannot be reached by rightward motion at all.* That is a direct violation
of what D3 exists to protect. Geometric entry is also involutive — ~→~ then ~←~ returns
you exactly where you started, because you re-enter through the edge you left by.

Memory is genuinely nicer for named jumps ("put me back in what I was doing in
~code~"), and that is the accepted cost. It is not taken because it is not worth the
state: a per-cell ~last-focus~ path must be persisted with the lattice and repaired by
[[#d18][D18]]'s rule whenever the tree mutates, since a stored path dangles exactly as easily as
a live cursor does. Stateless wins.

**** How the other behaviour is added back — and what that requires of the data model

Entry resolution is a generic function, ~resolve-entry (cell direction)~ with
~direction~ ~NIL~ for a jump. Adding memory is a ~defmethod~.

*But a ~defmethod~ has nowhere to store the memory, and that is a genuine constraint on
the data model rather than a detail:* ~defstruct~ instances cannot gain a slot in a
live image — redefining the structure invalidates every existing instance. ~defclass~
handles this natively through ~update-instance-for-redefined-class~; ~defstruct~ does
not. So an extension that needs per-cell state would require restarting the image,
which is precisely the thing the language decision exists to avoid.

*Rationale superseded, 2026-07-29.* The paragraph above is correct about ~defstruct~ and
it argued for ~props~ as the way around it. The spike settled the better answer: *stop
using ~defstruct~ for core state.* Live ~defclass~ redefinition was verified to migrate
pre-existing instances ([[file:SPIKE-WEEK0.org::#ext-3][spike §ext-3]]), so the
constraint this ruling was working around is self-inflicted, and the data model has been
changed to ~defclass~ throughout ([[#spec][Data model]]).

*Ruling, restated on its own merits: every user-visible object — ~lattice~, ~leaf~,
~split~ — carries a ~props~ plist from day one.* Not because core state cannot grow a
slot, but because *extension* state should not need a core edit to exist. A third-party
extension hanging per-cell data should not be modifying a ~defclass~ it does not own.
This is still the Emacs answer (symbol plists, text properties, buffer-local variables),
and it is still needed: without it, "extensible in Lisp" is true of behaviour and false
of state for anyone who is not the core author.

*** D21 — Layering: the conventional layer ships first, the lattice is an extension
:PROPERTIES:
:CUSTOM_ID: d21
:END:

*The thesis reversal.* Extensibility is the project; the lattice is its first hard test.
Build order:

1. An over-decomposed core (layer 0).
2. A *conventional* layout policy — arbitrary splits, per-window floating, minimize
   leaving the tiling tree. Daily-drivable. Not novel, not trying to be.
3. The *extension surface* itself: documented policy generics, the config file, worked
   examples. Paid for out of feature time.
4. *The lattice, as an extension* — no core edits.

Rationale, and the full argument is in [[#decision][Two layers]] and [[#extensibility][The extensibility surface]]: the
document previously asserted extensibility and never tested it. Building the lattice
from outside makes the claim *falsifiable*. Succeed, and there is proof plus the thing
worth having. Fail, and the claim was false — discovered in week three on a small
codebase, with a working window manager in hand, rather than in month six.

*Step 4 is the deliverable, not a stretch goal.* Stopping after step 2 means a month
spent rebuilding hyprland, worse than hyprland. A novel design may be worse than the
incumbent and still worth running; a conventional one may not.

*Recorded consequence:* if step 4 turns out to require core surgery, *that is the
finding* and it must be written down here rather than quietly absorbed by editing the
core. It is the single most informative result this project can produce about its own
premise.

*** D22 — Zoom is exact fit: cells stretch to fill the viewport (overturns D11)
:PROPERTIES:
:CUSTOM_ID: d22
:END:

/Lattice layer — parked with D1–D16, but ruled, so it is not re-argued./

The viewport always shows a *whole number of cells*, and cells scale so they fill it
exactly. Zoom input is continuous; it snaps to whichever whole-cell fit is closer.

Consequences, all of which reverse D11:

- *Column widths become proportions, not absolute pixels.* The visible columns are
  normalised to fill the screen.
- *The state is ~(cols, rows)~; the input is a scalar.* You turn a continuous knob and it
  lands on an integer pair. This is what reconciles D8 (widths) with D10 (cell counts),
  which were two incompatible models decided the same day and never noticed.
- *The zoom ladder is emergent and needs no authoring.* The achievable views are simply
  every integer ~(C, R)~ pair; zoom walks them by proximity. This dissolves the
  "four in the corners or four in a row?" problem — both are achievable views, and which
  one you land on follows from the current aspect.

*Three things die, and they are the price:*

1. *Partial trailing cells.* Gone. That was the point.
2. *"Panning never resizes a window."* With normalisation, a column's rendered width
   depends on which other columns are visible beside it. Widths 800/400/800/800: panning
   from ~[800,400]~ to ~[800,800]~ resizes everything on screen. Invisible on a uniform
   lattice, guaranteed once D12 has been used — and a pan-step relayout is not cheap
   (terminals rewrap, browsers reflow).
3. *"Cells never distort"* — D10's entire reason for being an integer multiplier.
   ~3×2 → 4×3~ takes a cell from 640×540 to 480×360; the axes scale by different
   factors.

*Mitigations, both required:*

- For (3): *zoom prefers aspect-preserving steps where one exists* (~2×2 → 4×4~,
  ~3×2 → 6×4~) and only lands on shape-changing pairs when a modifier asks for a finer
  step. Tier 0 — a predicate over candidate pairs.
- For (2): *both width solvers ship.* ~exact-fit~ (default) and
  ~absolute-with-clipping~ (old D11) are the same renderer differing in one function —
  /given the visible range and the viewport size, what pixel width does each column
  get?/ Tier 1, one generic, two methods. If pan-resize proves intolerable in use, it
  flips without touching anything else.

- [ ] *verb × direction × scope.* The verbs ~open~, ~move~, ~swap~, ~pull~ each take a

*** Lattice layer — parked until week 3, deliberately

- [X] *Does zoom stay live all the way out, or become a drawn map?* *RULED AND
      BUILT, 2026-07-31: the drawn map ships.* See =lattice/map.lisp=, which
      states the argument, and =doc/drawn-map.png=.

      The proposal below was adopted, with the threshold lowered from ~600px to
      320 — a 320-pixel terminal is still *recognisable*, and recognisable is
      what a peek is for. The counter-argument ("it is a mode, and the thesis
      was that zoom is never a mode") was answered rather than accepted: what
      the thesis objects to is an overview you *enter and leave with a
      command*, because then there are two states and you must know which one
      you are in. Here one control does one thing continuously and the
      rendering changes at a threshold, the way a map changes from streets to
      roads. You never enter it and cannot get stuck in it.

      The decisive point is the one the proposal already made: the alternative
      is not "no mode", it is cells too small to read *and* reflowed twice for
      the privilege. /Original proposal retained below./ Forced by the no-scaling finding (gotcha 6): every
      zoom step genuinely resizes every window. At k=3 on 1080p a cell is 640×360 —
      small but real. At k=4 it is 480×270 and nothing is readable.

      *Proposal:* live windows out to a configurable pixel threshold (default: stop
      once a cell would be under ~600px wide), then stop showing real windows and draw
      the lattice ourselves on a shell surface — cell rectangles, coordinates, cell
      names, window titles, app colours.

      *For:* the map is /free/. Nothing resizes to enter or leave it, so hold-to-peek
      is instant, whereas peeking with real windows would reflow every window on screen
      twice per peek. It is also the natural home for D5's coordinate overlay and D1's
      ephemeral jump labels.

      *Against:* at deep zoom you are looking at a diagram of your desktop rather than
      your desktop. It is a mode, and the original thesis was that zoom is never a mode.

      /Note: the pixel figures in that proposal predate [[#d22][D22]] and assume a 1×1 base
      layout, which made deep zoom look worse than it is. Under D22 the threshold is
      expressed as a cell pixel size, not a zoom level./

- [ ] *The ~compact~ family* (from D13) — which edge (up / down / left / right /
      diagonal) and what scope (row / column / region / plane)?
- [ ] *Can a cell span two grid positions?* (from D16). Still open after the bond
      ruling; the workaround puts a divider where nothing aligns.
- [ ] *Zoom anchor* — when the zoom level changes, how is the new viewport origin
      chosen? Proposed: origin = focused cell − ~floor((N−1)/2), floor((M−1)/2)~, i.e.
      the focused cell lands centre-ish, biased top-left, always visible, deterministic.
- [ ] *Pan animation* — /zoom animation is already answered by the protocol: no./
      Animating /panning/ remains cheap and is still open. Retained so it is not
      re-proposed as a fresh idea.
- [ ] *Workspaces* — infinitely many lattices. How are they addressed, and how does
      that compose with the ~(x, y)~ address of a cell? *Note this is now partly a core
      question* — the conventional layer needs workspaces too, and whatever it chooses
      constrains this.

** Week 1 — core client and the live loop

- Connect, bind globals, run the manage/render loop with the dynamic sequence
  discipline described in [[#language][Language]].
- *SWANK in a thread, and the top-level error handler.* Do this before anything
  interesting exists — it is how everything after this week gets debugged.
- ~handler-case~ on ~wl-message-error~ in the dispatch loop (the destroy-race fix).
- *Turn on static checking on day one:* ~(declaim (optimize (safety 3) (speed 1)))~ in
  development, ~ftype~ declarations on every Layer 0 function, and compiler warnings
  treated as build failures in CI. The spike verified this catches wrong arity,
  wrong-typed constants, typo'd accessors and typo'd calls *at compile time*

  what [[#language][§Language]] concedes to Rust, for the price of a ~declaim~. It will
  not catch a wrong-but-well-typed argument. Cheap enough that not doing it is
  indefensible.
- *Pin the protocol XML in-tree and add the codegen count as a regression check* — 8/57/44/10
  for =river-window-management-v1=, 3/11/5/1 for xkb. The protocol is unreleased and
  moving; a change should surface as a failing build, not a mystery.
- Place windows in a fixed 2×2. Verify:
  - offscreen positioning + ~hide~/~show~ behave as expected
  - keybindings work via =river-xkb-bindings-v1=
  - whether rendering state is genuinely legal in manage sequences (the open question)
  - whether an xdg_popup in a straddling cell gets sliced by ~set_clip_box~

    does it carry the keysym?* The keysym→command table depends on both.

** Week 2 — the conventional layer (the daily driver)

Split trees (D9) promoted from /a cell's contents/ to /the whole layout model/.
Directional focus (D18, D20), the verb grid (open / move / swap / pull × direction ×
scope), close and clear (D17), per-window floating with explicit render ordering,
minimize leaving the tiling tree, workspaces, persistence keyed on ~identifier~ so
hot-swap is seamless.

*Gate: by the end of week 2 this must be usable as the daily driver.* If it is not, the
lattice does not start — fix this first. Everything downstream depends on being able to
live inside it while building the rest.

** Week 2.5 — the extension surface (do not skip; this is the product)

Explicitly budgeted, and paid for by cutting features elsewhere. Rationale in
[[#extensibility][The extensibility surface]].

- Every policy decision made in weeks 1–2 audited into a *named generic function* with a
  documented contract. Anything sitting as an inlined ~cond~ gets promoted.
- *The config file*, with every [[#p1][P1]] fork present as a tier-0 value.
- The *extension-surface document* generated *from the live image*, not from the source:
  each policy generic, its lambda list, its docstring, and every method with its
  specializers. The spike built this in about fifteen lines over
  ~closer-mop:generic-function-methods~ and ~sb-introspect:function-lambda-list~
  ([[file:SPIKE-WEEK0.org::#ext-6][spike §ext-6]]), and it prints
  ~UNDOCUMENTED <-- flag me~ for any generic without a docstring.

  *Pull this forward to Week 1 and make it a CI gate.* It is the cheapest available
  forcing function against this document's own worst fear — an extension surface that
  rots because documenting it is a separate chore from writing it. Generated from the
  image, it is not a separate chore, and it cannot silently drift out of date.
- *One worked example extension per tier*, so that tier 1 is copy-and-modify rather than
  read-the-source.

** Week 3 — the lattice, as an extension (the experiment)

D1–D8, D10, D12, D13, D15, D16 and D22 — coordinates, spreadsheet geometry, viewport,
zoom, pan, shift semantics, bonds, compaction — built *from outside layer 0*.

*The rule: no core edits.* Every time one appears necessary, stop and write down what
was missing and why. *That list is the actual result of this project's central
experiment*, whichever way it comes out — a short, mechanical list means the thesis
held; a lattice that cannot be expressed without surgery means [[#extensibility][the honest claim]] was
still too optimistic, and this document has to say so.

Jump-to-coordinate, named cells, the drawn map / minimap as a shell surface — this is

* Ideas considered and rejected
:PROPERTIES:
:CUSTOM_ID: rejected
:END:

*Do not re-propose these without addressing the stated reason.*

| Idea | Why rejected |
|------+--------------|
| *Rust for the implementation* | Reversed 2026-07-29. Extensibility is the project thesis and a compiled core cannot deliver it without a boundary; the protocol turned out small enough (6 arg types, 11 interfaces) that binding maturity stopped being decisive; the work estimate favours CL once the boundary and script plumbing are counted. See [[#language][Language]] — including the honest list of what Rust would still have done better. |
| *Rust core + embedded Lisp (Steel, ECL, Janet, Rhai)* | The middle path is defined by having a boundary, and the boundary is exactly what makes Neovim-with-Lua and Helix-with-Steel fall short of Emacs. Steel additionally fails the same maturity bar used to doubt wayflan. ECL means a slower Lisp *and* a hand-written C FFI. |
| *Animated zoom* | Structurally impossible: no scaling primitive exists in the protocol, so every frame would resize every window. Animated *panning* is still open and still cheap. |
| *Automatic shifting on open/close* | D13. Violates D8's invariant that addresses stay where you left them, and D6 removed the scarcity that would justify it. |
| *Merging glued cells into one large cell* | D16. Breaks the addressing invariant. Bonding achieves the goal without it. |
| Rewrite Emacs in Rust | Decade-scale. Remacs died at =xdisp= and elisp GC — "things couldn't be updated piecemeal." Rune is one person, 0.1.0, and its author says it won't be a usable replacement. |
| Multithreaded Emacs (worker pool) | The month-sized version *already exists and was ignored*: =session-async.el=, one author, dormant since 2023. Org's own subprocess async demonstrates the fatal structural problem — the worker needs your config, and reproducing it is fragile. Live buffers are structurally off-limits (buffer mutex). |
| Windows programmable/Lisp WM | Superseded — Shaul chose Linux. Remains a viable *future* project. Blockers: cannot replace DWM, elevated windows untouchable, UWP/Electron need a permanent app-rules database, virtual-desktop APIs undocumented. |
| Declarative/plain-text photo editing | GUI feel dominates the value; competing with 15 years of darktable colour science. |
| Unified reading environment | Rejected outright. |
| Standalone org tangler (no Emacs) | Emacs is already available everywhere Shaul works; no real use case. |
| Local search across everything | ~rg~ covers content search; Everything is unbeatable on NTFS filename search. Gap too narrow. |
| Live-coding audio environment | Shaul does not do audio. |
| Typst/DOCX converter, SQL Server client, screenshot automation, release pipeline, structured terminal, filesystem time-travel, programmable spreadsheet | Mostly failed the "would you use it daily" or "could it become the standard" bars. |
| Contributing to Arcan | Means advancing someone else's 13-year vision; the hard parts are graphics plumbing where there's no advantage. |
| Building on Smithay (own compositor) | Not rejected — held as *fallback*. Order of magnitude more work, and it is a Rust library, so taking it also unwinds the language decision. |
| LiNix work | Off-limits by Shaul's explicit instruction. |
| *Scrapping the lattice entirely* — shipping only conventional splits + floating + minimize | Considered seriously 2026-07-29 and *deferred rather than dropped*. What remains after removing the lattice is i3 / sway / hyprland with a scratchpad — mature, maintained by other people, and hyprland is already configured on this machine. A novel design can be worse than the incumbent and still worth running, because it does something the incumbent cannot; a conventional design that is worse is merely worse. [[#d21][D21]] is the sequencing that keeps the idea alive without betting everything on it. |
| *Building the lattice first* (the pre-[[#d21][D21]] plan) | Put the untested extensibility thesis underneath the riskiest feature. Building the lattice as an extension instead makes the thesis falsifiable, and fails cheaply and early if it is false. |
| *Adding a second axis to niri instead of writing a WM* | Investigated 2026-07-30. *There is no layout seam.* niri's only layout trait is ~LayoutElement~, which abstracts /what a window is/ (~request_size~, ~render~, ~sizing_mode~, ~expected_size~) and not /how windows are arranged/; ~Layout<W>~ is generic over the element type, not over the algorithm. Layout logic is embedded directly in ~Workspace~ (scrolling) and ~Monitor~ (workspaces), across a ~5,000-line ~src/layout/~, with logical and physical coordinate spaces threaded throughout. There is no plugin system. Adding a Y axis is rewriting niri's core in someone else's Rust, with no design document and a permanent fork to own. Strictly more work than writing a river client. |
| *The lattice as a Hyprland Lua layout* | Investigated 2026-07-30. Hyprland 0.55 shipped Lua configuration with user-defined layouts (~hl.layout.register(name, {recalculate, layout_msg?})~), expanded in 0.56. It is a real extension point and it is *the wrong shape*, in four ways that are structural rather than effortful. (1) ~recalculate(ctx)~ hands you ~ctx.targets~ and ~ctx.area~ — /N visible windows inside one output rectangle/, which is exactly the abstraction [[#prior-art][orilla]] was rejected for; the lattice needs most windows hidden, positioned outside output bounds, across an unbounded plane. (2) *Focus is a window, structurally* — ~hl.dsp.focus()~ operates on windows and there is no reachable concept of a focused empty place, so [[#d18][D18]] cannot exist. (3) No clip primitive is exposed, so river's ~set_content_clip_box~ (this document's best find) has no equivalent and viewport-edge cells render as windows sliced in half. (4) *It is a designated extension point*, which is the precise thing this project exists to reject — implement the fixed interface, and everything outside it is unreachable. Hyprland's own stability note confirms the shape: internal methods change without notice and the Lua API is guaranteed only while the version matches. *Recorded as evidence for the thesis, not merely as a rejection:* an incumbent built the extension point somebody thought to expose, and the lattice falls outside it. |
