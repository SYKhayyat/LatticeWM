#+TITLE: Installing LatticeWM on Linux
#+OPTIONS: toc:2 num:nil

* The short version

#+begin_src sh
git clone … && cd LatticeWM
./bootstrap.sh        # fetches the Lisp dependencies into ./.deps/
make                  # build, twelve gates, 1493 checks
make image            # dump ./latticewm, one executable
./install.sh          # into ~/.local, and offer it at the login screen
#+end_src

Then log out and pick *LatticeWM*, or try it without logging out of anything:

#+begin_src sh
river -c latticewm    # nested, in a window, inside the session you have
#+end_src

*The first thing to press is =Super+/=*, which draws the whole keymap.

* What it needs

|-------------+---------------------------------------------------------------|
| =sbcl=      | The Lisp compiler.  Every distro packages it.                  |
| =river= 0.4+ | The compositor.  LatticeWM is its window manager, not a       |
|             | replacement for it.                                            |
| =git=, =curl= | Once, to fetch the rest.                                     |
|-------------+---------------------------------------------------------------|

Nothing else.  =bootstrap.sh= puts the Lisp libraries under =./.deps/= and
writes nowhere else; =rm -rf .deps= undoes it completely.

** SBCL

#+begin_src sh
sudo pacman -S sbcl               # Arch, Manjaro, EndeavourOS
sudo apt install sbcl             # Debian, Ubuntu, Mint, Pop!_OS
sudo dnf install sbcl             # Fedora, RHEL, CentOS
sudo zypper install sbcl          # openSUSE
sudo apk add sbcl                 # Alpine
sudo xbps-install -S sbcl         # Void
sudo emerge dev-lisp/sbcl         # Gentoo
#+end_src

Any SBCL from the last few years will do.  =bootstrap.sh= prints the right
line for your distro if it is missing.

** river, and the version that matters

*LatticeWM needs river 0.4.6.*  Not 0.4 or newer — that particular release,
until this program is re-vendored against a later one.  This is not a
preference and it is stricter than it looks, so it is worth the paragraph.

It talks =river-window-management-v1=, the protocol through which river hands
window management to an outside program.  That protocol does not exist before
0.4 at all, and it is young enough that river still changes it *within* a
version number: 0.4.6 raised it from 4 to 5 in what was otherwise a patch
release.  LatticeWM checks the version at startup and refuses to run on a
mismatch in *either* direction, naming both numbers, rather than starting and
misbehaving in ways nobody could diagnose.  If you see that refusal, it is
doing its job; =src/protocol/PINNED= says which river this build was vendored
from and the refusal itself says how to re-vendor.

Check what you have:

#+begin_src sh
river -version
#+end_src

Most distributions package river.  Which release they carry varies and changes
month to month, so check rather than assume — and if it is not the one this
build was vendored against, building river is genuinely easy, because it is one
Zig program with no plugin system.  Check out the matching tag rather than
=main=:

#+begin_src sh
sudo pacman -S zig wayland wayland-protocols libxkbcommon pixman     # or your equivalent
git clone --recurse-submodules https://codeberg.org/river/river
cd river && git checkout v0.4.6
zig build -Doptimize=ReleaseSafe --prefix ~/.local install
#+end_src

=bootstrap.sh= warns if it finds a river that is not the vendored release —
reading the release out of =src/protocol/PINNED=, so the warning cannot drift
from what the program will accept — and does not stop: everything except
actually running the window manager — the build, all twelve gates, all the tests
— works with no compositor on the machine at all.

If you use nix, you do not have to think about any of this: =shell.nix= reads
=flake.lock= and gives you the river the protocol was vendored from, so
=nix-shell=, =nix develop= and =nix build= agree with each other and with
=src/protocol/PINNED=.

** Moving to a newer river

The other direction, and it is four steps rather than two.  You do not have to
remember them: gate 5 fails, by name, on each one you have not done yet — it
pins the codegen counts *and* the version the program binds against the
version the XML declares, so a protocol that changed under you cannot pass
unnoticed and a half-finished re-vendor cannot either.

#+begin_src sh
cp "$(dirname "$(command -v river)")/../share/river-protocols/stable/"*.xml src/protocol/
# 1. set +WINDOW-MANAGEMENT-VERSION+ in src/runtime/session.lisp to the
#    version the refusal named
# 2. name the new release on line 1 of src/protocol/PINNED
make
# 3. gate 5 fails and prints the counts it saw; paste them into the
#    matching row of tools/gates.lisp
make check
#+end_src

=make check= is the one that matters, because it runs the integration suite
against a real headless river and is therefore the only step that can tell you
the new protocol still means what the program thinks it means.  If river has
*removed* or *renamed* something rather than added to it, this is where you
find out, and the compiler finds most of the rest.

Nothing about this needs the original author.  It is a file copy, two numbers,
a line of prose, and a test run.

* Where the Lisp dependencies come from

There are three ways for them to be present and the build cares about none of
them.  =tools/prelude.lisp= works out which applies:

1. *Already visible to ASDF* — a distro package, or a Quicklisp in your home
   directory that your =~/.sbclrc= loads.  Nothing to do.
2. *Under =./.deps/=*, which is what =bootstrap.sh= fills.
3. *Nowhere*, in which case the build stops and says to run =bootstrap.sh=.

The dependency that matters is *wayflan*, the Wayland client library.  The nix
build takes it from nixpkgs, which pins the upstream tree at 2026-01-01;
Quicklisp's dist of the same date carries the same tree.  So the two build
paths do not merely agree, they compile the same source, and there is no
second set of version numbers to keep in step.

The others are ordinary: =alexandria=, =closer-mop=, =bordeaux-threads=, plus
=fiveam= for the tests and =swank= for the REPL bridge.

** If you would rather use your own Quicklisp

#+begin_src sh
sbcl --eval '(ql:quickload (list "wayflan-client" "alexandria" "closer-mop" "bordeaux-threads" "fiveam" "swank"))'
make    # prelude.lisp finds them and never touches .deps/
#+end_src

** If your distro packages the Lisp libraries

Debian and Fedora package some of these as =cl-alexandria= and so on.  If
ASDF can already find them, the build uses them; wayflan is the one that is
unlikely to be packaged anywhere.

* Installing

=install.sh= puts four things in place, and each of them is a step that
somebody's first attempt at running a window manager from source misses:

| =$PREFIX/bin/latticewm=                    | the binary                     |
| =$PREFIX/bin/latticewm-session=            | river, told to run it          |
| =$PREFIX/share/wayland-sessions/….desktop= | so the login screen offers it  |
| =$PREFIX/share/man/man1/latticewm.1=       | =man latticewm=                |

#+begin_src sh
./install.sh                            # ~/.local, no root
sudo ./install.sh --prefix /usr/local   # system-wide
./install.sh --uninstall                # takes it all back out
#+end_src

A home-directory install puts the session entry in
=~/.local/share/wayland-sessions=.  GDM and SDDM read =$XDG_DATA_DIRS= and
find it; a few lighter greeters only look in =/usr/share/wayland-sessions=, so
if LatticeWM does not appear at the login screen, install it system-wide.

Your configuration is never overwritten — not on install, not on upgrade.

* NixOS

#+begin_src sh
nix-shell            # everything, including river and a screenshot tool
make
#+end_src

or with flakes:

#+begin_src sh
nix develop
nix run .#nested     # river with LatticeWM inside the current session
#+end_src

=bootstrap.sh= is unnecessary there and says so.  Nothing under =src/= knows
that nix exists: delete =shell.nix= and =flake.nix= and the project still
builds, which is the property those two files are held to.

** Installing it as a session, with the module

The flake ships a NixOS module, which is the way to get a login-screen entry
without =install.sh=:

#+begin_src nix
{
  inputs.latticewm.url = "github:SYKhayyat/LatticeWM";

  outputs = { nixpkgs, latticewm, ... }: {
    nixosConfigurations.yourhost = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [
        latticewm.nixosModules.default
        { programs.latticewm.enable = true; }
      ];
    };
  };
}
#+end_src

That is all of it.  =programs.latticewm.river= defaults to the river the flake
locks — the one the protocol was vendored from — and the session entry is
built from whatever you set it to, so the pair really is a pair.  Override it
and a mismatch fails =nixos-rebuild= with the two version numbers in the
message, rather than at a login screen where there is no terminal to read a
refusal in.

The module also turns on polkit, =hardware.graphics=, and the wlr xdg-portal,
because river needs all three to be useful and forgetting one produces
symptoms that look like the window manager's fault: no screen sharing, no
file-chooser, no hardware acceleration.

* Checking that it worked

#+begin_src sh
make            # the twelve gates, then the unit suite
./latticewm --version
./latticewm --list-commands | head
river -c "$PWD/latticewm --log-level debug"
#+end_src

The last one runs it nested inside your current session, in a window.  That is
a real compositor speaking the real protocol — it is how nearly all of this was
developed — and it cannot disturb the desktop you are already using.

* When something goes wrong

- *The build stops naming a system it cannot find.*  Run =./bootstrap.sh=.
- *It starts and the screen is black.*  That is an empty pane and it is
  drawn — press =Super+Return= for a terminal, or =Super+/= for the keymap.
- *A change to =init.lisp= broke it.*  Start with =--no-config=.  An error in
  the file is already logged rather than fatal, but this skips it entirely.
- *It will not start after a crash.*  =--no-restore= ignores the saved layout.
- *Nothing responds to keys.*  Check =river -version=; below 0.4 the window
  management protocol is absent and LatticeWM cannot bind anything.
- *You want to see what it is doing.*  =--log-level debug=, and
  =latticewm --eval '(world-cursor *world*)'= asks the running window manager
  where it thinks it is.  The control socket that answers is on by default.
