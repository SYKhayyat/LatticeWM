#+TITLE: Installing LatticeWM on Linux
#+OPTIONS: toc:2 num:nil

* The short version

#+begin_src sh
git clone … && cd LatticeWM
./bootstrap.sh        # fetches the Lisp dependencies into ./.deps/
make                  # build, twenty-two gates, 1300+ checks
make image            # dump ./latticewm, one executable, 13 MB
./install.sh          # into ~/.local, and offer it at the login screen
#+end_src

Then log out and pick *LatticeWM*, or try it without logging out of anything:

#+begin_src sh
river -c latticewm    # nested, in a window, inside the session you have
#+end_src

*The first thing to press is =Super+/=*, which draws the whole keymap.

* What it needs

|----------------+------------------------------------------------------------|
| =sbcl= 2.2.6+  | The Lisp compiler.  Every distro packages it, and every    |
|                | current one is newer than this; Debian and Ubuntu LTS ship |
|                | 2.2.9.  The floor is core compression — the shipping image |
|                | is dumped at zstd level 22 and SBCL used zlib, maximum 9,  |
|                | before 2.2.6.  =bootstrap.sh= checks it and reads the      |
|                | number out of =latticewm.asd=, which checks it again.      |
| =river= 0.4.5+ | The compositor.  LatticeWM is its window manager, not a    |
|                | replacement for it.  *0.4.5 or newer, including newer than |
|                | this build knows about* — LatticeWM binds the protocol at  |
|                | its own version, so a river that has moved ahead speaks    |
|                | the older dialect back and everything works minus the      |
|                | features nobody has vendored yet.  §"river, and the        |
|                | version that matters" says where the floor comes from.     |
| =git=, =curl=  | Once, to fetch the rest.                                   |
|----------------+------------------------------------------------------------|

Nothing else.  =bootstrap.sh= puts the Lisp libraries under =./.deps/= and
writes nowhere else; =rm -rf .deps= undoes it completely.

*Almost nothing else.  One of the Lisp dependencies grovels a C header*, so a
working C compiler is a build requirement of this project even though nothing
in it is written in C.  Most distributions give you one with the base install;
*Fedora does not give you all of it*, because its gcc is configured to read
RPM's hardening specs and those live in =redhat-rpm-config=:

#+begin_src sh
sudo dnf install redhat-rpm-config     # Fedora, RHEL, CentOS
#+end_src

Without it =bootstrap.sh= stops with =gcc: fatal error: cannot read spec file
'/usr/lib/rpm/redhat/redhat-hardened-cc1'=, which names neither this project
nor the package.  It says which package now, and this paragraph exists because
a stock Fedora is where that was found rather than where it was predicted.

** SBCL

#+begin_src sh
sudo pacman -S sbcl               # Arch, Manjaro, EndeavourOS
sudo apt install sbcl             # Debian, Ubuntu, Mint, Pop!_OS
sudo dnf install sbcl             # Fedora, RHEL, CentOS
sudo zypper install sbcl          # openSUSE
sudo apk add sbcl                 # Alpine
sudo xbps-install -S sbcl         # Void
sudo emerge dev-lisp/sbcl         # Gentoo
#+end_src

*2.2.6 or newer*, and that is a real floor rather than a shrug at "recent".
=tools/image.lisp= dumps the shipping image at zstd level 22; SBCL's core
compression was zlib with a maximum level of 9 until 2.2.6, so on an older one
=make build gates test= may pass and =make image= cannot, which leaves nothing
to install. The number lives in =latticewm.asd=, which checks it whenever the
system is loaded — including from a bare =(ql:quickload :latticewm)= — and
=bootstrap.sh= reads it back out of that file rather than keeping a copy.

Every current distribution is newer: Debian and Ubuntu LTS ship 2.2.9, Arch
and Fedora ship current. =bootstrap.sh= prints the right install line for your
distro if SBCL is missing.

** river, and the version that matters

*LatticeWM needs river 0.4.5 or newer, and "or newer" has no upper end.*

It talks =river-window-management-v1=, the protocol through which river hands
window management to an outside program.  That protocol does not exist before
0.4 at all, and it is young enough that river still changes it *within* a
version number: 0.4.6 raised the interface from 4 to 5 in what was otherwise a
patch release.  So the version is checked at startup — but as a *floor*, not
as an equality, and the difference is the whole of this section.

Wayland versions every interface, and a client says which version it wants
when it binds.  The compositor is then obliged to speak that version, not the
newest one it knows.  LatticeWM binds at the version its vendored XML declares,
so a river three releases ahead answers in the dialect this build was compiled
for.  You lose the features added after your build, and nothing else.  That
means *your distribution can move river without asking you*, which is what
distributions do, and which used to mean a login screen that refused.

Downward there is no such trick, and that is where the floor is.  Of the
requests LatticeWM sends, the newest arrived in interface version 4
(=exit_session=, =set_dimension_bounds=, =set_presentation_mode=), so 4 is the
floor.  Below it LatticeWM would be sending requests the compositor has never
heard of, and there is no degrading around that — so it refuses, names both
numbers, and tells you to upgrade.  The floor moves only when LatticeWM starts
sending something newer; re-vendoring alone does not move it.

In river releases that is *0.4.5 or newer*, which is the number quoted above.
river 0.4.5 carries interface version 4 and 0.4.6 carries 5.  Whether some
earlier 0.4.x also carried 4 is not recorded here, so an older river may work
and is untested.  The check is on the interface version, not on the release
string, so if it starts it is because the protocol agreed.

*The bottom of that range is exercised rather than assumed.*  =make
integration= — the suite that drives a real headless river as a client — runs
green against river 0.4.5 on Fedora 44, which is a build vendored at interface
version 5 talking to a compositor offering 4.  It binds at 4, receives no
=capture_sessions= because that event arrived in 5, reports that as a version
gap rather than a failure, and passes everything else.  That is the exact
configuration the old equality check refused to start in.

If you want to know what a given build accepts, ask it:

#+begin_src sh
latticewm --version    # LatticeWM 0.1.0 (river_window_manager_v1 v4-v5, ...)
#+end_src

Check what you have:

#+begin_src sh
river -version
#+end_src

Most distributions package river.  Which release they carry varies and changes
month to month, so check rather than assume — and if it is not the one this
build was vendored against, building river is genuinely easy, because it is one
Zig program with no plugin system.  Check out the matching tag rather than
=main=:

#+begin_src sh
sudo pacman -S zig wayland wayland-protocols libxkbcommon pixman wlroots  # or your equivalent
git clone --recurse-submodules https://codeberg.org/river/river
cd river && git checkout v0.4.6
zig build -Doptimize=ReleaseSafe --prefix ~/.local install
#+end_src

*Two things that cost an evening here and are written down rather than
remembered.* River pins its Zig hard: =v0.4.6= wants *Zig 0.16*, and a 0.14 or
0.15 fails at =build.zig= line 10 with ='@import' of ZON must have a known
result type=, which names neither Zig nor a version. Read =README.md= at the
tag you checked out — it says which. If your distribution packages a different
one, the official tarball unpacks anywhere and needs no root:

#+begin_src sh
curl -sSLO https://ziglang.org/download/0.16.0/zig-x86_64-linux-0.16.0.tar.xz
tar xf zig-x86_64-linux-0.16.0.tar.xz
./zig-x86_64-linux-0.16.0/zig build -Doptimize=ReleaseSafe --prefix ~/.local install
#+end_src

And river pins *wlroots* just as hard: =v0.4.6= wants *0.20*, and a 0.19 fails
with =unable to find dynamic system library 'wlroots-0.20'=.  Check with
=pkg-config --modversion wlroots-0.20= before starting.

*Both of those are moving targets and your distribution decides which you get.*
Ubuntu 26.04 packages Zig 0.14 and wlroots 0.19 — neither is enough, so river
has to be built with a downloaded Zig against a wlroots you also build.
Fedora 44 packages Zig 0.16 and wlroots 0.20.2, and river builds out of the box
on it.  That is not a recommendation of one distribution over another; it is
the reason this section exists, and the reason the two-line check above is
worth running before the clone rather than after the failure.

*Check your package manager before any of this.*  Fedora 44 packages river
itself — =sudo dnf install river= gives 0.4.5, which is inside the supported
range, so none of the Zig and wlroots archaeology above applies there.  That is
the ordinary case and it is worth trying first; the build instructions are for
when your distribution has nothing, or has something below the floor.

=bootstrap.sh= warns if it finds a river that is not the vendored release —
reading the release out of =src/protocol/PINNED=, so the warning cannot drift
from what the program will accept — and does not stop: everything except
actually running the window manager — the build, all twenty-two gates, all the tests
— works with no compositor on the machine at all.

If you use nix, you do not have to think about any of this: =shell.nix= reads
=flake.lock= and gives you the river the protocol was vendored from, so
=nix-shell=, =nix develop= and =nix build= agree with each other and with
=src/protocol/PINNED=.

** Moving to a newer river

The other direction, and it is four steps rather than two.  You do not have to
remember them: gate 5 fails, by name, on each one you have not done yet — it
pins the codegen counts *and* the version the program binds against the
version the XML declares, so a protocol that changed under you cannot pass
unnoticed and a half-finished re-vendor cannot either.

#+begin_src sh
cp "$(dirname "$(command -v river)")/../share/river-protocols/stable/"*.xml src/protocol/
# 1. set +WINDOW-MANAGEMENT-VERSION+ in src/runtime/session.lisp to the
#    version the refusal named
# 2. name the new release on line 1 of src/protocol/PINNED
make
# 3. gate 5 fails and prints the counts it saw; paste them into the
#    matching row of tools/gates.lisp
make check
#+end_src

=make check= is the one that matters, because it runs the integration suite
against a real headless river and is therefore the only step that can tell you
the new protocol still means what the program thinks it means.  If river has
*removed* or *renamed* something rather than added to it, this is where you
find out, and the compiler finds most of the rest.

Nothing about this needs the original author.  It is a file copy, two numbers,
a line of prose, and a test run.

*And it is run rather than only written down, which it was not.* This recipe is
the install path for most people — the pin is exact, and on most distributions
at most times the packaged river will not match it — while gate 5 only ever
checked the river we had already vendored from.

#+begin_src sh
make revendor-check                      # a river we do NOT accept is refused,
                                         # by name, with both version numbers
make revendor-check RIVER_SRC=~/src/river   # do the recipe for real, and build
#+end_src

The first needs nothing but this checkout: it bumps an interface version in a
scratch copy of the XML, asserts the build refuses and says which interface and
which two numbers, and puts the tree back.  A pin that fails silently is worse
than no pin, and that is the property it holds.  The second is the recipe
itself, executed: point it at a river source tree and it copies, rewrites
=PINNED=, builds and runs the gates, and tells you either that the four steps
worked or exactly which one did not.

* Where the Lisp dependencies come from

There are three ways for them to be present and the build cares about none of
them.  =tools/prelude.lisp= works out which applies:

1. *Already visible to ASDF* — a distro package, or a Quicklisp in your home
   directory that your =~/.sbclrc= loads.  Nothing to do.
2. *Under =./.deps/=*, which is what =bootstrap.sh= fills.
3. *Nowhere*, in which case the build stops and says to run =bootstrap.sh=.

The dependency that matters is *wayflan*, the Wayland client library.  The nix
build takes it from nixpkgs, which pins the upstream tree at 2026-01-01;
Quicklisp's dist of the same date carries the same tree.  So the two build
paths do not merely agree, they compile the same source, and there is no
second set of version numbers to keep in step.

The others are ordinary: =alexandria=, =closer-mop=, =bordeaux-threads=, plus
=fiveam= for the tests and =swank= for the REPL bridge.

** If you would rather use your own Quicklisp

#+begin_src sh
sbcl --eval '(ql:quickload (list "wayflan-client" "alexandria" "closer-mop" "bordeaux-threads" "fiveam" "swank"))'
make    # prelude.lisp finds them and never touches .deps/
#+end_src

** If your distro packages the Lisp libraries

Debian and Fedora package some of these as =cl-alexandria= and so on.  If
ASDF can already find them, the build uses them; wayflan is the one that is
unlikely to be packaged anywhere.

* Installing

=install.sh= puts six things in place, and each of them is a step that
somebody's first attempt at running a window manager from source misses:

| =$PREFIX/bin/latticewm=                    | the binary                            |
| =$PREFIX/bin/latticewm-session=            | river, told to run it                 |
| =$PREFIX/share/wayland-sessions/….desktop= | so the login screen offers it         |
| =$PREFIX/share/man/man{1,5}/=              | both man pages                        |
| =$PREFIX/share/latticewm/=                 | the lattice, examples, docs, protocol |
| =$PREFIX/share/latticewm/doc/=             | the licences, ours and the font's     |

#+begin_src sh
./install.sh                            # ~/.local, no root
sudo ./install.sh --prefix /usr/local   # system-wide
./install.sh --uninstall                # takes it all back out
#+end_src

Three more flags exist for packagers. =--no-config= skips writing a starter
=init.lisp=; =--river PATH= names the compositor the launcher and the session
entry run, instead of whatever =river= resolves to at login; and =--destdir
PATH= writes everything under a staging root while baking =--prefix= into the
paths inside the files.

#+begin_src sh
make DESTDIR="$pkgdir" PREFIX=/usr install
#+end_src

is what Arch, Debian, RPM, Gentoo, Alpine and Void all build with, and it is
the thing =--prefix= alone cannot express: a package needs =/usr= inside every
path the installed program will use and every byte written somewhere else.
=DESTDIR= implies =--no-config=, because no postinstall may write into a
user's home directory — which is also what a system install used to do, into
*root's* =.config=, under the =sudo ./install.sh --prefix /usr/local= this
document recommends. =make install-check= now runs the staged path too, and
asserts the thing only that path can get wrong: that the launcher and the
session entry name the prefix rather than the staging root, which is the
packaging bug that installs cleanly and fails at a login screen.

*This is the only installer.* =nix build= runs this same script rather than
keeping its own list of what ships — there used to be two lists and they had
drifted apart, including over the lattice sources, which meant the
shipped configuration failed to load on the one path that reaches a user who
never ran =make=. Gate 9 checks that =flake.nix= still delegates and installs
nothing by hand; =make install-check= installs to a scratch prefix, checks
every file above is there, and then checks that uninstalling gives all of it
back.

The bitmap font is Terminus, under the SIL Open Font License, and the licence
text ships with the install because =src/runtime/font.lisp= says it must travel
with any copy of the glyph table — which the binary contains.

A home-directory install puts the session entry in
=~/.local/share/wayland-sessions=.  GDM and SDDM read =$XDG_DATA_DIRS= and
find it; a few lighter greeters only look in =/usr/share/wayland-sessions=, so
if LatticeWM does not appear at the login screen, install it system-wide.

Your configuration is never overwritten — not on install, not on upgrade.

** For packagers: the version, and a tarball

The version lives in one file, =VERSION=. Both =.asd= files read it with
ASDF's =:read-file-line=, =flake.nix= reads it with =builtins.match= the same
way it already reads river's version out of =src/protocol/PINNED=, and gate 19
holds both man pages to it. It used to be written out in four places, and the
sole git tag matched none of them.

=make dist= writes =dist/latticewm-<version>.tar.gz= from the git index, so
what ships is exactly what is tracked — no =.deps/=, no fasl cache, no image
somebody left in the tree. It refuses on a dirty tree and on a tag that
disagrees with =VERSION=. The release procedure is in =CHANGELOG.md=.

nix-shell            # everything, including river and a screenshot tool
make
#+end_src

or with flakes:

#+begin_src sh
nix develop
nix run .#nested     # river with LatticeWM inside the current session
#+end_src

=bootstrap.sh= is unnecessary there and says so.  Nothing under =src/= knows
that nix exists: delete =shell.nix= and =flake.nix= and the project still
builds, which is the property those two files are held to.

** Installing it as a session, with the module

The flake ships a NixOS module, which is the way to get a login-screen entry
without running =install.sh= yourself.  The store path it installs is built by
that same script; what the module adds is a session entry naming the river
=programs.latticewm.river= is set to, which is a decision only a system
configuration can make.

#+begin_src nix
{
  inputs.latticewm.url = "github:SYKhayyat/LatticeWM";

  outputs = { nixpkgs, latticewm, ... }: {
    nixosConfigurations.yourhost = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [
        latticewm.nixosModules.default
        { programs.latticewm.enable = true; }
      ];
    };
  };
}
#+end_src

That is all of it.  =programs.latticewm.river= defaults to the river the flake
locks — the one the protocol was vendored from — and the session entry is
built from whatever you set it to, so the pair really is a pair.  Override it
and a mismatch fails =nixos-rebuild= with the two version numbers in the
message, rather than at a login screen where there is no terminal to read a
refusal in.

The module also turns on polkit, =hardware.graphics=, and the wlr xdg-portal,
because river needs all three to be useful and forgetting one produces
symptoms that look like the window manager's fault: no screen sharing, no
file-chooser, no hardware acceleration.

* Checking that it worked

#+begin_src sh
make            # the twenty-two gates, then the unit suite
./latticewm --version
./latticewm --list-commands | head
river -c "$PWD/latticewm --log-level debug"
#+end_src

The last one runs it nested inside your current session, in a window.  That is
a real compositor speaking the real protocol — it is how nearly all of this was
developed — and it cannot disturb the desktop you are already using.

* When something goes wrong

- *The build stops naming a system it cannot find.*  Run =./bootstrap.sh=.
- *It starts and the screen is black.*  That is an empty pane and it is
  drawn — press =Super+Return= for a terminal, or =Super+/= for the keymap.
- *A change to =init.lisp= broke it.*  Start with =--no-config=.  An error in
  the file is already logged rather than fatal, but this skips it entirely.
- *It will not start after a crash.*  =--no-restore= ignores the saved layout.
- *Nothing responds to keys.*  Check =river -version=; below 0.4 the window
  management protocol is absent and LatticeWM cannot bind anything.
- *You want to see what it is doing.*  =--log-level debug=, and
  =latticewm --eval '(world-cursor *world*)'= asks the running window manager
  where it thinks it is.  The control socket that answers is on by default.
