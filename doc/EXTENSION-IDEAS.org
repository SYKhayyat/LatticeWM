#+TITLE: Extension Ideas
#+SUBTITLE: Things the policy layer could become, collected before they were built
#+OPTIONS: toc:2 num:nil

This document is a backlog, not a plan. Nothing here is promised, nothing
here is scheduled, and nothing here has been argued to the standard DESIGN.org
holds decisions to. Each entry states the behavior a user would see, what
makes it natural in Common Lisp specifically, and which part of the surface
it would touch — so that whoever picks it up (including a future version of
the author) can tell quickly whether it is still worth doing.

Ideas graduate out of this file by being built or by being refuted in
writing. They do not rot silently: if an idea here becomes impossible because
the core changed, that is a finding and belongs in FINDINGS.org with this
file updated to say so.

* Promotions — examples that should be modules

STATUS, updated as they land: all four have graduated.  ~focus-follows-mouse~,
~master-stack~, ~scrolling-columns~ and ~window-rules~ are modules under
=extensions/=, each loadable with =(load-extension "...")= and each carrying
its own tests in the build.  The examples remain for teaching; the modules are
what a user loads.

The four files under =examples/= exist to teach the extension surface. Three
of them are also things users ask for on every tiling window manager, and a
user should not have to copy lisp out of a teaching directory to get it.

Each becomes its own ASDF system beside =lattice=, loadable with
=(load-extension "...")=, held to gate 3 (no reaching into src/) and gate 4
(core loads and lays out with the extension absent):

- ~focus-follows-mouse~ — one hook consumer. BUILT.
- ~master-stack~ — a second layout model; one method. Its value as a module
  is evidentiary: every additional layout model outside src/ is another data
  point for the claim that the conventional policy is not privileged.
- ~scrolling-columns~ — same argument, stronger example: niri's whole model
  in sixty lines.
- ~window-rules~ — a friendlier front over the built-in table; lowest value
  of the four, since =(setf *window-rules*)= already covers most of it.

* Buffers — windows you call by name

STATUS: BUILT, as =extensions/buffers/=.  The registry is a hash on the world;
switching recalls through the minimize/restore doors so the displaced window
remembers its spot; the three open questions below were settled as follows --
focus after a recall is configurable and defaults to following; undo ignores
switches by default (the switch resets undo's baseline instead of recording)
with an opt-in to record; two panes never show one window, because a live
Wayland window has exactly one rectangle, so an on-screen buffer jumps instead.

The problem: today a window lives in exactly one pane. To look at it
somewhere else you move it there. If it is minimized it is gone until
restored to the same place.

The behavior: every window gets a name. Any pane can display any window by
name, from anywhere. Standing in a pane and asking for ~chat~ shows the chat
window right there. The window was never moved or closed; panes are views,
windows are objects.

What exists already, and what does not:

- *Tabs* are a stack of windows in one pane showing one at a time. What they
  lack is exactly the buffer idea: tabs are anonymous and local to their
  pane. Buffers are named and global.
- *Minimize* already preserves identity and position across hide/show. That
  is the mechanism the buffer layer hides clients with.
- The *prompt machinery* already does prefix/substring/subsequence completion
  with a history ring. Buffer switching is one prompt away.

The genuinely new surface is small: a global registry (name → window), a
display verb a pane delegates to, and answers for the questions tabs never
face — focus repair when a named window moves panes mid-operation, whether
layout undo crosses a buffer swap, what bury means when two panes show the
same name (or whether that state is representable at all).

Roughly a hundred and fifty lines against the container surface, and it would
be the first extension that changes how the tree is *thought about* rather
than what keys do.

* Projects — workspaces bound to directories

A project is a folder. This extension binds a workspace to one: spawning a
terminal there starts in it, the editor opens it, and switching projects
switches everything at once. Switch-by-name from the prompt.

Natural in Lisp for the same reason buffers are: a project is a small object
with a hook into spawn and workspace creation, not a feature of the
compositor. Touches the spawn table and one or two placement generics.

STATUS: BUILT, as =extensions/projects/=.  The seam it needed was one dynamic
variable, =*spawn-directory*=, consulted by the single =spawn= command every
spawn path funnels through; the binding between project and workspace is the
workspace's label, so nothing here owns a workspace and nothing can go stale.

* Transient rules — "the next window matching X"

Permanent rules say pavucontrol always floats. A transient rule says: the
NEXT window matching this opens floating, once, then expires. Useful for
applications whose second window differs from their first — installers,
dialogs that follow a main window, anything where a permanent rule would be
too broad.

Implementation shape: a queue consulted at manage time before the permanent
table, entries consumed on first match. One hook (~:manage~-adjacent) plus a
prompt verb ("next matching window floats"). Small, and it closes a real
expressiveness gap river's own protocol leaves open.

STATUS: BUILT, as =extensions/transient-rules/=.  The queue is consulted by
a PRIMARY method on =window-rule-for= — primary, not another ~:around~,
because two methods with identical qualifiers and specializers replace
rather than compose, and window-rules already owns an ~:around~ there.

* Idle and lock — a native session policy

hypridle-equivalent behavior using the hook surface: dim after N minutes,
lock via ext-session-lock-v1, DPMS off after M. The lock half is already
described in README.org's locker section — the WM knows a lock is held and
behaves correctly under it. What is missing is the timer side and a config
surface for the thresholds. Replaces an external daemon for this session and
exercises hooks nobody has used for anything timing-shaped yet.

STATUS: BUILT, as =extensions/idle-lock/=, on the =:user-activity= hook the
runtime grew for it.  Thresholds are a list of (seconds . command) steps that
fire once per quiet period, with resume commands for when presence returns;
a session already locked stands down rather than fighting its locker.

* Layout persistence — arrangements that survive logout

The core already saves layouts and reads them back. This extension makes
that automatic per-workspace: save on change or on exit, restore at session
start, with the honest caveat README.org already carries — undo restores
arrangements, not applications; windows that closed while logged out are
absent from the restored tree. Worth deciding early whether restore is best
effort (missing windows skipped) or exact (refuses when the tree cannot be
honored).

STATUS: BUILT, as =extensions/layout-persistence/=, in both modes —
=:best-effort= keeps an empty pane where an application has not come back,
=:exact= refuses whole rather than half-honour — and keyed by application id
rather than river identifier, so a named layout means the same thing after a
reboot.  Save-on-change rides the core's own coalesced save.

* Ideas that need Common Lisp to make sense

These are the ones the reminder "this is CL" is pointing at — features that
are either unnatural or impossible in a C/Rust WM, because they depend on
the program being a live image of generic functions rather than a fixed
binary.

** Restarts for broken windows — the condition system, applied

When an application exits unexpectedly, or a client misbehaves at manage
time, signal a condition instead of printing a log line. Attach restarts:
=~RETRY= re-spawn the application, =~UNDO= revert whatever layout change was
in flight, =~DISMISS= ignore. Restarts are selectable from the keyboard, in
an echo-area menu, exactly like an SLDB buffer.

No other WM offers this because no other WM has restarts. It converts "my
app crashed and now my layout is weird" from a debugging session into a
menu pick.

STATUS: BUILT, as =extensions/window-restarts/=.  A window that vanishes
unasked-for is a BROKEN-WINDOW condition and an echo-area notice; the three
answers are ordinary commands and a keymap you bind behind your own chord.
"Asked for" is decided by whether a close command ran half a second ago.

** Window rules as methods — EQL specializers

The rule table maps properties to behaviors. But the policy layer is generic
functions, which means a rule *is* a method waiting to happen:

#+begin_src lisp
(defmethod p:placement :around ((policy conventional-policy)
                                (window (eql-app-id "pavucontrol")))
  (call-next-method :float t))
#+end_src

A rules module could store rules in exactly this form: listable (each rule
is inspectable source), removable (remove-method), ordered by specificity
(CLOS computes it), and live-patchable from the prompt. The table stops
being a parallel mini-language and becomes the language itself. Whether the
ergonomics beat a plain list for non-programmers is the open question —
examples/02 exists because the table is usually enough — but for the tier-2+
user this dissolves the boundary between configuring and programming.

STATUS: BUILT, as =extensions/rules-as-methods/= — with the honest
mechanical answer to the specializer question: a rule is a method on a
generic eql-specialized on the app-id STRING, not on the window, and the
bridge into placement is the runtime's =:window-rule= hook, so no :AROUND
methods fight over identical specializers.

** Command journal and replay

Record every command that changes state — keys, socket forms, SLIME — into
a replayable journal (undo already walks the same doors for layouts). Then:
replay a journal into a fresh session and reproduce yesterday's arrangement
and settings exactly; diff two journals to answer "what did I change since
it worked"; ship a journal as a bug report. The capture points all exist;
the journal is storage discipline over them.

STATUS: BUILT, as =extensions/command-journal/= — one wrapper on the one
command path, entries as plain =(command . arguments)= lists saved beside the
layouts.  Replay goes through RUN-COMMAND so every other extension's wrapper
sees it; undo, redo and repeat are looked straight through.

** Keyboard macros

Wrap command dispatch: start/stop recording, replay, name. Because every
user action routes through one command path, recording is interception at a
single choke point rather than input synthesis. Ten lines of state around
dispatch, and the WM has vim-style repeatable sequences over arbitrary
commands including prompts.

STATUS: BUILT, as =extensions/keyboard-macros/= — the ten lines grew a
little saving named macros beside the journals, and the exclusion list
learned from command-journal's lesson about what =.= repeats.

** Save-world sessions

SBCL can dump a running image. A session could too: extensions loaded,
settings changed, journals attached — ~save-session~ writes a core; the next
login resumes that image instead of booting the default one and re-reading
init.lisp. Sessions stop being configuration applied at startup and become
state that persists. The hard problems are reconnecting to a fresh river
(the image must survive its sockets dying) and the temptation to treat a
core dump as a backup strategy. Listed because it is the most
concept-changing idea in this file, flagged because it may be the least
worth the cost.

STATUS: BUILT, as =extensions/session-dump/= — and cheaper than feared,
because the shipping binary was already a dumped image, so the mechanism is
proven in every install.  =M-x dump-session= saves the layout, writes the
image with a resume toplevel that calls START (:CONFIG NIL — the image's
settings ARE the configuration now), and exits; resume reconnects to the
fresh river.  The costs named above are real: a core is 100+ MB, version
skew must be managed (nix pins it), and it is not a backup.

* Sessions from a file — declared, not remembered

The problem with restore-style persistence is that it answers "what was
open when I left" rather than "what should be open". This extension is the
declarative direction: a text file that names workspaces, the applications
that belong in them, and their placement, and a loader that builds the whole
arrangement from it at startup or on demand.

The format question answers itself in CL: the manifest is Lisp. Where a
YAML schema needs a loop construct, this has ~loop~; "four terminals tiled
on workspace 3" is one form; conditionals and variables cost nothing:

#+begin_src lisp
(workspace 1
  (split :horizontal
         (app "emacsclient -c")
         (app "foot")))
#+end_src

The loader may be close to free: =--eval= already exists, so loading is
reading a file of forms into the running image.

What makes it more than dotfile plumbing is the symmetry with the command
journal (above): the journal *records* sessions backward, the manifest
*declares* them forward — same machinery pointed both ways. A journal can be
edited into a manifest; a manifest replay produces a journal-shaped log.
Deciding early that both share one notion of "a session's state changes"
keeps them from growing two formats.

Placement half vs spawn half matters: the core already reads saved layouts,
so arranging existing windows is mostly done. Spawning applications into
declared places is the new part, and it wants care around windows that fail
to start or arrive late.

STATUS: BUILT, as =extensions/declared-sessions/=.  The manifest is Lisp,
read with the keyword package so bare tags just work; the skeleton is built
first as empty panes and each application is spawned into the pane waiting
for it — arrivals ride the =:window-rule= hook, one consumption per window.
A workspace that already holds windows is never dropped for a declaration.

* Floating-only — a policy, not a hack

Some users do not want tiling at all: every window floats, drag-and-resize
everywhere, nothing snaps. The README positions floating as one verb among
many; this extension makes it the whole model.

It belongs on this list because of what it would prove. If the layout model
is genuinely a replaceable policy, then "no layout" must be expressible as a
policy — a placement method that declines to tile — rather than a pile of
=~float= rules bolted onto a tiler that still wants to tile. One class, a
few methods answering "where does a new window go" (nowhere; center it) and
"what does resize mean" (the pointer's answer), and the conventional tree is
never entered.

STATUS: BUILT, as =extensions/floating-only/=, and the proof went through:
one class, ONE overridden method (=should-float-p= answers yes), zero core
changes.  Placement already knew what to do with a window that should float.
See FINDINGS.org's extensions-era section.

If it turns out floating-only cannot be written without reaching past the
published surface, that refutes part of the architecture claim and belongs
in FINDINGS.org either way.

* Nested compositor cells — other WMs as panes

Not as ridiculous as it sounds, because LatticeWM does it to itself daily:
~make run~ starts river nested inside the current session as an ordinary
Wayland client. Any compositor that supports nested operation becomes just
another window in the tree.

A nested cell would be a pane owning a child process (the inner compositor)
and its socket; closing the cell kills the process; the inner WM's windows
are invisible to LatticeWM, which sees one client. Uses even without the
lattice: testing a WM change without leaving the session; a workspace that
is a whole different desktop.

Feasibility by inner WM: river nested is proven (the development loop).
Hyprland nests via ~WLR_BACKENDS=wayland~. niri is Smithay-based and whether
it runs as a Wayland client at all is unverified — test before promising
anything.

Costs, stated plainly: keybinding collisions (both WMs want Super chords;
the outer grabs first, so the inner needs a different modifier or an escape
hatch), double compositing overhead, and focus routing across two keyboard
grabbers stacked at one boundary. Lifecycle and cleanup are the deep part;
spawning a process into a pane is mostly spawn-table work.

In the lattice extension this becomes what it sounds like: each plane of
the infinite grid hosting an entire foreign window manager. Listed under
the CL tier not because Lisp is required but because the container surface —
a new kind of cell content — is exactly the mechanism gate 2 documents for
adding kinds of things panes can hold.

STATUS: BUILT (supervision half), as =extensions/nested-cells/= — named
cells with a supervised child inheriting the session's =WAYLAND_DISPLAY=,
close/reopen semantics, and a sweep that forgets children who died on their
own.  Placement of the cell's window composes with the rule modules rather
than duplicating them; whether a given inner compositor nests cleanly is
that compositor's business.

* Ordering

If forced to sequence: promote the four examples first (housekeeping, and it
hardens the extension path for everything else); then buffers (highest ratio
of conceptual change to code); then transient rules and idle/lock (small,
independent, immediately useful); then projects, persistence, and the CL
tier as interest dictates. The CL tier ideas share a prerequisite worth
building deliberately when the first of them lands: a single, documented
notion of "every door through which state changes" — undo and the journal
want the same list, and finding it once serves both.

* Keyboard overview — the keyboard is the overview

A mode: zoom out and every window rearranges into QWERTY rows under letter
badges; press a letter to go to that window, shift+letter to pull-mark
several, RET gathers them where you started, ESC cancels. Expose, but the
spatial map is one your hands already know.

STATUS: BUILT, as =extensions/kbd-overview/=.  No new input plumbing — the
mode arms river's own chord capture by pushing a keymap of per-window
closures, re-arming itself after each pull-mark so multi-pick works.  Snap-
back swaps the saved original nodes back by reference.  Letter priority and
physical geometry are separate options, so either can change without the
other caring.
