#+SUBTITLE: The only document you need, and the reason there is only one

* The shape of the whole thing

Three layers, and you can stop reading after whichever one answers your
question.

| Tier | You write | Restart? | Example |
|------+-----------+----------+---------|
| *0* | a value | no | ~(setf *gaps* 8)~ |
| *1* | a method | no | ~(defmethod gaps ((p conventional-policy) c) 8)~ |
| *2* | a method plus state on ~props~ | no | remember which pane a cell was in |
| *3* | a new container or policy class | no | the whole lattice |

Nothing above needs a restart, a rebuild, or a plugin manifest. Everything can
be evaluated into the *running* window manager and takes effect on the next
frame.

* Ask the running window manager

Before reading anything, ask it. It knows more about itself than this file
does, and it cannot be out of date.

The binary answers without a running session, which is what you want while
writing a configuration file:

#+begin_src sh
latticewm --extension-surface   # every policy generic, with its contract
latticewm --container-surface   # every generic a new container kind answers
latticewm --list-options        # every value, with its default and what it does
latticewm --list-commands       # every command
latticewm --list-keys           # every binding
#+end_src

*There are two surfaces and they answer different questions.* The extension
surface is what the window manager *decides* — where a window goes, what a
border looks like, what a key means. The container surface is what it can
*hold*. Overriding a policy generic changes an answer; implementing the
container protocol adds a new kind of thing to have answers about. Almost
everything you will ever write is the first; =lattice/= is the second.

Both are generated from the running image, so neither can be out of date, and
both list the methods *you* have added — which is how you check that your
configuration file was actually loaded.

And a session that is already up, over the control socket — which is on by
default and needs no flag:

#+begin_src sh
latticewm --eval '(world-cursor *world*)'      # where focus is right now
latticewm --eval '(policy-name (current-policy))'
#+end_src

And from inside, ~describe~ works on everything:

#+begin_src lisp
(describe 'should-float-p)
(describe 'tree-move)
#+end_src

The docstrings are the specification. They were written to be read this way,
and several of them explain *why* a decision went the way it did — which is
usually the thing you actually need before overriding it.

* Where the configuration lives

=~/.config/latticewm/init.lisp=, plain Common Lisp, read in the
=LATTICEWM/USER= package — which inherits the model, the policy surface and the
runtime, so nothing needs a prefix.

#+begin_src sh
latticewm --write-config     # writes a commented starter file
#+end_src

An error in it is logged and startup continues. A window manager that refuses
to run because of a typo in its configuration leaves you with no way to fix the
typo.

* Tier 0 — values

#+begin_src lisp
(setf *gaps* 6)
(setf *border-width* 2)
(setf *focused-border-color* '(0.9 0.5 0.2 1.0))
(setf *terminal* "alacritty")
(setf *spawn-mode* :split)          ; :split | :fill-first | :stack
(setf *split-axis* :longer)         ; :longer | :horizontal | :vertical
(setf *focus-after-close* :stay)    ; :stay | :mru | :next
(setf *focus-follows-mouse* t)

;; The hardware.  On river nothing else on the machine configures it.
(setf *xkb-layout* "de")            ; what the keys do, for every application
(setf *tap-to-click* t)
(setf *repeat-rate* 50)
(setf *input-rules*                 ; per device, later rules winning
      '(("Touchpad" :natural-scroll t)
        ("Logitech" :accel-profile :flat)))
#+end_src

Every one of these exists because the design reached a fork where both answers
were defensible. DESIGN calls that P1 — "where a fork is situational rather
than principled, both options ship and configuration picks the default" — so
these are not preferences somebody guessed at, they are the places the design
declined to decide for you.

~latticewm --list-options~ lists all of them with their reasoning.

** Which wins, the option or the generic

Some options share a name with a generic — ~*gaps*~ and ~gaps~, ~*border-width*~
and ~border-width~ — and the relationship is always the same one: *the generic
is the extension point, and the option is what its shipped method returns.*
Change the option to change the shipped answer. Write the method to change the
decision. A policy that overrides the method stops reading the option, and
after that setting it does nothing.

You do not have to remember which options those are, and neither does this
page. ~latticewm --extension-surface~ prints a ~read by:~ line under every
option saying what in the running program looks at the value, and beneath it
the methods that win over that reader:

#+begin_example
*gaps*
  now: 0
  read by: gaps (layout-policy t)
  overridden for: gaps (layout-policy stack), gaps (lattice-policy grid)

*new-workspace*
  now: :empty
  read by: make-workspace (structure-policy t t)
  overridden by: make-workspace (lattice-policy t t)
#+end_example

That is an image with the lattice enabled, which is why the lattice is in it.
The copy of this document under =doc/EXTENSION-SURFACE.txt= is generated from
the core alone and shows only the core's own overrides — ask your own running
window manager to see yours.

#+CLAIM: (find "gaps (lattice-policy grid)"
#+CLAIM:       (mapcar #'option-shadow-name (option-shadows :gaps)) :test #'string=)
#+CLAIM: (find "make-workspace (lattice-policy t t)"
#+CLAIM:       (mapcar #'option-shadow-name (option-shadows :new-workspace)) :test #'string=)

~read by~ is asked of the compiler's cross-reference data and the two override
lines are asked of the generic function's method list, so all three are facts
about the image you are running rather than sentences somebody has to remember
to keep true. A policy *you* loaded appears in them, which is the point: this
is the answer to /I set it and my policy ignored it/.

The two labels say different things. ~overridden by~ is a method that wins
wherever the reader applied — under that policy the option decides nothing,
unless the method calls ~call-next-method~. ~overridden for~ is the same thing
narrowed to the argument classes it names, so ~*gaps*~ still reaches every
container that is not a stack or a lattice cell.

*And the same fact from the other end.* Everything above is printed under the
*option*, which only helps if you arrived at the question holding one. Most
people arrive holding a generic: you read the generics section, it says /to
change one, write a method/, and you write a method. So each generic whose
shipped method reads an option now says so, directly beneath its docstring:

#+begin_example
gaps (latticewm/policy:policy latticewm/policy::container)
----------------------------------------------------------------------------
Pixels of empty space to leave between CONTAINER's adjacent children.

Specialize on the container to vary it: zero inside a stack, larger between
lattice cells than between splits within a cell.

  answered from: *gaps*
  methods:
    (layout-policy stack)               ; layout.lisp
    (layout-policy t)                   ; layout.lisp
#+end_example

Read that as /you may not need a method at all/. Twenty-five of the sixty-six
generics carry the line, and for those the decision is already tier-0: set the
variable in your config file and the shipped answer changes. Write the method
when you want a decision that a single value cannot express — one that depends
on the container, the window, or what else is on screen — and know that your
method is then the reason the option stops being read, because it is the method
that was reading it.

The line describes the image you are running, so an extension's own option
appears on it. Load the lattice and ~gaps~ reads =answered from: *cell-gap*,
*gaps*= — the extension's knob, named where the generic it answers is. Each
name is spelled the way you would have to type it in a configuration file,
which is asked of the reader's package rather than assumed: ~*cell-gap*~ needs
no prefix because the lattice makes its names visible in =latticewm/user= when
it loads, and an extension that does not would appear here qualified. The copy
under =doc/EXTENSION-SURFACE.txt= is generated from the core alone and shows
only ~*gaps*~, for the same reason its override lines show only the core's.

An option that nothing reads is a failing build; so is an ~overridden by~ that
neither composes nor reads an option of its own — you may replace a shipped
answer wholesale, but not leave the person who was setting the option with
nothing to set; and so is an option named after a generic that no method on that
generic reads. The last one is why the shared name can be trusted rather than
merely observed: ~*gaps*~ and ~gaps~ are one relationship because gate 17 fails
the build on the day they stop being, and not because this page says so. The
lattice does replace ~make-workspace~ wholesale, and pays for it with
~*new-workspace-cells*~. See gates 11, 15 and 17 in
[[file:../PLAN.org::#gates-added][PLAN.org §gates-added]] for the option that
shipped wired to nothing, the one that shipped switched off, and the five whose
names were a claim nothing checked.

#+CLAIM: (member '*gaps* (gethash 'gaps (options-by-generic)))
#+CLAIM: (string= "*gaps*" (option-print-name '*gaps*))

* Tier 1 — methods

The whole of it:

#+begin_src lisp
(defmethod GENERIC ((policy conventional-policy) ARGS...)
  ...)
#+end_src

Three rules, and the third is the one that bites:

1. *Specialize on ~conventional-policy~*, not on a protocol class. The shipped
   defaults are on the six protocol classes ~policy~ inherits; yours must be
   more specific or it replaces rather than extends them.
2. *Use ~call-next-method~* when you mean "the usual thing, plus this". It is
   the common case.
3. *Do not reimplement the caller.* If you find yourself copying a shipped
   method in order to change three lines of it, the thing you want to change is
   probably its own generic. Look for it in ~latticewm --extension-surface~
   first.

** A worked one

Float two applications that get tiling wrong:

#+begin_src lisp
(defmethod should-float-p ((policy conventional-policy) (win window))
  (or (call-next-method)
      (member (window-app-id win) '("pavucontrol" "blueman-manager")
              :test #'equal)))
#+end_src

Paste it into a REPL and the *next* window obeys it. Nothing restarted.

** A second one, where a table cannot reach

~*input-rules*~ covers per-device settings and is what most people want. Write
the method when the decision is a *program* rather than a table — here, flat
acceleration for anything that is a drawing tablet, whatever it is called:

#+begin_src lisp
(defmethod input-settings ((policy conventional-policy) device)
  (append (when (eq :tablet (input-device-kind device))
            '(:accel-profile :flat))
          (call-next-method)))
#+end_src

Note the shape: your settings, then ~call-next-method~. A property named twice
takes the first, a property you do not name keeps the shipped answer, and a
property no device supports is skipped rather than sent. ~(reload-input)~
applies it to everything already plugged in.

** The generics worth knowing about first

| Generic | Question |
|---------+----------|
| ~layout-children~ | how does this container divide its rectangle? |
| ~step-address~ | where does motion go from here? |
| ~entry-address~ | arriving at a container, which child? |
| ~spawn-target~ | where does a new window land? |
| ~should-float-p~ | does this window float? |
| ~on-window-close~ | what happens to the pane when the window goes? |
| ~focus-after-remove~ | where does the cursor go after a close? |
| ~border-color~ / ~border-width~ / ~gaps~ | how it looks |
| ~key-unbound~ | typing in an empty pane |
| ~input-settings~ | how should this keyboard or touchpad be configured? |
| ~keyboard-layout-for~ | which xkb layout does this keyboard want? |

~latticewm --extension-surface~ prints every one with its contract and with the
methods that currently answer it — including yours, which is how you check that
your file was actually loaded. Do not count them from this table; ask. There
are sixty-six, and this table shows the dozen you are most likely to want.

** The six protocols

~policy~ is not one interface. It is a class that implements six, and the
shipped defaults live on the *narrow* ones:

| Protocol | What it answers |
|----------+-----------------|
| ~layout-policy~ | how a rectangle is divided, and what is shown |
| ~appearance-policy~ | colours, fonts, and what the status line says |
| ~motion-policy~ | where the cursor goes |
| ~structure-policy~ | where things go when the tree changes |
| ~lifecycle-policy~ | windows arriving, leaving, floating, minimizing |
| ~input-policy~ | what a key, a click or a drag means, and how the hardware that sends them is configured |

Which means a mixin that answers for *one* of them is a real thing you can
write, and it says what it is:

#+begin_src lisp
(defclass tall (layout-policy) ())

(defmethod layout-children ((p tall) (c split) rect)
  ...)

(defclass mine (tall conventional-policy) ())
(setf *policy* (make-instance 'mine))
#+end_src

~tall~ answers for layout and for nothing else. Before the split it would have
nominally implemented all fifty-eight generics, and every generic added to
~policy~ afterwards would have widened what it was answering for.

* Tier 2 — methods that need to remember something

Every node carries a ~props~ plist. Use it rather than adding a slot, because
adding a slot to a class you do not own is a fork.

#+begin_src lisp
(setf (prop node :my-extension/last-focused) 2)
(prop node :my-extension/last-focused)
#+end_src

Namespace your keys with a prefix. Two extensions using ~:last~ is a bug
neither author can see.

*A key you read must be written by something, and the build checks it.* This is
the one rule about ~props~ that is worth stating, because breaking it produces no
error of any kind: ~prop~ answers ~nil~ for a key nobody wrote, ~nil~ is a legal
value, and the branch behind the read simply never runs. That shipped twice here
— the lattice's ~clip-rect~ read a viewport bound nothing wrote, so the one
method standing for river's content clipping cropped nothing for its whole life,
and the core's ~render-order~ had a third render tier keyed on a property no node
was ever given. Gate 13 reads =src/=, =lattice/= and =examples/= and fails the
build on a key that is read and never written, which is what you will see if you
misspell one of yours in either place.

The converse is *reported* rather than failed: writing a key nothing in the tree
reads is exactly how you publish a fact for somebody else's status bar, and four
core properties are in that position deliberately. If you are the somebody else,
=make gates= prints the list.

* Tier 3 — new layout models

This is where the design stops being a window manager with settings and starts
being a substrate, and it is smaller than it sounds.

** A new arrangement: one method

=examples/03-master-stack.lisp= is dwm's layout — one large pane, everything
else stacked beside it — in one ~layout-children~ method and one
~step-address~ method. The tree is untouched; only the answer to "where do
these children go" changed. Switch back and every window is where you left it.

** A new *kind* of container: about sixty lines

=examples/04-scrolling-columns.lisp= is niri and PaperWM: an infinite
horizontal strip that scrolls sideways. It subclasses
~sequential-container~ — which supplies addressing, insertion and removal — and
answers three questions: how it is drawn, how motion crosses it, and where you
land arriving at it.

*Read that file before reading =lattice/=.* It is the same shape at a tenth of
the size, and the lattice is only larger because a plane has more data in it
than a strip does.

*** The list is the point

Run =latticewm --container-surface= and read it before you start. Six of the
members are obvious and the rest are not, and *a kind that answers only the
obvious six loads without complaint and then loses data*. That is not
hypothetical — it is what happened to a grid written with the source open, and
each of these was found the hard way:

| generic | what skipping it costs |
|---------+------------------------|
| ~copy-node-slots~ | undo and layout snapshots silently drop your children |
| ~serialize-node~ | every restart loses the arrangement, and the windows |
| ~deserialize-node~ | its other half; both or neither |
| ~node-signature~ | undo skips past the operation the user wanted back |
| ~default-address~ | focus repair lands somewhere that is not on screen |
| ~address-equal~ | ~eql~ is wrong the moment an address is not an integer |

Every one of them has a default on ~container~ that is correct for a dense,
integer-addressed container and wrong for anything else. That is what makes
skipping them silent rather than loud, and it is why the list is generated from
the image rather than written here: this table can go stale and the document
cannot.

If you subclass ~sequential-container~ rather than ~container~ — as the
scrolling-columns example does — the addressing half is already answered and
what is left is the state your kind adds. Answer ~copy-node-slots~,
~node-signature~ and the two persistence generics for that state and nothing
downstream will ever ask you about it again.

** What you get for free

The point of the container protocol is what you do *not* have to write. A new
container kind inherits, without being told:

- directional motion, including motion that crosses in and out of it;
- focus repair after any surgery anywhere in the tree;
- ~move~, ~swap~, ~pull~, ~send-to-workspace~ and every other structural verb;
- persistence, floating, minimize, fullscreen, tabs;
- being nestable inside any other container, including itself.

What you *do* have to write is on the container surface, and there is a check
standing over it: gate 2 requires every member of it to be documented, exactly
as it does for the policy generics, and gate 10 stops the core from working
around it with a ~typecase~. Between them, a kind that answers the protocol is
a first-class citizen of a program that has never heard of it.

* The lattice

An infinite two-dimensional plane of cells, each holding a split tree. It is a
separate system, and loading it is opt-in:

#+begin_src lisp
(asdf:load-system "lattice")
(lattice:enable :cols 2 :rows 2)
#+end_src

Your existing workspaces become planes with everything you had in cell (0,0),
and nothing is lost. ~(lattice:disable)~ goes back.

- Coordinates are integers, origin (0,0), *+Y is up*. This is deliberate and
  is not Wayland's convention; the lattice is a map and maps read that way.
- *Zoom is the choice of how many cells are visible* — 1, 2, 4, 6, 8 — which is
  the novel part. Zoom is normally a mode you enter and leave; here it is a
  continuous layout control.
- Motion runs straight through the cell boundary. Moving right from the
  rightmost pane of a cell lands on the leftmost pane of the cell to its right.
  There is no mode and no second command.
- ~*zoom-mode*~ picks how zoom makes room. ~:fit~ stretches the visible cells to
  tile the screen; ~:fixed~ gives a cell ~*cell-width*~ by ~*cell-height*~ pixels
  wherever it sits, scrolls the plane under the screen, and *crops the trailing
  cell at the edge* — river's ~set_content_clip_box~, with the border redrawn at
  the crop, which is the one thing in this program the compositor does for free.
  Resize a column and ~:fixed~ keeps it that many pixels wide however you pan;
  ~:fit~ will change every width on screen when you pan a plane with a resized
  column in it, which is the whole reason there are two.

Read =FINDINGS.org= for what building it cost, which is the most useful thing
this project has to say about its own design.

* Hooks, when you only want to notice

A generic decides *what happens*; one answer wins and the return value matters.
A hook notices *that something happened*; every function runs and nobody is in
charge. If you want a hook's return value, you wanted a method.

#+begin_src lisp
(defun note-the-window (win) (logmsg :info "opened ~a" (window-app-id win)))
(add-hook :window-opened 'note-the-window)
#+end_src

#+begin_src sh
latticewm --hooks    # every hook, what it is called with, and when it fires
#+end_src

*That list used to be typed here, and it was four names short.* It named
thirteen of the program's seventeen, missing ~:layout-restored~ — which is the
hook the lattice itself uses — and the three that report input devices, with
"~(all-hooks)~ is authoritative" underneath, which is a true sentence that only
helps somebody already at a REPL. There are eighteen, and the list is generated
from the running image now, like the other two surfaces, and installed beside
them as =HOOKS.txt=.

#+CLAIM: (= 18 (length (all-hooks)))
#+CLAIM: (every (lambda (row) (stringp (second row))) (all-hooks))

Two are worth naming here. ~:capture-changed~ is the only fact in the list your
own screen cannot show you: it fires with a window or an output and the number
of screen capture sessions now reading it, so a status bar, a keyboard light or
a script that mutes a microphone can follow a screen share without polling
anything. And ~:keyboard-focus-changed~ is the one a status bar showing the
focused window actually wants — ~:focus-changed~ reports the *cursor*, which is
a place, and focusing a floating window does not move it.

*The argument list beside each name is checked, in both directions.* Attaching
a function that cannot be called with them says so at the moment you attach it,
and a ~run-hooks~ inside the program that passes the wrong number fails the
build. Neither check existed while the lambda list in ~defhook~ was discarded,
and the failure it lets through is the quiet kind: hook functions run inside a
guard, so one of the wrong shape signals on every fire, is caught, and leaves
nothing behind but a line in a log file you do not have open.

*One hook's return value matters*, and it is the exception that proves the
rule. ~:reserve-space~ asks how much of an output to keep clear, each function
answers ~(TOP RIGHT BOTTOM LEFT)~ in pixels, and the answers are *added
together* — so two status bars each get their strip and the second does not
have to know about the first:

#+begin_src lisp
(defun my-bar-edges (output) (declare (ignore output)) (list 28 0 0 0))
(add-hook :reserve-space 'my-bar-edges)
#+end_src

That used to be a special variable outside the hook mechanism entirely, so the
program had two ways to hook and only one of them was documented or gated.

** Wrapping every command

Neither a generic nor a hook: *advice*. A function of ~(command arguments
thunk)~ that runs around every command in the system, including ones you wrote.

#+begin_src lisp
(defun time-commands (command arguments thunk)
  (declare (ignore arguments))
  (let ((start (get-internal-real-time)))
    (prog1 (funcall thunk)
      (logmsg :debug "~a took ~d ms" (command-name command)
              (round (- (get-internal-real-time) start) 1000)))))
(add-command-wrapper 'time-commands)
#+end_src

A session recorder, a modal layer that vetoes commands, and a per-command timer
are all the same shape.

*Layout undo used to be built on this and nothing else, and that was the wrong
altitude.* A command wrapper reaches exactly ~run-command~, and none of the
live-system doors go through it: ~eval-expression~ on =Super+;=, the control
socket, and SLIME all evaluate directly. So =Super+; (setf (world-root *world*)
(make-leaf))= destroyed a layout with no undo entry, while an arrow key
recorded a snapshot for a cursor move that changed nothing.

Undo is taken at the *settle points* now — the four places where a human or a
script has just done something arbitrary — and the test is what happened to the
tree rather than which function ran:

#+begin_src lisp
(note-layout-settled "opened a socket of my own")
#+end_src

If your extension opens a fifth door — a socket, a timer, a second REPL — call
that after it, and the layout changes made through it become recoverable like
everyone else's. It is cheap when nothing happened: one ~node-signature~ walk
and no copy at all. The command wrapper is still there and still covers every
command including yours; all it does now is *name* the step.

~(remove-command-wrapper 'time-commands)~ takes it off again, and you will want
it: a wrapper runs around *every* command, so the one you are still writing is
the one that can make the window manager stop responding to keys. Wrapping from
a REPL and unwrapping when it misbehaves is how this gets developed, and it is
the only way back out short of a restart.

*Give the function a name and add the symbol, not ~#'the-function~ and not a
lambda.* The list holds whatever you give it, and a function object is a
snapshot: redefining the function afterwards leaves the hook calling the old
one, and evaluating the ~add-hook~ again adds a *second* entry, because the new
object is not ~EQL~ to the old. A symbol has neither problem — it is looked up
when the hook runs, so redefinition takes effect, and adding it twice replaces
rather than accumulates.

This is not a style preference. It bit the shipped code: reloading the file
that draws the help screen left the old drawing winning, because both
generations were on the hook and the older one ran second.

* Keys

A binding names a command as a *string*, so redefining the command later takes
effect without rebinding the key.

#+begin_src lisp
(define-key *keymap* "Super+Return" '("terminal"))
(define-key *keymap* "Super+Shift+q" '("close"))

;; A chord.  River's ensure_next_key_eaten makes submaps exit cleanly on a key
;; they do not bind, so this behaves the way it does in Emacs.
(let ((window-map (make-keymap :name "window")))
  (define-key window-map "h" '("focus" :left))
  (define-key window-map "l" '("focus" :right))
  (define-key *keymap* "Super+w" window-map))
#+end_src

Both ~Super+x~ and ~C-x~ spellings parse. Punctuation needs its X11 name —
~bracketright~, ~comma~, ~minus~ — because ~Super++~ cannot be parsed.

New commands are ordinary functions with a docstring:

#+begin_src lisp
(defcommand center-window ()
  "Float the focused window and put it in the middle of the screen."
  (toggle-float)
  (relayout))
#+end_src

** Commands that take arguments

A command with parameters is reachable from ~M-x~ too: it is asked for them,
one prompt at a time. You do not have to say anything for this to happen — the
*name* of the parameter decides what kind of value it holds.

#+begin_src lisp
(defcommand nudge (direction pixels)
  "Move the focused float DIRECTION by PIXELS."
  (move-float direction pixels))
;; M-x nudge  ->  "nudge direction: " (completing over left/right/up/down)
;;            ->  "nudge pixels: "
#+end_src

~*argument-naming-convention*~ is the table, and it is a tier-0 value, so
adding to it is a ~setf~. Where a name is misleading, say so at the command:

#+begin_src lisp
(defcommand open-in (name)
  "Open the program NAME."
  (:interactive :shell-command)   ; not one of *our* command names
  (spawn name))
#+end_src

A new *kind* of value takes three lines. ~:candidates~ is a form evaluated each
time the prompt goes up, so it can name things that did not exist at load time:

#+begin_src lisp
(define-argument-type :monitor "monitor: "
  :documentation "One of the connected outputs, by name."
  :candidates (mapcar #'output-name (all-outputs))
  :parse (lambda (text)
           (or (find text (all-outputs) :key #'output-name :test #'string-equal)
               (error "no monitor called ~a" text))))
#+end_src

Two policy generics govern the prompt itself, and both are one method to
replace: ~complete-candidates~ decides how what you type is matched against the
candidates (the default is prefix, then substring, then subsequence), and
~argument-type-for~ decides the naming convention wholesale.

A key bound to a command with required arguments and given none *asks* for
them, so ~(define-key *keymap* "Super+g" '("goto"))~ is a sensible binding: the
key names the verb and the verb collects its own object.

* The development loop

This is the part the language was chosen for, so it is worth doing properly.

1. Start the window manager. The control socket is already there: a Unix socket
   in =$XDG_RUNTIME_DIR=, mode 0600, on by default.
2. Evaluate into it with =latticewm --eval=, from a shell, a script, or an agent.
3. Watch. Correct. Evaluate again.

#+begin_src sh
latticewm --eval '(setf *gaps* 20)' --eval '(relayout)'
latticewm --eval '(defmethod border-width ((p conventional-policy) node focused)
                    (if focused 6 1))' --eval '(relayout :force t)'
#+end_src

*SWANK is off by default and you have to ask for it.* It is a TCP server
offering arbitrary code execution with no authentication step, which is right
for a development tool and wrong for something that starts before you have done
anything, so it is opt-in and binds to loopback:

#+CLAIM: (null (option-default :swank-port))
#+CLAIM: (eq t (option-default :ipc-socket))

#+begin_src sh
latticewm --swank-port 4005      # or (setf *swank-port* 4005) in init.lisp
#+end_src

With it running, ~M-x slime-connect~ from Emacs gets you the full editor
integration — completion, the inspector, and a backtrace you can restart from —
which is worth the flag for a session you intend to spend the afternoon in. The
socket is what to reach for otherwise: it needs no flag, no editor and no Lisp
on the far end.

Two things to know:

- ~relayout~ is safe from any thread. Called outside a protocol sequence it
  defers to the next one rather than emitting illegally.
- Anything else that touches the compositor should go through ~in-wm~, because
  the Wayland client is single-threaded. Redefining a method never needs it.

*And the discipline that comes with it:* anything you redefine live and do not
write back into your config is gone at the next restart. The REPL is a
workflow, not a free feature.

* When something goes wrong

A bad method logs and the window manager keeps running. That is the whole point
of the condition system here: an unhandled error in a compiled window manager
unwinds and takes your session with it, and here the socket is still open, the
tree is intact, and you can fix the function from inside the desktop it is
misplacing windows in.

#+begin_src sh
latticewm --eval '(world-cursor *world*)'    # where does it think focus is?
latticewm --eval '(length (all-windows))'    # what does it think it is managing?
latticewm --log-level debug
#+end_src

If you see ~SEQUENCE-VIOLATION~, you have called a protocol request from the
wrong context. The message names the request and what it needed. It is a
*continuable* error, so at a REPL you can send it anyway and see what river
does — which is how two of the bugs in this project's history were diagnosed.

* The rules the core will not let you break

Recorded so you do not spend an afternoon trying.

- *The manage/render discipline.* Protocol law. The wire layer enforces it and
  the enforcement is correct.
- *Scaling.* There is no scaling primitive anywhere in river's protocol — no
  scale, no transform, no matrix. "Zoom out" cannot mean "draw the same windows
  smaller"; it can only mean "give every window smaller dimensions". Everything
  about how zoom works follows from this and none of it is a choice.
- *Focus is a place, not a window.* Structural. Everything downstream assumes a
  cursor into the tree exists. Every behaviour you would want from the
  window-model is reachable as policy on top of this one; the reverse is not.

* If you change this page

Every sentence here is a claim about a program that moves, and this page has
been wrong before: its development loop opened with "SWANK is listening on port
4005" for as long as it took somebody to read it after SWANK was turned off by
default, with eleven build gates passing the whole time.

So gate 12 reads this file. Two things follow for anyone editing it.

*Every earmuffed name you write in code markup has to be a real option.*
Automatic; you do not have to do anything. Name one the program does not have
and the build fails with the line number. This also means you cannot use an
earmuffed placeholder — write "an option" rather than a fake one — which is a
small cost and the reason the check has no false positives to argue with.

*Any sentence can be pinned to the running program with one line.* A =#+CLAIM:=
keyword holds a form, which is read in ~latticewm/user~ — the same package your
configuration file is read in, so it says what you would say — and evaluated
against the loaded image on every build. NIL fails, naming the file, the line,
the form, and the sentence above it.

#+begin_example
There are sixty-six policy generics.
#+CLAIM: (= 66 (length (policy-generics)))
#+end_example

Consecutive =#+CLAIM:= lines are one run, and every complete form in the run is
one claim, so a long one can be spread over several lines. The form has to
name something the program owns — ~#+CLAIM: t~ is itself a failure, because a
gate that can be told it passes is not a gate.

It cannot catch a false sentence nobody pinned, and nothing honest could. What
it does is make the pinning cost one line, so the sentences that carry a number
or a default can stop being promises.
