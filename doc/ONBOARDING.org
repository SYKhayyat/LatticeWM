#+TITLE: Onboarding — contributing to LatticeWM
#+OPTIONS: toc:2 num:nil

This is the guide for somebody who wants to change *this repository*. If you
want to change *your own window manager* without touching this repository —
which is what most people want, and what the whole design is arranged around —
read [[file:EXTENDING.org][EXTENDING.org]] instead. The two guides do not
overlap much on purpose: one is about the machine, the other is about the
seams the machine exposes.

[[file:../CONTRIBUTING.md][CONTRIBUTING.md]] is the short version of this page,
and it is the one to read if you are opening a single pull request today. This
one is for the second week.

* Why this is not shaped like the window manager you were expecting

If you have used Emacs or StumpWM you already have the thesis: *the running
system is the editable system.* There is no plugin API, no reload command and
no manifest, because there is no boundary to have one across. You attach to a
live session, you evaluate a ~defmethod~, and the next frame is drawn by the
method you just wrote. The window manager you are changing is the one currently
holding your windows.

That is the whole reason the project exists, and everything awkward about
contributing to it follows from taking it seriously.

** The bargain, stated once

Every claim this project makes about itself is supposed to be attached to
something that runs. That is why there is so much machinery for a window
manager: twenty-two build gates, a unit suite, an integration suite that drives
a real compositor, six references generated from the running image, and a set
of checks over the prose itself.

The reason is not rigour for its own sake, and it is not taste. *A program you
edit while it is running has no compile-and-ship moment where somebody notices
the documentation went stale.* Emacs solves this with ~C-h f~ and the
convention that every function carries its own paragraph — the documentation
lives in the image, so it cannot drift from it. This project takes the same
bet: the keymap overlay is drawn from the live keymap, ~--extension-surface~ is
generated by asking the image, and =doc/*.txt= is that output committed.

The gates are what replaces the moment you lost. They are the price of the
feature, and if you find yourself resenting one, that is the trade to argue
with rather than the gate.

The practical consequence for you is that *the machinery will run on your
branch and some of it will refuse things that feel arbitrary.* Every one of
those refusals exists because something rotted silently once. Each gate prints
why it exists before it prints what is wrong with your change. If one of them
does not, that is a bug in the gate and worth its own issue.

* Day one

** Get it building

#+begin_src sh
git clone https://github.com/SYKhayyat/LatticeWM.git
cd LatticeWM
./bootstrap.sh          # fetches the dependencies into .deps/; idempotent
make                    # build, and the gates
make test               # the unit suite
#+end_src

=bootstrap.sh= needs SBCL and an internet connection, once. It installs a
pinned Quicklisp dist *inside the project* under =.deps/=, so it never touches
a Quicklisp you already have and nothing outside the checkout changes. It is
safe to run again.

If SBCL is missing, =bootstrap.sh= prints the install line for your
distribution rather than a shell error. If it is too old, it says so and names
the number — which it reads out of =latticewm.asd= rather than keeping a copy.

** The one command that matters

#+begin_src sh
make check
#+end_src

That is build, gates, unit suite and the integration suite against a real
headless river. It is what CI runs and it is what to run before pushing. It
*fails* rather than skips when river or a terminal emulator is missing —
~REQUIRE_INTEGRATION=0~ forgives that, and you should know why you are asking.

If =make check= is green on your machine it will be green on ours. That is a
stronger promise than it sounds, and it is worth knowing where it comes from:
the generated documents are byte-identical across every SBCL the project
supports, so "it passed here" is not a statement about your compiler.

** What you now have

=make= leaves fasls in =~/.cache/common-lisp= and nothing in the tree.
=make image= dumps =./latticewm=, a single compressed executable of about 13
MB, which is the thing a user installs. =make image-fast= is the same
uncompressed — much larger, a fraction of a second faster to start, and for the
edit loop only. Nothing installs it.

* The development loop

River is a wlroots compositor and wlroots has a Wayland backend, so *river
runs inside the session you are already in, in a window*. That is the entire
development setup: your editor on one side, river-in-a-window on the other, and
no second machine.

#+begin_src sh
make run       # builds image-fast, then starts river with LatticeWM inside it
#+end_src

This also works under WSLg, which is worth saying because it is not obvious:
WSL with a Wayland session gives you a nested river and a real LatticeWM, and
the integration suite runs there unmodified.

** Editing it while it runs

This is the part worth setting up properly on day one, because once you have it
the rest of the loop stops involving =make= at all.

A dumped image keeps the compiler — this is StumpWM's shipping model and it is
proven — so ~defmethod~ against a live session works, and the effect is visible
on the next frame. Not a party trick: it is the development loop, and it is why
the whole extension surface is generic functions rather than a callback table.

SWANK is *off by default*, deliberately. An unauthenticated
arbitrary-code-execution port, opened before the user has done anything, is not
a default — and the day it was turned off, the first line of the extension
guide became false and eleven gates passed anyway, which is the story gate 12
exists because of. Turn it on for a session:

#+begin_src sh
latticewm --swank-port 4005
#+end_src

Then ~M-x slime-connect~ (or SLY's equivalent) and redefine things against a
running desktop. Recompiling one function with ~C-c C-c~ is the inner loop;
=make= is for when you have changed something the image cannot patch, like the
package definitions.

A word on why this is safe enough to rely on: unhandled conditions do not take
the session with them. Every event handler runs inside a restart, and the top
level installs a debugger hook, because a window manager sitting at a ~0]~
prompt on a terminal nobody is reading — holding an unfinished manage sequence
while the desktop freezes — is the single worst failure mode available to this
class of program. So a broken method you just wrote costs you a log line, a
backtrace naming your method, and one badly-placed window. Then you fix it at
the same REPL, which is the entire point.

Set =*debug-on-error*= when you want the condition to reach SLIME instead, with
the real stack and the restarts — including ~ABANDON~, which is almost always
the one to pick. With nothing attached, that option will exit the window
manager on the first error, which is why it is off.

If you would rather not attach a REPL, there is a control socket:

#+begin_src sh
latticewm --eval '(print (world-root *world*))'
latticewm --eval '(setf *gaps* 24)'
#+end_src

=--eval= talks to an *already-running* LatticeWM. For a layout or focus bug,
printing the tree is usually the whole diagnosis.

** Asking the program instead of reading the source

Emacs's real advantage over everything that copied its keybindings is not the
bindings — it is that you can always ask. This is the same idea pointed at a
program with nowhere to print: every one of these is generated by interrogating
the running image, so none of them can be out of date, including for things you
defined five minutes ago at a REPL.

#+begin_src sh
latticewm --extension-surface   # every policy generic, its docstring, what reads it
latticewm --container-surface   # every generic a new container kind must answer
latticewm --list-options        # every value you can set, with its default
latticewm --list-commands
latticewm --list-keys
latticewm --hooks
#+end_src

=make surface= writes the same six documents into =doc/=. Never edit those by
hand; run the target and commit what it writes.

* The map

#+begin_example
src/model/       the tree, geometry, paths, windows — no compositor, no policy
src/policy/      every decision, as a generic with a shipped method
src/runtime/     everything that talks to river or owns mutable state
src/wire/        the generated protocol bindings and the one door to them
src/protocol/    vendored river and wayland XML, plus PINNED
lattice/         the shipped extension: an infinite plane of cells
examples/        five worked extensions, loaded and exercised by the suite
tools/           the build, the gates, the image, the integration suite
tests/           the unit suite
doc/             prose, plus the six generated references
#+end_example

The layering is load-bearing and three gates defend it:

- *=src/model/= knows nothing about a compositor.* It is a tree and some
  rectangles. Almost everything in the unit suite lives here because almost
  everything here can be constructed.
- *=src/policy/= is where decisions live*, one generic per decision, each with
  a shipped method. This is the surface an extension specialises. Gate 20
  refuses a method in =src/policy/protocol.lisp= — that file declares generics
  and nothing else.
- *=src/runtime/= is what cannot be a decision*: the event loop, the manage
  sequence, surfaces, the socket.
- *=src/wire/= is the only place allowed to call a protocol request.* Gate 22
  refuses one from anywhere else. If you need a new request, add an alias in
  =src/wire/wrappers.lisp= and call that.

The rule that generates most of the others: *if it is a decision, it is a
generic in =src/policy/=; if it is a mechanism, it is in =src/runtime/=.* When
you are unsure which you are writing, you are usually writing a decision.

* The instruments, and what each cannot see

There are five, and they are pointed at different things on purpose. Knowing
which one *could* have caught a given bug is the fastest way to know where a
new check belongs.

| instrument | asks | cannot see |
|---|---|---|
| gate 1 (=tools/build.lisp=) | does it compile with zero warnings | anything about behaviour |
| gates 2–22 (=tools/gates.lisp=) | is the *image* self-consistent | anything that needs a compositor |
| the unit suite (=tests/=) | is a constructed state handled right | anything it cannot construct |
| the integration suite (=tools/integration.lisp=) | does a real river agree | anything a headless backend has no hardware for |
| =make surface= + =git diff= | do the generated documents still match | prose nobody generated |

Two things follow from that table and both have cost this project something:

*A check that constructs its own input can only ever confirm the constructor.*
The integration suite exists because of this. It receives state from a
compositor rather than building it, and the first time it ran it found that
pointer bindings had been enabled through the keyboard interface — a type error
inside a generated marshaller, caught, logged, and completely silent. Super+drag
had never worked.

*A gate whose scope is unstated is a gate people stop reading.* Gate 1 says
"zero compiler warnings" and for a long time compiled =src/= and =lattice/= and
nothing else, while the build printed a warning from =examples/= on every run.
It compiles the examples now. If you add a directory of Lisp that nothing
loads, put it in front of gate 1 the same way.

* Making a change: what each kind obliges you to do

This is the part worth skimming before you start, because the obligations are
enforced and they are not all obvious.

** Adding an option

An option is =define-option=, a default and a docstring. Three gates then have
something to say:

- *Gate 11* refuses an option nothing reads. A knob wired to nothing is worse
  than a missing feature, because the documentation agrees with the user that it
  should have worked. This is not hypothetical — it shipped, for the whole life
  of one option, under a completely green build.
- *Gate 17* refuses an option named after a generic that is not that generic's
  shipped answer. If there is a =gaps= generic and a =*gaps*= option, they are
  one relationship or they are a trap. Five pairs share a name today, and the
  rule they all obey is: /the generic is the extension point, the option is what
  its shipped method returns./ Nothing stronger than habit made that true, until
  the gate asked — move the read into a helper, or answer the option from a
  different generic, and a user reads ~gaps~, sets =*gaps*=, and is wrong for a
  reason no instrument could see.

  #+CLAIM: (let ((by-generic (options-by-generic)))
  #+CLAIM:   (every (lambda (g) (member (find-symbol (format nil "*~a*" (symbol-name g))
  #+CLAIM:                                          '#:latticewm/policy)
  #+CLAIM:                              (gethash g by-generic)))
  #+CLAIM:          '(gaps border-width keys-hint move-into-occupied new-child-side)))
- *Gate 15* refuses a method that overrides away the only reader of an option
  without offering an option of its own. There is always a knob, even when it is
  not that one.

The docstring should say what turning it off *costs*, not what it does. Read a
few of the shipped ones; they are the house style and they are the thing
=--list-options= prints.

** Adding a command

=defcommand=, with a docstring, because gate 2 will refuse it without one. The
docstring is not a label — it is what the help overlay draws, what =apropos=
searches, and what =describe-command= shows. Write the paragraph.

If the command takes required arguments it can still be bound to a key: a
binding with no arguments asks for them interactively rather than failing.

** Adding a generic — the extension surface

This is the important one, because a generic is a promise to strangers.

- Gate 2 wants a docstring.
- Gate 16 refuses an export nothing reaches. *Export the symbol in the same
  commit as the thing that uses it* — a test, a caller, or a document. An
  export with no reader is a promise with nothing behind it, and this project
  has shipped three of those.
- Gate 6 measures how much behaviour is answered from *outside* =src/=, and
  prints two numbers: with the lattice and without it. The second one is the
  uncomfortable one and it is the one to argue with.

Write the shipped method as the default, and say in the docstring what a
specialising method is for. If your generic reads an option, that is the tier-0
path and it should be documented as such — the generated surface prints both
halves of that relationship automatically.

** Adding a hook

Declare it and run it. Gates 7 and 14 close the loop from both ends: a hook
declared and never run fails, a hook run and never declared fails, and a hook
nothing has ever attached to fails. Fourteen of seventeen hooks had never been
attached to by anything, which meant their contracts — the arguments they pass
and the moment they fire — were guesses. Three were wrong.

** Adding a container kind

Read =latticewm --container-surface=, then =lattice/= as the worked example.
Gate 10 refuses a =typecase= on a container class anywhere in =src/=: the core
dispatches through the container protocol or it does not dispatch. Gate 13
refuses an extension property written and never read, or read and never written.

** Touching the protocol

=src/protocol/= is vendored XML and =PINNED= is the record of where it came
from. Gate 5 holds the generated bindings to it. Re-vendoring is how features
are picked up, not how installation is survived — the program accepts a *range*
of river versions, so a newer river is a supported configuration.

=make revendor-check= asserts that a build vendored at a version the program
cannot speak refuses by name rather than misbehaving.

* Running against a real compositor

=make integration= drives a real river on a headless wlroots backend, as an
ordinary Wayland client. It needs river and a terminal emulator on =PATH=.

#+begin_src sh
make integration                      # forgiving: skips with a message
make check                            # strict: a missing river is a failure
RIVER=/usr/bin/river make integration # pin which river to test against
#+end_src

*Test both ends of the version range if you can.* The program binds the
protocol at the version its vendored XML declares and accepts compositors from
a declared floor upward. Those are two different promises:

- against the *floor*, the question is whether every request this program sends
  is one an older river understands;
- against the *ceiling*, the question is whether every event this program binds
  for is one it can actually decode.

Only the first was ever in doubt out loud. The second is the one that fails
silently. If you have two rivers installed, the ~RIVER~ variable above makes
running both a one-line difference.

The suite sorts what did not happen into three categories and they are not
interchangeable: *skip* (a headless backend has no such hardware), *missing* (a
dependency is not installed), and *old* (this river predates the feature). Only
the last is fixable by upgrading, so it says so separately.

* More than one compiler

The declared minimum SBCL lives in =latticewm.asd=, in one place, and
=bootstrap.sh= and the CI floor job both read it back out of that file rather
than keeping a copy.

That number was wrong once, and the way it was wrong is the most useful story
in this repository. The floor was declared, a CI job was built specifically to
test it, that job failed on thirty consecutive runs — and nobody read it. The
failure was four tests dying on an unbound variable before reaching an
assertion, caused by a *test helper* whose body referred to a variable bound
only after the body ran. Newer SBCL deletes that reference because its value is
discarded; older SBCL does not.

So: the instrument existed, was pointed at exactly the right question, and was
reporting a defect in itself. That is the failure mode *after* the one the gates
were designed against, and the only defence is reading the red.

If you change anything in =tests/=, in =tools/build.lisp=, or in how the
generated documents are produced, run it on more than one SBCL before you push.

* The prose is code too

This is the part that surprises people. Gate 12 checks the documents:

1. *Every prose file is classified.* A new =.org= in the root or in =doc/= must
   be declared *current* (it describes the program as it is, and a false
   sentence in it is a bug) or *historical* (a dated record, frozen on purpose)
   in =tools/gates.lisp=. Arriving unclassified is the one thing a document may
   not do, because that is how a document goes unread.
2. *Every earmuffed name a current document mentions in code markup or a source
   block must be something the program actually has.* This is the check that
   exists because an option was documented as working in three places while
   nothing read it.
3. *Every earmuffed name a docstring mentions must too.*
4. *A =#+CLAIM:= line makes a sentence executable.* It is an org keyword, so it
   does not render, and the form it holds is evaluated against the loaded image
   on every build. NIL fails the gate, naming the file, the line, the form and
   the sentence above it. =README.org= pins its key tables this way and
   =doc/EXTENDING.org= has the worked description; copy one of those rather
   than a shape from here, because a claim in a document is a live thing and an
   example of one in another document is not.

   Claims are read in the same package a configuration file is read in, so a
   claim can only say what a user could say. That is the right constraint: it
   keeps them inside the surface the documents describe, and it means any of
   them can be pasted into a running session and watched. A claim that consults
   nothing fails on principle — a gate that can be told it passes is not a gate.

*The frozen documents.* =DESIGN.org=, =PLAN.org=, =ASSESSMENT.org= and
=SPIKE-WEEK0.org= are records of what was decided and when. Do not edit them
into agreement with what shipped — that destroys their only value. =DESIGN.org=
contains a row reading /"Overturned by D22, in this document"/, which is what an
unlaundered record looks like. If one is wrong about the program today, the fix
is a new note saying so, a =#+CLAIM:= line, or a change to the program.

*Do not write a number in prose that nothing checks.* A count repeated in two
files is a count that will come to disagree with itself; this project has
watched it happen four times. Either attach a =#+CLAIM:=, or write the shape
instead of the number.

* The house style, which is not a style guide

Two conventions, and both are load-bearing rather than cosmetic. Nothing
enforces them except review, and they are the reason the tree reads the way it
does.

** Docstrings are paragraphs, because they are the interface

A docstring here is not a label. It is what ~describe-command~ draws on screen,
what ~apropos-command~ searches, what the help overlay shows next to the key,
and what =--extension-surface= prints. It is the documentation, not a note
about it.

So: say what the thing is *for* and what choosing differently *costs*. An
option's docstring should tell somebody what they lose by turning it off. A
generic's should say what a specialising method is for and what it will break.
Compare a few shipped ones before writing your first; they are long on purpose
and they are the reason a stranger can use the system without reading =src/=.

The corollary, which is the part people find odd: *the discoverability
commands are the interface, and the source is the fallback.* =Super+/= draws
the whole keymap. ~M-x~ completes over every command. ~apropos~ searches the
docstrings, so "screen" finds ~toggle-fullscreen~ though the word is not in its
name. If a thing you added cannot be found that way, it is not finished.

** Comments argue, they do not restate

The comments in this tree are unusually long and they are almost never
descriptions of what the code does. They are the *argument* — what was tried,
what broke, why the obvious shape is wrong, and what a future reader would
otherwise repeat.

That is deliberate and it is the project's answer to a real problem: the
reasoning has to outlive whoever had it. A comment saying "increment the
counter" is worth nothing. A comment saying "this is a HANDLER-BIND and not a
HANDLER-CASE, because HANDLER-CASE unwinds before the handler runs and the
backtrace is then this macro's own frames" has just saved somebody an
afternoon, and that comment is in the tree because it did not exist and the
afternoon was spent.

When you write a comment here, write the thing you would have wanted to know
before you started. If you fixed a bug, the comment records the bug, not the
fix — the fix is in the diff and the bug is not.

* Sending it

- *Commits explain /why/, at length when the reason is not obvious.* The git
  log here is documentation. Read a few before writing one.
- *=CHANGELOG.md=, under =## Unreleased=*, for anything a user or a packager
  would notice.
- *One concern per pull request.* A branch that fixes a bug and reformats a
  file costs the reviewer the ability to see either.
- *New behaviour needs a test*, and new behaviour on the extension surface
  needs a docstring, because gate 2 will not let it through without one.
- *Run =make check= first.* All of CI is reachable from your machine except
  the nix build, and a red gate reads better locally than in a log.

* Things that will trip you, in the order they usually do

1. *Gate 16, on your first export.* Export in the same commit as the caller.
2. *Gate 12, on your first new document.* Classify it in =tools/gates.lisp=.
3. *Gate 22, on your first protocol call.* Add a wrapper in =src/wire/= and
   call that.
4. *The generated documents.* If you changed a docstring, an option or a
   generic, run =make surface= and commit the diff. CI regenerates and diffs
   them, so forgetting shows up as a failure in a file you did not edit.
5. *=make -j=.* Nothing here is safe under parallel make; the Makefile says so.
6. *A gate that fails in a file you did not touch.* That is usually correct and
   usually means a document, an export or a generated file now disagrees with
   the program. Read the gate's paragraph before assuming it is confused.

* If you change this page

It is a *current* document, so its sentences are checked and a false one is a
bug. It is also the page a second contributor reads before they know enough to
doubt it, which is the argument for keeping it shorter than it wants to be.
