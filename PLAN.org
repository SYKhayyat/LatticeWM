* What changed from DESIGN's plan, and why
:PROPERTIES:
:CUSTOM_ID: deltas
:END:

Three deltas. Each is a reversal of a decision in DESIGN.org and is recorded here rather
than quietly applied, per that document's own standing rule.

** Delta 1 — the conventional layer and the lattice share one geometry
:PROPERTIES:
:CUSTOM_ID: delta-1
:END:

DESIGN's [[file:DESIGN.org::#plan][§plan]] builds split trees twice: as the whole layout
model in week 2, then as cell contents in week 3. That is the same code written twice
under a budget that cannot afford it once.

*A cell boundary and a split boundary are the same thing seen twice.* A split separates
two subtrees, reached by ~:a~ / ~:b~. A cell separates two subtrees, reached by
~(x±1, y)~. Nested versus indexed. Nothing else differs.

The consequence that makes it worth doing: *directional motion is continuous across the
boundary.* Move left from the leftmost leaf of cell ~(0,0)~ and you arrive at the
rightmost leaf of cell ~(-1,0)~. No mode, no separate command, no discontinuity in the
user's model. Emacs's ~windmove~ and lattice cell motion are one verb with one
implementation.

So: build cells-holding-trees on day one. Ship with a single cell at ~(0,0)~ and the
viewport locked at 1×1, and it *is* a conventional tiling window manager. Unlock
coordinates and zoom and it is the lattice. Same code, extended, not ported.

** Delta 2 — D21's experiment becomes a daily CI check, not a week-3 milestone
:PROPERTIES:
:CUSTOM_ID: delta-2
:END:

[[file:DESIGN.org::#d21][D21]] holds: the lattice must be expressible without core
surgery, and if it cannot be, *that is the finding*. What changes is when you learn it.

Under D21 as written you learn in week 3, which under this budget may not happen, so the
experiment that justifies the whole sequencing never runs.

Instead: *the lattice lives in a separate ASDF system* that depends only on the core's
exported policy package. Core loads, starts and runs with the lattice absent. Any core
edit the lattice demands shows up as a failing gate, on the day it happens, from day
one. See [[#gates][CI gates]], gate 3.

This keeps D21's falsifiability and removes its scheduling risk. It costs nothing.

** Delta 3 — the cut list guts D22's own mitigations, so D22 flips
:PROPERTIES:
:CUSTOM_ID: delta-3
:END:

[[file:DESIGN.org::#d22][D22]] (exact-fit zoom) accepts, as a stated price, that *panning
resizes every visible window* on a non-uniform lattice. Terminals rewrap, browsers
reflow. Pan is the frequent navigational verb, and
[[file:DESIGN.org::#d7][D7]] sells it as pure view control.

D22's own escape hatch: both width solvers ship as two methods on one generic.

*Ruling: ~absolute-with-clipping~ (the old D11 behaviour) is the shipped default;
~exact-fit~ is the alternate method.* [[file:DESIGN.org::#feasibility][§feasibility]]
already established that ~set_content_clip_box~ renders the partial trailing cell
cleanly, with the border redrawn at the clip edge, free, from the compositor. D22 traded
a cosmetic problem that the compositor solves for a functional one that it does not.

This is a one-line default change, not a redesign, and it is reversible by config.

** Module map

#+begin_example
latticewm.asd              ; core system
lattice.asd                ; the extension. depends on LATTICEWM/POLICY only.

src/
  package.lisp
  protocol/
    river-window-management-v1.xml   ; vendored, pinned
    river-xkb-bindings-v1.xml        ; vendored, pinned
  wire/
    sequence.lisp    ; *sequence*, check-sequence, with-manage/with-render
    wrappers.lisp    ; macro-generated wrapper per generated request (all 68)
    dispatch.lisp    ; event loop; handler-case on wl-message-error
    session.lisp     ; connect, bind globals, SWANK thread, *debugger-hook*
  model/
    tree.lisp        ; node / leaf / split. pure surgery, no protocol.
    space.lisp       ; coordinate -> cell map. one cell is the degenerate case.
    focus.lisp       ; the cursor, and the one focus-repair function
    geometry.lisp    ; (tree, rect) -> list of (leaf . rect). pure.
  policy/
    protocol.lisp    ; DEFGENERIC ONLY. docstrings mandatory. no methods.
    conventional.lisp; the default methods. the shipped behaviour.
  runtime/
    emit.lisp        ; placements -> set_position / propose_dimensions / order
    windows.lisp     ; window lifecycle, identifier bookkeeping
    keys.lisp        ; xkb bindings, keymap, submaps
    commands.lisp    ; the command registry
  config.lisp        ; loads ~/.config/latticewm/init.lisp

lattice/
  policy.lisp        ; methods on the same generics. coordinates, viewport, zoom, pan.
  commands.lisp
#+end_example

Two rules, and they are the project:

1. *~src/policy/protocol.lisp~ contains no methods.* Generics and docstrings only. It is
   the extension surface, and it is a file you can read in one sitting.
2. *Nothing in ~lattice/~ may edit anything in ~src/~.* Enforced by gate 3.

** The policy surface
:PROPERTIES:
:CUSTOM_ID: generics
:END:

This is the whole extension contract. It is deliberately small; a surface nobody can
hold in their head is not a surface.

| Generic | Question it answers |
|---------+---------------------|
| ~place (policy node rect)~ | how does a subtree divide its rectangle? |
| ~move-focus (policy cursor direction)~ | where does motion go, including across cells? |
| ~resolve-entry (policy container direction)~ | arriving at a container, which leaf? ([[file:DESIGN.org::#d20][D20]]) |
| ~spawn-target (policy cursor)~ | where does a new window land? ([[file:DESIGN.org::#d14][D14]]) |
| ~on-window-open (policy window)~ | tiled or floating? focus it or not? |
| ~on-window-close (policy cursor node)~ | collapse or clear; where does focus go? ([[file:DESIGN.org::#d17][D17]]) |
| ~should-float-p (policy window)~ | the floating rule |
| ~on-minimize (policy window)~ | minimize semantics, ours entirely |
| ~visible-region (policy viewport)~ | what is shown, what is ~hide~-den |
| ~column-widths (policy visible-range viewport-w)~ | absolute-with-clipping vs exact-fit ([[#delta-3][Delta 3]]) |
| ~window-dimensions (policy leaf rect)~ | ~propose_dimensions~, and gravity when refused |
| ~render-order (policy nodes)~ | the ~place_above~ chain |
| ~key-unbound (policy cursor keysym)~ | typing in an empty pane ([[file:DESIGN.org::#d19][D19]]) |

Thirteen. If this list reaches thirty, the decomposition has gone wrong in the direction
of ceremony. If it drops below ten, it has gone wrong in the direction of a monolith.

* What extensibility is actually worth here
:PROPERTIES:
:CUSTOM_ID: extensibility-real
:END:

Added 2026-07-30, after pressing on the question honestly. This section is the rationale
for gate 6, for the SWANK bridge in [[#phase-4][Phase 4]], and for how the worked
examples are framed. DESIGN argued the language decision on *human* extensibility and got
a thin margin. The real requirement is different and the margin is wider.

** The Emacs mechanism is a ratio, not a language

Lisp is not what kept Emacs alive. *The ratio is.* Emacs is roughly 1.3 to 1.4 million
lines of Elisp on about 400,000 lines of C. The overwhelming majority of the system is
written in its own extension language, and three things follow:

- Every feature is a worked example of how to write a feature.
- Anything you want to change is already written in the language you would change it in.
- The extension surface is not documented, it is *demonstrated*, a million lines over.

Vim has Vimscript and is not Emacs. Neovim has Lua and is not Emacs. Hyprland has Lua as
of 0.55 and is not Emacs. In all three the core is C or C++ and the scripting sits on
top. The boundary is not the disease. *How little of the system lives above it* is.

*Therefore the load-bearing metric is the runtime-to-policy line ratio*, and it is
checked continuously rather than discovered at the end. See gate 6.

| Shape | Runtime | Policy | Meaning |
|-------+---------+--------+---------|
| Emacs shape | ~500 | ~1,500 | the language bought something real |
| Vim shape | ~2,000 | ~200 | CLOS paid for, nothing received |

*The compounding took Emacs decades and this project has fifteen days.* What gets built
here is the seed, not the advantage. Whether it compounds is entirely a function of other
people and cheap AI, which is why [[#phase-4][Phase 4]] is not cuttable.

** The real requirement: a cheaper AI must be able to extend it

Not "Shaul edits a ~defparameter~." The post-expiry maintainer is a weaker and cheaper
model, plus whatever contributors the release attracts. That is a different set of
properties from human extensibility, and Common Lisp scores differently on them.

| What a weak model needs | Common Lisp | Compiled + plugin API |
|-------------------------+-------------+------------------------|
| Context per change | one docstring, one ~defmethod~ | the trait, its types, the boilerplate |
| …when the change is *not* covered by the surface | still one ~defmethod~ | read core, edit core, rebuild |
| Additive vs invasive | new file, zero core diff | additive inside the API, surgical outside |
| Feedback loop | *eval, observe, correct, re-eval* | edit, build, restart, lose session, reproduce |
| Intermediate state observable? | *yes, live objects* | no, only rendered output |
| Discoverability | ask the running image | grep the repo, hope docs are current |
| Correctness oracle before running | gate 1 only, partial | *the compiler, and it is better* |
| Bad extension kills the session? | no, signals with a restart | yes, panics |

*The feedback loop is the largest single factor.* It converts "reason correctly on the
first attempt" into "try, observe, correct." Weak models are bad at the first and decent
at the second, so this is not a marginal gain, it is a change of task.

*Honest size of the difference:* for changes the extension surface covers, roughly two to
three times easier, almost all of it from the loop. For changes it does not cover, the
difference is not a multiplier but a binary: possible, versus needing a rebuild by the
resource that expired. Window managers are mostly the second case.

** The strongest argument against the above

*A cheap model writes better Rust than it writes Common Lisp.* Training data for Rust
dwarfs Common Lisp and CLOS specifically is not something small models are fluent in.
That is a real cost and it partially offsets the loop advantage.

What rescues it: the code a cheap model needs to write here is
~(defmethod place ((p my-policy) node rect) …)~. Small, formulaic, three worked examples
beside it, verified live at a REPL before it is committed. That is the easiest possible
target, and nothing like asking a weak model for 500 lines of new subsystem.

*So the fluency gap is survivable only because the surface is small and the examples
exist.* Both are [[#phase-4][Phase 4]], which is why it is not cuttable.

** The caveat that must not get lost

Every advantage above routes through /there is a documented generic for the thing you
want to change/. Without one, Common Lisp's advantage collapses to roughly zero and
becomes *worse* than the compiled path, because now there is no oracle, no compiler, and
a weak model editing a monolith.

*The language multiplies the decomposition. It does not substitute for it.*
[[#phase-2][Phase 2]] is still the entire project.

* CI gates
:PROPERTIES:
:CUSTOM_ID: gates
:END:

All six run on every commit from day one. They are cheap and they are the only automated
defence the project has.

1. *Zero compiler warnings* under ~(declaim (optimize (safety 3) (speed 1)))~ with
   ~ftype~ on every exported function. Verified in
   [[file:SPIKE-WEEK0.org::#ext-7][spike §ext-7]] to catch wrong arity, wrong-typed
   constants, typo'd accessors and typo'd calls at compile time.
2. *Every generic in ~policy/protocol.lisp~ has a docstring.* The generated
   extension-surface document prints ~UNDOCUMENTED <-- flag me~ and the build fails.
   ~15 lines over ~closer-mop~ and ~sb-introspect~, already written in
   [[file:SPIKE-WEEK0.org::#ext-6][spike §ext-6]].
3. *The lattice touches no core.* ~git diff --name-only~ over the lattice work asserts
   nothing under ~src/~. This is [[file:DESIGN.org::#d21][D21]]'s experiment, run daily.
4. *Core runs without the lattice.* Load ~latticewm.asd~ alone, start, place a window,
   exit. The extension must be genuinely optional or it is not an extension.
5. *Codegen counts match the pinned XML.* 8/57/44/10 for window-management, 3/11/5/1
   for xkb. A protocol change becomes a failing build rather than a mystery.
6. *The runtime-to-policy line ratio is reported on every build.* Not pass/fail, a
   number, printed where it cannot be ignored. ~src/wire/~ + ~src/runtime/~ against
   ~src/model/~ + ~src/policy/~ + ~lattice/~. This is the Emacs-shape test from
   [[#extensibility-real][§extensibility-real]] and it is the closest thing to a direct
   measurement of whether the language decision paid off. Check it on Day 9. Runtime
   growing faster than policy is the earliest visible symptom of the monolith failure
   mode, and it shows up weeks before anything else does.

*Gate 3 is necessary and not sufficient, and this must be said out loud.* It is
satisfiable in bad faith: make every core generic take ~&rest args~, push all state
through ~props~, and the letter passes while the spirit dies. So gate 3 reports two
numbers alongside pass/fail — *the lattice's ~defmethod~ count and its total lines*. A
lattice that is three hundred lines of methods is the thesis holding. One that is two
thousand lines re-implementing geometry is the thesis failing while wearing the gate's
uniform.

* Packaging: both targets, neither privileged
:PROPERTIES:
:CUSTOM_ID: packaging
:END:

** Plain Linux is the primary build

Ordinary ASDF. SBCL and Quicklisp are packaged on every distribution. ~wayflan~ is not
in Quicklisp's distribution, so it is a git submodule or a ~qlot~ pin, not a curl.

#+begin_example
make          -> builds, runs the gates
make run      -> runs against the current WAYLAND_DISPLAY
make image    -> save-lisp-and-die -> ./latticewm, one executable
make install  -> ./latticewm + share/ + a sample init.lisp
#+end_example

*~save-lisp-and-die~ does not cost live redefinition.* The dumped core retains the
compiler, so SWANK connects and ~defmethod~ still works at runtime. This is StumpWM's
shipping model and it is proven. Ship the image with ASDF included so user extensions
can be ~asdf:load-system~-ed from ~~/.config/latticewm/~.

Result: a single ~40 to 60 MB executable, dependencies libc only, runs on Arch, Fedora,
Debian, Void, anything.

** Nix is a packaging target, not a dependency

~flake.nix~ exposes ~packages.default~ (the same image), ~devShells.default~ (SBCL,
Quicklisp, the pinned river), and a NixOS module. It consumes the same ~Makefile~.

*Nothing in ~src/~ may know that nix exists.* If the flake is deleted the project still
builds. That is the test.

** Protocol pinning, in both worlds
:PROPERTIES:
:CUSTOM_ID: pinning
:END:

~river-window-management-v1~ is *unreleased and moving*, and a pre-release protocol can
break within a version number rather than politely bumping to v2. After budget expiry a
river upgrade could break the window manager with no one available to repair it. This is
the largest threat to the "survives without AI" requirement, larger than any
decomposition risk, and DESIGN treats it as a CI check.

Three layers, and the first two work everywhere:

1. *Vendor the XML in-tree* and generate from the vendored copy, never from a URL.
2. *Assert the version at bind time.* We generate against
   ~river_window_manager_v1~ version 5. On registry bind, if the compositor advertises
   something we did not generate against, *refuse to start* and print the two version
   numbers, the river commit this build is known good against, and what to do. A clear
   refusal is repairable by a non-programmer. Silent misbehaviour is not.
3. *Nix pins river itself* in the flake, so the compositor and the window manager become
   one versioned pair upgraded deliberately or never. On plain Linux the equivalent is
   crude and works: record the known-good river commit in the DESIGN and *keep a copy of
   the working river binary*. River is Zig and builds to a single file.

** Phase 0 — unblock the compositor (Day 1, timeboxed, hard)
:PROPERTIES:
:CUSTOM_ID: phase-0
:END:

Runs in parallel with Phase 1. Do not let it block writing code.

- [ ] *Try river nested first.* River is a wlroots compositor and wlroots has a Wayland
      backend, so it should run inside the existing niri or hyprland session, in a
      window, on the machine that already exists. *Verify this specifically for river
      before betting the day on it.* If it works, the dev loop is Emacs on one side,
      river-in-a-window on the other, SLIME between them, and no second machine is ever
      needed.
- [ ] If nested fails, build river main bare-metal on the NixOS box. Half a day.
- [ ] Build ~canoe~ via its ~shell.nix~ against the same river. It is the known-good
      reference to diff against when sequencing goes wrong.

*Abort condition: if there is no working river by end of Day 2, stop and re-plan.* Every
subsequent phase past Phase 2 assumes it.

** Phase 1 — plumbing (Days 1 to 3, needs no river)
:PROPERTIES:
:CUSTOM_ID: phase-1
:END:

All of this is testable against WSLg or any Weston. None of it waits on Phase 0.

- [ ] ASDF skeleton, vendored XML, codegen, package with a ~wl~ local nickname.
- [ ] ~safety 3~ + ~ftype~ + warnings-as-errors. Gate 1 live.
- [ ] Extension-surface generator and gate 2. Lift the ~15 lines from the spike.
- [ ] Sequence discipline: ~*sequence*~, ~check-sequence~, ~with-manage-sequence~,
      ~with-render-sequence~, and the macro that emits a wrapper for each of the 68
      generated requests. Test by asserting the condition fires on a deliberate
      violation.
- [ ] Dispatch loop with ~handler-case~ on ~wl-message-error~. *Test it properly:* churn
      surfaces against WSLg until the destroy race fires, then confirm the loop survives
      and does not desync. DESIGN calls this a five-line fix from a source read; that is
      a claim, not a result.
- [ ] SWANK in a thread, and the top-level ~*debugger-hook*~. A daemon with no
      controlling terminal that hits an unhandled condition hangs on a ~stdin~ that is
      not there.
- [ ] Gate 5, the codegen count check.

** Phase 2 — the core model (Days 3 to 5, needs no river) — *THE PROJECT*
:PROPERTIES:
:CUSTOM_ID: phase-2
:END:

*This is the phase that decides whether the project succeeds.* Everything before it is
plumbing anyone can write; everything after it inherits whatever this produces. It has
no external dependency, so it cannot be blocked, only rushed. Do not rush it.

- [ ] ~model/tree.lisp~ — pure split-tree surgery. split, close-collapse, clear, move,
      swap, pull. No protocol calls anywhere in this file.
- [ ] ~model/space.lisp~ — the coordinate map. One cell at ~(0,0)~ is the degenerate
      case and the conventional layer is exactly that. Written once, per
      [[#delta-1][Delta 1]].
- [ ] ~model/focus.lisp~ — the cursor, and *the single focus-repair function every verb
      calls*. Improvised per-verb repair is how you get fifteen subtly different
      behaviours and a bug class where focus points at a node that no longer exists.
- [ ] ~model/geometry.lisp~ — ~(tree, rect) -> ((leaf . rect) …)~. Pure.
- [ ] ~policy/protocol.lisp~ — the thirteen generics, docstrings mandatory, no methods.
- [ ] ~policy/conventional.lisp~ — the default methods.
- [ ] *Unit tests over all of it.* This is the one part of a window manager that is
      testable without a compositor. Take the free lunch.

** Phase 3 — wire it up (Days 5 to 9)
:PROPERTIES:
:CUSTOM_ID: phase-3
:END:

- [ ] Window lifecycle: ~window~ event to a leaf, closed to tree surgery plus focus
      repair, ~identifier~ recorded.
- [ ] ~runtime/emit.lisp~: placements to ~set_position~, ~propose_dimensions~,
      ~hide~/~show~, and an explicit ~place_above~ chain. Render order is undefined by
      default; every node must be ordered deliberately.
- [ ] Keybindings via ~river-xkb-bindings-v1~. Command registry. Spawn.
- [ ] Floating with explicit render ordering. Minimize leaving the tree.
- [ ] The [[file:DESIGN.org::#week0][Week 0 river-side checks]], which are now due:
      is rendering state genuinely legal in a manage sequence (the spec contradicts
      itself); does an ~xdg_popup~ in a straddling cell get sliced by ~set_clip_box~;
      does ~ate_unbound_key~ fire under ~clear_focus~ and does it carry the keysym.
- [ ] Persistence: ~identifier~ to location, s-expression under ~$XDG_STATE_HOME~,
      debounced write.

*Checkpoint, end of Day 9, and it is the one that matters:* a window manager you can
spawn, split, navigate, close and float, running nested. If this is not true on Day 9,
*cut Phase 5 rather than Phase 4* and say so in this file.

*Dogfood nested. Do not make it your only window manager yet.* A WM you live in
generates an unbounded papercut queue, and DESIGN's week-2 daily-driver gate was written
assuming weeks 3 and 4 existed to absorb it. They do not.

** Phase 4 — the extension surface and a public release (Days 9 to 11)
:PROPERTIES:
:CUSTOM_ID: phase-4
:END:

*Not cuttable.* This is the deliverable, not the documentation of it.

- [ ] Audit every policy decision made in Phases 2 and 3. Anything sitting as an inlined
      ~cond~ that a user might plausibly want to change becomes a generic.
- [ ] ~~/.config/latticewm/init.lisp~, with every [[file:DESIGN.org::#p1][P1]] fork
      present as a tier-0 value.
- [ ] *The SWANK bridge. This is a shipped artifact, not an assumption.* A small socket
      client (or MCP shim) that takes a form, evaluates it inside the running window
      manager, and returns the value plus any condition and backtrace.

      The entire cheap-AI argument in [[#extensibility-real][§extensibility-real]] rests
      on a model being able to eval into the live image. Without this tool that argument
      describes a capability nobody can reach, and the language decision quietly stops
      paying for itself. With it, the loop advantage becomes real for the exact agent
      that will be doing the extending after August.

      Secondary benefit that justifies building it even if the first never materialises:
      *you use it during Phases 3 and 5 yourself.* It is not speculative infrastructure.
- [ ] *Three worked example extensions, framed as onboarding material for a weak model,
      not as human documentation.* Each must be one ~defmethod~ shaped, self-contained in
      one file, and verifiable at the REPL in a single eval. Suggested:
      focus-follows-mouse; a window rule matching ~app_id~ to a spawn cell; MRU focus
      after close instead of stay-put.

      The test is not "would a person understand this." It is *"could a cheap model
      produce a fourth one by pattern-matching on these three."* If the answer is no, the
      surface is wrong and this is the last moment it can be fixed.
- [ ] The generated extension-surface document, checked in, regenerated by CI. It is the
      thing the bridge lets a model query at runtime, so it must be machine-readable
      first and pretty second.
- [ ] *Tag v0.1 and announce it.* DESIGN notes there has never been a Common Lisp
      Wayland window manager and that StumpWM's community wants a successor, then never
      plans for it. *The single best insurance against budget expiry is other people
      holding the code.* A project with three contributors survives; a perfectly
      decomposed project with zero does not. This costs half a day and it is the highest
      expected-value half-day in the plan.

** Phase 6 — bonus, days 16 to 22 if the budget runs long
:PROPERTIES:
:CUSTOM_ID: phase-6
:END:

In priority order: the drawn map on a ~wl_shm~ shell surface; named cells; the
~compact~ family; bonds ([[file:DESIGN.org::#d16][D16]]); ephemeral jump labels; pan
animation. Assume none of it happens.

* The cut list, stated explicitly so it does not drift back
:PROPERTIES:
:CUSTOM_ID: cuts
:END:

Cut: the minimap and drawn map, ~wl_shm~ and the fd path, named cells, ephemeral jump
labels, pan animation, bonds, the ~compact~ family, workspaces beyond a flat list.

Cutting ~wl_shm~ is a bonus rather than a loss: it removes the least-proven part of
wayflan from the critical path.

*One thing is deliberately un-cut, and the reason matters.* DESIGN calls two-dimensional
navigation "the single biggest design risk" and names three mitigations: the minimap,
named cells, and the coordinate overlay ([[file:DESIGN.org::#d5][D5]]). The cut list
removes the first two. *Removing all three would ship the ZUI get-lost failure mode with
nothing standing against it*, and the resulting lattice would plausibly be worse than
niri's strip rather than better.

The coordinate overlay is by far the cheapest of the three and it stays. It can be text
on a small shell surface, or in the degenerate case border colour keyed to coordinate
parity. It ships in Phase 5.

* Decisions taken by fiat, 2026-07-30
:PROPERTIES:

** Deltas 1 and 2 held; Delta 3 is conditional

[[#delta-1][Delta 1]] — cells and splits share one geometry — is the strongest result here.

cell boundary needed zero lines: ~find-motion-target~ ascends out of a split,

[[#delta-3][Delta 3]] — ~absolute-with-clipping~ as the shipped default — is *reversed, with
its own argument preserved*. Delta 3 is right that ~exact-fit~ makes a column's

There is a test asserting both halves. If this proves wrong in daily use the fix
is one ~setf~.

** The hole the first session left, stated plainly

M-x shipped, and it could reach *thirty-seven of sixty-seven commands* — the

: workspace takes number -- run it from a REPL

which is a reasonable thing to say to a Lisp programmer and no answer at all to

already bound, or by opening a REPL — and [[#extensibility-real][§extensibility-real]]'s whole argument
is that the command registry is a *user interface* rather than an
implementation detail. It was not one yet.

It is now *71 of 72*, and the exception is ~focus-path~, whose argument is a
list of integers naming a place in the tree. Nobody types that. The point of
the exception is that M-x says so instead of putting up a prompt that cannot be
answered. There is a test asserting that the list of refusals is exactly that
one command, so a future command that quietly becomes unreachable fails the
build rather than going unnoticed.

** How, and why it is not Emacs's design

Emacs's ~(interactive "sPrompt: ")~ is a string DSL with about forty
single-letter codes, and nobody remembers more than four. The mechanism here is
the same idea with the hindsight applied:

- An *argument type* is a named object — a prompt, a candidate list, a parser —
  and ~define-argument-type~ adds one in three lines from a configuration file.
- The type of a parameter is *inferred from what it is called*. A parameter
  named ~direction~ holds a direction; one named ~number~ holds a number.
- ~(:interactive ...)~ after a docstring overrides that per command, and is
  needed exactly twice in the whole system: ~spawn~'s ~command~ is a shell
  command line, and ~describe-command~'s ~name~ is one of ours.

The inference sounds like a hack and is not. The parameter names were already
chosen to read well in a docstring — that is what makes ~substitute-arguments~
work on the help screen — and *a name that reads well in a docstring is a name
that says what kind of thing it is*. The convention covers every shipped
command, in the core and in the lattice, with two exceptions and no
annotations. It is a tier-0 option, so adding to it needs no code.

Two decisions inside this went to [[#the-policy-surface][the policy surface]] rather than the runtime,
and the surface count moved 40 → 42 for them:

- ~complete-candidates~ — prefix, then substring, then subsequence. This is the
  most personal decision in the whole minibuffer; Emacs ships six completion
  styles and that is the right number to ship when the answer is taste.
- ~argument-type-for~ — the naming convention itself, which is a *scheme*
  somebody may want to replace wholesale rather than entry by entry.

The test that caps the surface at forty was moved to forty-five, with the
reason written into the test rather than into a commit message.

** The bindings nobody would have found by reasoning

Reading text needs the keys bound, because river delivers keys to the focused
*window* and gives the window manager only what it asked for. The first session
bound printable ASCII with *no modifiers* — 98 bindings — and that was enough
to type a command name.

It is not enough to type ~(+ 1 2)~. River matches a binding on keysym *and*
modifiers, and the keysym xkb produces for Shift+9 on a US layout is
~parenleft~ with Shift still in the modifier set. A binding for ~parenleft~
with no modifiers never fires. So every printable keysym is now bound twice,
bare and with Shift, plus the arrows, Home, End, Delete, and twelve Ctrl
chords: *214 bindings, created once, enabled only while a prompt is up.*

Doing it by mask rather than by working out which characters are shifted on
which layout is what makes it work on a Dvorak or a German keyboard.

*Still unverified:* whether river reports Shift in the modifier set for a
shifted keysym, or masks it out. Both bindings exist, so one of them matches
either way — but which one has not been observed, because observing it needs a
human pressing a bracket, and the whole session was driven through the SWANK
bridge.

** The finding: ~#'foo~ in a hook cannot be redefined

Worth recording because it is a defect in the *live-redefinition thesis*
itself rather than in a feature.

Reloading =help.lisp= into the running window manager changed nothing on
screen. The reason: ~(add-hook :draw-overlays #'draw-help-overlay)~ stores the
function *object*. Redefining the function afterwards leaves the hook calling
the old one, and re-running the ~add-hook~ adds a second entry, because the new
object is not ~EQL~ to the old. Both generations then ran, and the older
drawing won by being second.

=echo.lisp= had the same bug in a worse form — a ~pushnew~ of an anonymous
lambda onto ~*reserve-hooks*~, which cannot dedupe at all, so every reload
would have reserved another strip of the screen.

Fixed by registering *symbols*: a symbol is looked up when the hook runs, so
redefinition takes effect, and a second ~add-hook~ of the same symbol replaces
rather than accumulates. ~add-hook~'s docstring now says so, and ~:draw-overlays~
— the one hook in the system that four things used and nothing documented — is
now declared, so it appears in the extension surface.

*The general form of this:* the mechanisms that make a live image worth having
are not automatic. They have to be used a particular way, and the way is not
the one that reads most naturally.

** The finding: twenty-four options that could not be set

The starter configuration this program writes has, on line 55:

: ;; (setf *terminal* "alacritty")

A configuration file is read in ~LATTICEWM/USER~, which inherits
~LATTICEWM/RUNTIME~ wholesale. ~*TERMINAL*~ was never exported from it. So that
line — *the line the program itself suggests* — interns a brand new symbol in
~LATTICEWM/USER~, sets that, and changes nothing whatsoever.

Twenty-four of the thirty-one runtime options were in this state, including
~*terminal*~, ~*editor*~, ~*browser*~ and ~*modifier*~ — the four values a
person is most likely to want on their first day — and every colour, scale and
column count in the entire widget layer.

*Why nothing caught it.* Each one was declared with ~define-option~, so it was
registered, documented, printed by ~--list-options~, readable through
~Super+? o~ and settable through ~Super+? s~ and ~M-x set-option~, all of which
route through the keyword registry rather than the symbol. Gate 2 checks that
options are documented. The surface tests check that they have defaults and
round-trip. Six gates and 570 checks passed over a system where the single most
common thing a user would type into a config file silently did nothing.

It is the same shape as [[file:FINDINGS.org][FINDINGS.org]] core edit 3 — /the shipped defaults were on
the class users specialise/ — and the same lesson, which §honest predicted and
which has now happened twice: *nothing verifies that the decomposition is good,
and every automated check can pass while the thing is unusable in its most
common mode.* What caught it, again, was going and looking: reading the file a
new user is handed, and asking whether each line in it actually works.

There is now a test that asserts *symbol identity* — not accessibility — for
every registered option, and it fails with the name of the offending option and
the package to export it from. It was checked against the bug rather than
merely written: re-breaking one symbol makes it fail.

** The welcome overlay

A window manager has a discoverability problem no editor has: at startup the
screen is empty, nothing is clickable, and every key is unlabelled. =Super+/=
has drawn the whole keymap since the first session, which helps precisely
nobody who does not already know to press =Super+/=.

niri answers this with an important-hotkeys overlay on first run. So does this,
now: about a dozen rows, shown once, marked in ~$XDG_STATE_HOME~, and reachable
forever after with ~M-x welcome~. The rows are derived — key names from
~*modifier*~, descriptions from each command's own docstring — for the same
reason the help overlay is: a welcome screen that disagrees with the keymap is
worse than no welcome screen, and it would disagree the first time anybody
rebound anything.

The marker is written *before* the overlay is drawn. The two orderings do not
cost the same: one loses a welcome screen once, the other repeats a failure on
every subsequent start.

** Gate 6: ruled

[[#log2][§log2]] left the question open — is gate 6 measuring the wrong pair, or is the
decomposition failing? *Ruled: neither. The widget layer should become
extensible, and the ratio should go above 1 by moving code rather than by
moving the measurement.*

The ruling matters because gate 6 counts *by directory* — ~src/wire/~ plus
~src/runtime/~ against ~src/model/~ plus ~src/policy/~ plus ~lattice/~ — so
adding a ~define-option~ inside =src/runtime/help.lisp= moves the number by
exactly zero. That is not a flaw in the gate. It is the gate insisting the
decomposition be real: a generic that lives in the runtime is still something a
user has to read the runtime to find.

The split to make is the Emacs one. The C core does redisplay primitives;
Elisp decides what is on the mode line. Here: shm buffers, the fd path, glyph
blitting and surface lifecycle stay runtime; colours, column layout, which font
at which size for which role, what the status line says, how a help page
composes, and the completion styles become generics under ~src/policy/~.

Roughly 400 lines have to cross to reach 1.0 from the 0.80 this session ends
at. The candidates, in order of how much of each is genuinely a decision:
=echo.lisp= (what a status line shows is ~mode-line-format~, and it is
hardcoded), =minibuffer.lisp=, =help.lisp=, =font.lisp= — where the PSF loader
is mechanism but *which font for which role* is policy, and making that live is
runtime font loading, which is a feature rather than an accounting exercise.

[[#log3][§log3]] ruled that gate 6 should move because code crosses from runtime to

** The split mechanism was half policy and half TYPEP

Every genuine *decision* about splits was already a method — ~layout-children~,
~step-address~, ~entry-address~, ~should-collapse-p~, ~insertion-weight~. The
*verbs* were not: five places asked ~(typep x 'split)~ inline, and a ~typep~
cannot be specialized.

The consequence was specific rather than theoretical. A container kind from
outside that divides space exactly the way a split does — the shipped
scrolling-columns example, or anybody's own variant — was invisible to
~resize~, ~equalize~, ~equalize-all~ and ~tab~, and ~tree-split-at~ would never
join it, so splitting three times inside one built a ladder of nested
two-child containers instead of one row of four.

~a-container-kind-the-core-never-heard-of-works-everywhere~ passed throughout,
because it exercises layout, motion and surgery, all of which do go through
generics. *The test was right and the claim it was read as supporting was
wider than the test.*

Four generics carry it now, each fallback specialized on ~T~ rather than on
~container~ so that a caller walking up a parent chain and reaching ~NIL~ gets
an answer instead of ~no-applicable-method~ — the same lesson
~layout-children~'s fallback already records. ~src/model/~ stays pure: the
decision crosses that line as a closure, exactly the way ~%simplify-upwards~
already takes ~allow-collapse~ instead of calling ~should-collapse-p~.

** Fonts are data now, and the cap on them was wrong

The window manager shipped with one font wired in as three constants and a
table. The reasoning for a bitmap font at all still holds — Pango would be a C
font stack in the way of surviving without a maintainer — but it was never an
argument for the font being *unchangeable*.

A ~font~ is now a struct, the generated Terminus table registers itself as the
default, ~load-psf~ reads any console font off the disk, and ~font-for (policy
role)~ decides which is used where. PSF rather than BDF or TTF for one reason:
*the fonts are already on the machine*, a few dozen of them, so changing the
font needs nothing found, converted or installed.

Two things only running it could find, and it found both inside a minute:

1. ~uiop:run-program~ with ~(:string :element-type (unsigned-byte 8))~ reads
   the pipe as *text* anyway and dies on the first octet that is not valid in
   the default encoding — immediately, for a font table. The failure surfaced
   as *"the font did not change"* rather than as an error, because the caller
   fell back to the built-in one. ~:external-format :latin-1~ is the fix: the
   encoding whose code points are its bytes.
2. The first version capped fonts at eight pixels wide, with a docstring
   confidently explaining that Terminus's larger sizes are taller rather than
   wider. *They are not.* ~ter-122b~ is eleven wide and ~ter-d28n~ is fourteen,
   so the cap refused every size above the smallest — which is to say every
   font somebody changing the font would be reaching for. Glyph rows are
   stride-addressed now and the leftmost pixel is the high bit at any width.

The second is the more interesting one. It was not a coding error; it was a
*stated assumption in a docstring* that was simply false, and the only thing
that could have caught it was pointing the loader at the fonts on the disk.
Third time this log has had to record that.

** Where gate 6 actually stands

: 1.20 -> 0.82 -> 0.80 -> 0.87 (options and fonts) -> 0.85 (the PSF loader)
:                            -> 0.86 (font tests)

~policy/appearance.lisp~ took the twenty-four widget options — every colour,
scale, height and column count in the echo area, minibuffer, help overlay and
empty-pane hint — out of ~src/runtime/~, and added the font layer. That is
~+259~ policy lines and ~-100~ runtime.

Then ~psf.lisp~ put ninety-odd lines *back* into the runtime, and the ratio
fell again. That is correct and worth stating plainly rather than hiding:
reading bytes off a disk is mechanism. A feature that makes the system more
configurable can move the number the wrong way, and a gate that punished it
for that would be a gate arguing against its own purpose.

*It is 0.86, and it is not above 1 yet.* Getting there needs roughly 270 more
lines to cross, and the honest candidates are no longer easy ones:

- The text-composition half of =help.lisp= — ~summary-of~, ~wrap-text~,
  ~truncate-text~, ~substitute-arguments~. Pure functions, and every one of
  them is a decision about how a docstring reads on a screen. Perhaps ninety
  lines, and the only obstacle is that ~substitute-arguments~ takes a command
  object and would have to take a lambda list instead.
- =echo.lisp='s content. What a status line is made of is ~mode-line-format~,
  the single most-customised variable in Emacs, and here it is hardcoded.
- *The real question: the command registry and the keymap.*
  [[#extensibility-real][§extensibility-real]] says outright that the command registry is "a user
  interface rather than an implementation detail". If that is true then
  ~defcommand~, ~define-key~ and the shipped keymap are policy, and moving
  them settles gate 6 outright — five hundred and fifty lines. If it is not
  true, then a registry is infrastructure and the number has to be earned
  somewhere else.

That is a genuine architectural call rather than an accounting one, and it is
the next thing to decide.

[[#log4][§log4]] ended at 0.86 and named the open question as /is the command registry
policy?/ — framed as a close call. It was answered by inverting the burden of
proof, and the ruling is the useful part of this session:

#+begin_quote
Anything you can put above the line and give the user is a win. You need a
real, solid, very good reason to make something core.
#+end_quote

That is a stronger claim than [[#extensibility-real][§extensibility-real]] ever made, and it changes the
question from /can I justify moving this?/ to /can I justify keeping it?/
Applied mechanically, the test for "solid reason" is: *does it touch the
protocol or the server?*

: commands.lisp    241 lines    0 protocol references
: minibuffer.lisp  614 lines    0
: config.lisp      321 lines    0
: state.lisp       224 lines    0
: log.lisp         100 lines    0
: keys.lisp        309 lines    2
: windows.lisp     232 lines   12

On that test the command registry is not a close call at all.

** What moved, and the trick that made it free

~log.lisp~ and ~commands.lisp~ to ~src/policy/~, plus the pure text functions
out of =help.lisp= and the five program defaults out of =config.lisp=.

~guarded~ earns its place there by its own docstring, which was written long
before this question came up: it exists "at every boundary where a *policy
method* is called — that is, at every point where user code runs inside ours."
That is a policy decision about what happens when an extension misbehaves, and
it was sitting in the runtime.

*The move cost zero edits at four hundred call sites*, and the first attempt
at it was the wrong one. Prefixing every use of ~logmsg~, ~guarded~ and
~defcommand~ with ~p:~ was a 403-substitution rewrite that also mangled
~command~ — a parameter name in half a dozen files — and prefixed words inside
comments. It was reverted whole. What replaced it is ~:import-from~ in the
runtime's ~defpackage~: the symbols live in ~LATTICEWM/POLICY~, are imported
into ~LATTICEWM/RUNTIME~, and are re-exported there so ~r:defcommand~ keeps
resolving for the lattice. Not one reference in any file changed.

The lesson is worth keeping: *a package system is the tool for moving symbols
between layers.* Rewriting call sites to do it is doing the package system's
job by hand, badly.

** The bug the move exposed

Gate 2 failed immediately: ten undocumented generics, all of them CLOS slot
readers — ~command-name~, ~command-function~, ~argument-type-prompt~ and
friends.

The cause is older than this session. ~policy-generics~ was:

: (do-external-symbols (symbol '#:latticewm/policy)
:   (when (and (fboundp symbol) (typep (fdefinition symbol) 'generic-function))
:     (pushnew symbol out)))

— *every exported generic in the package*. Meanwhile ~policy-generic-p~ sat
beside it, written, documented, and never called, saying:

#+begin_quote
The test is structural rather than a maintained list: a generic function
exported from this package whose first required argument is specialized on
POLICY somewhere. A list would drift; this cannot.
#+end_quote

The two definitions were indistinguishable for exactly as long as the only
generics in the package were the surface. The moment a class with slot readers
moved in, ten accessors became extension-surface entries, gate 2 demanded
docstrings for them, and *the sentence the surface document prints at the top
of itself* — "every generic below takes a POLICY as its first argument" —
became false.

Nothing had noticed, because nothing could: the drift needed a class to arrive
in the package, and none ever had. ~policy-generics~ walks ~policy-generic-p~
now, and the test asserts both halves — that everything in the surface passes
the structural test, *and* that the five accessors which exposed it are
excluded — because a test that only counted would have passed throughout.

** Gate 6

*The label changed.* It has read "watch this: runtime is outgrowing policy"

Two honesties about it. It is *1.01*, which is a margin of forty-three lines

Emacs is around 3.5. This is 1.01. What that number now means is that *the
system has as much decision in it as mechanism* — which is the floor of the
