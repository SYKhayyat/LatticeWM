* What changed from DESIGN's plan, and why
:PROPERTIES:
:CUSTOM_ID: deltas
:END:

Three deltas. Each is a reversal of a decision in DESIGN.org and is recorded here rather
than quietly applied, per that document's own standing rule.

** Delta 1 — the conventional layer and the lattice share one geometry
:PROPERTIES:
:CUSTOM_ID: delta-1
:END:

DESIGN's [[file:DESIGN.org::#plan][§plan]] builds split trees twice: as the whole layout
model in week 2, then as cell contents in week 3. That is the same code written twice
under a budget that cannot afford it once.

*A cell boundary and a split boundary are the same thing seen twice.* A split separates
two subtrees, reached by ~:a~ / ~:b~. A cell separates two subtrees, reached by
~(x±1, y)~. Nested versus indexed. Nothing else differs.

The consequence that makes it worth doing: *directional motion is continuous across the
boundary.* Move left from the leftmost leaf of cell ~(0,0)~ and you arrive at the
rightmost leaf of cell ~(-1,0)~. No mode, no separate command, no discontinuity in the
user's model. Emacs's ~windmove~ and lattice cell motion are one verb with one
implementation.

So: build cells-holding-trees on day one. Ship with a single cell at ~(0,0)~ and the
viewport locked at 1×1, and it *is* a conventional tiling window manager. Unlock
coordinates and zoom and it is the lattice. Same code, extended, not ported.

** Delta 2 — D21's experiment becomes a daily CI check, not a week-3 milestone
:PROPERTIES:
:CUSTOM_ID: delta-2
:END:

[[file:DESIGN.org::#d21][D21]] holds: the lattice must be expressible without core
surgery, and if it cannot be, *that is the finding*. What changes is when you learn it.

Under D21 as written you learn in week 3, which under this budget may not happen, so the
experiment that justifies the whole sequencing never runs.

Instead: *the lattice lives in a separate ASDF system* that depends only on the core's
exported policy package. Core loads, starts and runs with the lattice absent. Any core
edit the lattice demands shows up as a failing gate, on the day it happens, from day
one. See [[#gates][CI gates]], gate 3.

This keeps D21's falsifiability and removes its scheduling risk. It costs nothing.

** Delta 3 — the cut list guts D22's own mitigations, so D22 flips
:PROPERTIES:
:CUSTOM_ID: delta-3
:END:

[[file:DESIGN.org::#d22][D22]] (exact-fit zoom) accepts, as a stated price, that *panning
resizes every visible window* on a non-uniform lattice. Terminals rewrap, browsers
reflow. Pan is the frequent navigational verb, and
[[file:DESIGN.org::#d7][D7]] sells it as pure view control.

D22's own escape hatch: both width solvers ship as two methods on one generic.

*Ruling: ~absolute-with-clipping~ (the old D11 behaviour) is the shipped default;
~exact-fit~ is the alternate method.* [[file:DESIGN.org::#feasibility][§feasibility]]
already established that ~set_content_clip_box~ renders the partial trailing cell
cleanly, with the border redrawn at the clip edge, free, from the compositor. D22 traded
a cosmetic problem that the compositor solves for a functional one that it does not.

*And that ruling was itself reversed while this paragraph went on stating it.*
[[#log][§log]] records the reason — on a uniform lattice ~exact-fit~ panning resizes
nothing, and columns are uniform until somebody resizes one, so the cost the ruling
above was avoiding is a cost only the people who have already opted into it pay.
~*zoom-mode*~ ships as ~:FIT~; both solvers are still two methods on one generic, so
the flip is one ~setf~ in either direction. D22 stands.

#+CLAIM: (eq :fit (option-default :zoom-mode))

This is a one-line default change, not a redesign, and it is reversible by config.

*And the mode this paragraph rules on was half-built, which nobody found for as long as
it was the mode nobody was in.* ~set_content_clip_box~ does render the partial trailing
cell cleanly and it is free from the compositor — and the method that asks for it read a
bound that nothing in the tree wrote, so it cropped nothing, ever. Under ~:fixed~ a
column you had resized was ignored outright, which is the sharpest form of the problem:
the *only* reason to leave ~:fit~ is that you resized something and do not want panning
to move it, and the mode you were sent to dropped the resize. A cell that had run clean
off the edge was placed offscreen rather than hidden, and the drawn map's threshold
computed the ~:fit~ cell width in both modes. All four are fixed and all four are now
covered — see [[file:FINDINGS.org::#dead-property][FINDINGS: the method that could not
fire]]. *The default is unchanged*: ~:fit~ is still right for the reason above, and what
changed is that the alternative is now the thing this ruling describes.

Two rules, and they are the project:

1. *~src/policy/protocol.lisp~ contains no methods.* Generics and docstrings only. It is
   the extension surface, and it is a file you can read in one sitting.
2. *Nothing in ~lattice/~ may edit anything in ~src/~.* Enforced by gate 3.

** The policy surface

* What extensibility is actually worth here
:PROPERTIES:
:CUSTOM_ID: extensibility-real
:END:

Added 2026-07-30, after pressing on the question honestly. This section is the rationale
for gate 6, for the SWANK bridge in [[#phase-4][Phase 4]], and for how the worked
examples are framed. DESIGN argued the language decision on *human* extensibility and got
a thin margin. The real requirement is different and the margin is wider.

** The Emacs mechanism is a ratio, not a language

Lisp is not what kept Emacs alive. *The ratio is.* Emacs is roughly 1.3 to 1.4 million
lines of Elisp on about 400,000 lines of C. The overwhelming majority of the system is
written in its own extension language, and three things follow:

- Every feature is a worked example of how to write a feature.
- Anything you want to change is already written in the language you would change it in.
- The extension surface is not documented, it is *demonstrated*, a million lines over.

Vim has Vimscript and is not Emacs. Neovim has Lua and is not Emacs. Hyprland has Lua as
of 0.55 and is not Emacs. In all three the core is C or C++ and the scripting sits on
top. The boundary is not the disease. *How little of the system lives above it* is.

*Therefore the load-bearing metric is how much of the behaviour lives above the
boundary*, and it is checked continuously rather than discovered at the end. See gate 6.

| Shape | Runtime | Policy | Meaning |
|-------+---------+--------+---------|
| Emacs shape | ~500 | ~1,500 | the language bought something real |
| Vim shape | ~2,000 | ~200 | CLOS paid for, nothing received |

*Amended 2026-08-06.* This section originally read "the load-bearing metric is the
runtime-to-policy line *ratio*", and the table above is what that meant. The ratio was
gate 6 for the life of the project and is now deleted; [[#gates][§gates]] item 6 carries
the argument. The correction is not to the paragraphs above — Emacs' million lines of
Elisp really are the mechanism, and "how little of the system lives above the boundary"
really is the disease — it is that *lines by directory* is the wrong reading of "above
the boundary". A file's directory is a filing decision. What is actually being claimed
is that a stranger can change the system's behaviour without editing the core, and the
only direct evidence of that is *methods a stranger wrote*. Counting those instead
survives the one attack the ratio did not: you cannot move a file into the answer.

Read the table above as illustrative of the argument rather than as the metric. The
metric is the two numbers in [[#gates][§gates]] item 6.

*The compounding took Emacs decades and this project has fifteen days.* What gets built
here is the seed, not the advantage. Whether it compounds is entirely a function of other
people and cheap AI, which is why [[#phase-4][Phase 4]] is not cuttable.

** The real requirement: a cheaper AI must be able to extend it

Not "Shaul edits a ~defparameter~." The post-expiry maintainer is a weaker and cheaper
model, plus whatever contributors the release attracts. That is a different set of
properties from human extensibility, and Common Lisp scores differently on them.

| What a weak model needs | Common Lisp | Compiled + plugin API |
|-------------------------+-------------+------------------------|
| Context per change | one docstring, one ~defmethod~ | the trait, its types, the boilerplate |
| …when the change is *not* covered by the surface | still one ~defmethod~ | read core, edit core, rebuild |
| Additive vs invasive | new file, zero core diff | additive inside the API, surgical outside |
| Feedback loop | *eval, observe, correct, re-eval* | edit, build, restart, lose session, reproduce |
| Intermediate state observable? | *yes, live objects* | no, only rendered output |
| Discoverability | ask the running image | grep the repo, hope docs are current |
| Correctness oracle before running | gate 1 only, partial | *the compiler, and it is better* |
| Bad extension kills the session? | no, signals with a restart | yes, panics |

*The feedback loop is the largest single factor.* It converts "reason correctly on the
first attempt" into "try, observe, correct." Weak models are bad at the first and decent
at the second, so this is not a marginal gain, it is a change of task.

*Honest size of the difference:* for changes the extension surface covers, roughly two to
three times easier, almost all of it from the loop. For changes it does not cover, the
difference is not a multiplier but a binary: possible, versus needing a rebuild by the
resource that expired. Window managers are mostly the second case.

** The strongest argument against the above

*A cheap model writes better Rust than it writes Common Lisp.* Training data for Rust
dwarfs Common Lisp and CLOS specifically is not something small models are fluent in.
That is a real cost and it partially offsets the loop advantage.

What rescues it: the code a cheap model needs to write here is
~(defmethod place ((p my-policy) node rect) …)~. Small, formulaic, three worked examples
beside it, verified live at a REPL before it is committed. That is the easiest possible
target, and nothing like asking a weak model for 500 lines of new subsystem.

*So the fluency gap is survivable only because the surface is small and the examples
exist.* Both are [[#phase-4][Phase 4]], which is why it is not cuttable.

** The caveat that must not get lost

Every advantage above routes through /there is a documented generic for the thing you
want to change/. Without one, Common Lisp's advantage collapses to roughly zero and
becomes *worse* than the compiled path, because now there is no oracle, no compiler, and
a weak model editing a monolith.

*The language multiplies the decomposition. It does not substitute for it.*
[[#phase-2][Phase 2]] is still the entire project.

* CI gates
:PROPERTIES:
:CUSTOM_ID: gates
:END:

All six run on every commit from day one. They are cheap and they are the only automated
defence the project has.

/There are twelve now. The six planned here are below; the six that were added are in
[[#gates-added][§gates-added]], because each of them exists for a bug that had already
shipped and the bug is the reason./

1. *Zero compiler warnings* under ~(declaim (optimize (safety 3) (speed 1)))~ with
   ~ftype~ on every exported function. Verified in
   [[file:SPIKE-WEEK0.org::#ext-7][spike §ext-7]] to catch wrong arity, wrong-typed
   constants, typo'd accessors and typo'd calls at compile time.
2. *Every generic in ~policy/protocol.lisp~ has a docstring.* The generated
   extension-surface document prints ~UNDOCUMENTED <-- flag me~ and the build fails.
   ~15 lines over ~closer-mop~ and ~sb-introspect~, already written in
   [[file:SPIKE-WEEK0.org::#ext-6][spike §ext-6]].
3. *The lattice touches no core.* ~git diff --name-only~ over the lattice work asserts
   nothing under ~src/~. This is [[file:DESIGN.org::#d21][D21]]'s experiment, run daily.
4. *Core runs without the lattice.* Load ~latticewm.asd~ alone, start, place a window,
   exit. The extension must be genuinely optional or it is not an extension.
5. *Codegen counts match the pinned XML.* 8/57/44/10 for window-management, 3/11/5/1
   for xkb. A protocol change becomes a failing build rather than a mystery.
6. *How much of the behaviour is answered from outside ~src/~.* Two numbers against two
   floors: policy generics with at least one specialising method defined outside ~src/~,
   and the count of such methods. This is the Emacs-shape test from
   [[#extensibility-real][§extensibility-real]] and it is the closest thing to a direct
   measurement of whether the language decision paid off.

   *This was written as the runtime-to-policy line ratio, and the ratio was deleted on
   2026-08-06.* The plan asked for a number "printed where it cannot be ignored"; it
   became a number with a floor, because a number alone cannot fail. What neither
   version could survive is that a ratio of line counts *by directory* is satisfiable by
   moving files. It was, four times — see [[#log4][§log4]], [[#log5][§log5]],
   [[#log6][§log6]] — walking 0.82 to 1.17 largely by relocation, two of those commits
   reproducing 96–100% of the moved lines verbatim with no new dispatch point, one of
   them recovering 90% of its gain by changing the counting rule while its message denied
   being an accounting change, and the 0.80 floor set *after* the position had been
   arranged. Most of those moves were right for other reasons and stay. The metric does
   not: a gate that is cheaper to satisfy by ~git mv~ than by writing a method will be
   satisfied that way, and then it is shaping where code is filed rather than measuring
   anything.

   The replacement asks the question the ratio was a proxy for, and no rearrangement of
   the tree can move it. It is gate 3's ~defmethod~ floor — "an extension that answers
   almost no generics is going round the protocol" — generalised from the lattice to the
   whole surface. It sits at *15 of 65*, which is the honest number and is much less
   flattering than 0.99.

*Gate 3 is necessary and not sufficient, and this must be said out loud.* It is
satisfiable in bad faith: make every core generic take ~&rest args~, push all state
through ~props~, and the letter passes while the spirit dies. So gate 3 reports two
numbers alongside pass/fail — *the lattice's ~defmethod~ count and its total lines*. A
lattice that is three hundred lines of methods is the thesis holding. One that is two
thousand lines re-implementing geometry is the thesis failing while wearing the gate's
uniform.

** The eight that were added
:PROPERTIES:
:CUSTOM_ID: gates-added
:END:

Not one of these was foreseen here, and that is the interesting part: every one exists
because something had already shipped broken, and in every case the instruments that
existed were individually reasonable and all pointed somewhere else.

7. *Every declared hook is run, and every run hook is declared.* ~:focus-changed~ was
   declared, documented "for status bars", named in the extension guide, and run by
   nothing. A hook is a promise about when a function will be called and nothing checked
   the caller existed. What this cannot see is the third state, which is where the
   mechanism actually was — declared, run, and nobody listening. That is gate 14.
8. *Every event we handle exists on the interface we handle it for.* The output ~:name~
   event we listened for is not on the interface we bind, so outputs had no names, on
   every machine, in silence.
9. *The image, the one installer and the sample config agree.* Three independently
   maintained lists of where an extension lives, and they disagreed.

   And then the gate read one installer and there were *two*. ~flake.nix~ kept its own
   ~installPhase~ with a second hand-maintained list of what ships, and that list did not
   include ~lattice.asd~ — so the bug this gate is named after was live on the nix path
   for the whole life of the gate, on the path that reaches somebody who never ran
   ~make~, which is exactly the machine "does not have the source" describes. The two
   lists differed in six places: no lattice sources, no man pages, no launcher and a
   flattened ~doc/~ on one side; no pinned protocol on the other; and a ~tools/wmeval~
   that existed only on the nix side and spoke to a SWANK port that is off by default.

   *A gate that names an artifact can be satisfied by adding a row*, which is the mistake
   [[#gates][gate 5]]'s comment records making. So the check is not "does ~flake.nix~ also
   install ~lattice.asd~" — it is *there is one installer*: ~flake.nix~ runs ~install.sh~
   and installs nothing by hand. Under that, a new artifact is added in one place or in
   none, and whether the two paths agree stops being a question anybody has to ask.

   It also checks the two licences, because the font's is a *condition* rather than a
   document: ~src/runtime/font.lisp~ is a generated table of Terminus glyphs and says in
   its own header that the OFL text must travel with any copy of it. The binary contains
   the table. Neither path shipped it on purpose — nix caught it through a ~doc/*.txt~
   glob — and neither shipped ours at all, because ~LICENSE~ has no extension and both
   paths matched on one.

   *And it is still text, so something else runs it.* The gates cannot install: there is
   no image yet when they run. ~tools/install-check.sh~ installs to a scratch prefix,
   asserts every artifact, and then asserts that ~--uninstall~ gives all of it back —
   which found that the removal list had never included ~latticewm-config.5~. ~make
   install-check~ runs it, CI runs it after the image, and ~nix build~ now runs the
   installer itself in a sandbox on every build.
10. *No container kind is named by class outside its own definition.* ~copy-node~ was a
    ~typecase~ over the concrete container classes, so the lattice's grid matched no
    clause and copied with no children — and ~serialize-node~ had the identical shape
    and dropped the whole lattice on every restart.
11. *Every registered option is read by something.* ~*smart-gaps*~ was a
    ~define-option~, an export, and a docstring promising to drop gaps and borders when
    a workspace holds one window. ~--list-options~ printed it, the generated extension
    surface described it as working, the config man page listed it beside ~*gaps*~, and
    nothing in the program read the value.

    *Being registered, documented, installable and settable are four promises an option
    makes, and it makes a fifth: that somebody looks.* Every instrument the project had
    asked the registry a question about itself — gate 2 about docstrings, gate 9 about
    the installed list, ~every-option-is-reachable-from-a-config-file~ about whether the
    symbol a user would set is the symbol registered, which is the check that found
    [[#log3][§log3]]'s twenty-four unsettable options. That test is the direct template
    for this gate and it is the right shape: /compare two artifacts that are maintained
    independently, because that is the comparison no human ever performs./ There the two
    were the registry and the user package. Here they are the registry and the compiled
    program.

    It asks SBCL's cross-reference data rather than the source text. A grep for the name
    counts the ~defparameter~, the export, four docstrings and the man page; the
    compiler's answer is about the program, sees a read inside a macro expansion, and
    cannot be satisfied by prose. The same function answers the generated document's
    ~read by:~ line, so the check and the documentation cannot disagree about it.
12. *Every claim the documents make about the program is still true of it.*
    [[file:doc/EXTENDING.org][doc/EXTENDING.org]]'s development loop opened with
    "Start the window manager. SWANK is listening on port 4005." ASSESSMENT U1 turned
    SWANK off by default, correctly, and the first instruction in the extension guide
    became false. Eleven gates, two test suites and a CI workflow passed on every build
    after that, because *not one of them can read a paragraph.*

    It was not an isolated slip. README said the HiDPI, layer-shell and drag-resize
    paths were "all three exercised by the test suite" and none of the three had a
    single test reference. ~*smart-gaps*~ was documented as working in three places
    while nothing read it — gate 11 catches the option and nothing caught the
    sentences. [[#generics][§generics]] above said "if this list reaches thirty" while
    the list stood at sixty-five. And the lattice's line count appeared in four places
    and three of them disagreed, in two files, one of which contradicted itself forty
    lines apart.

    *This is the gate a project with this thesis cannot do without.* The bet in
    [[#extensibility-real][§extensibility-real]] routes entirely through /there is a
    documented generic for the thing you want to change/: a stranger who cannot trust
    the document is a stranger reading the source, which is the situation the document
    exists to prevent. Every other gate defends the code from the code. This one
    defends the reader.

    Three checks, deliberately of different kinds. *Every prose file is classified* —
    /current/, describing the program as it is, or /historical/, a dated record frozen
    on purpose — and a file in neither fails, so a new document cannot arrive unread.
    *Every option a current document names is registered*, automatically and without
    anyone's cooperation, read from code markup rather than raw text because org's bold
    syntax is also asterisks and a check with false positives is a check that gets
    weakened. And *~#+CLAIM:~ makes a sentence executable*: an org keyword holding a
    form, read in ~latticewm/user~ — the package a config file is read in — and
    evaluated against the loaded image, failing the build with the file, the line, the
    form and the sentence above it. A claim must name something the program owns, or
    ~#+CLAIM: t~ would be a gate that can be told it passes.

    *What it does not do, said plainly:* it cannot find a false sentence nobody
    annotated, and there is no honest way to make it. What it can do is make a sentence
    pinnable for the cost of one line, catch the naming rot automatically, and refuse a
    document that arrives unclassified. The claim count is printed with no floor,
    because prose is deleted along with the thing it described; the two automatic
    checks are what stop it becoming a no-op if the claims went away.
13. *Every node property the program reads is written by something.* ~props~ is the
    third way to keep state here — [[file:DESIGN.org::#d20][D20]]'s answer to "an
    extension needs somewhere to put its own state" — and it was the unchecked one. An
    option is registered and gate 11 asks who reads it; a hook is declared and gate 7
    asks who runs it; *a property key is neither registered nor declared.* It is a
    keyword typed in two places, the write and the read, and nothing compared the two.

    Two keys had only one of the two, in the same tree, with nothing in common but the
    mechanism. =:lattice/viewport-bounds= was read by the lattice's ~clip-rect~ and
    written by nothing, so the one method standing for ~set_content_clip_box~ — the best
    find in [[file:DESIGN.org::#feasibility][§feasibility]], the cropped trailing cell
    that ~:fixed~ zoom exists for, a row in
    [[file:FINDINGS.org::#twelve][FINDINGS' list of what the extension overrides]] —
    returned "clip nothing" for its entire life. And =:overlay= was read by the core's
    ~render-order~ as a third render tier above the floats, which no node could be put
    into, because every overlay in this program is a *surface* rather than a node.
    Neither is a typo. Both are a keyword that was read where it should also have been
    written, and *an absent property is a legal answer*, so there was nothing to signal
    and nothing to test.

    It reads the source with the *reader*, which is the whole difference from a grep: a
    key is found by symbol identity against ~prop~, so every nickname in the tree is the
    same function; a docstring naming a key is a string rather than a form and cannot
    make it pass; and a ~setf~ place is told apart from a read structurally rather than
    by looking left for a bracket. Gate 11's instrument is unavailable here — keywords
    are constants, not variables, and ~who-references~ answers ~nil~ for every one of
    them.

    *It fails one direction and reports the other.* A key that is read and never written
    is provably dead code and there is no arrangement of the program in which that was
    the intent. A key that is written and never read is what D20 exists for — state hung
    on an object for a reader the core does not know about — so the four in that position
    are printed on every build rather than failed on. Demanding an in-tree consumer for
    =:pid= would be a check writing the design.
14. *Every declared hook is attached to by a suite that runs it.* Gate 7 above compares
    two sets of names — declared here, run there — and both sets are written by the same
    hand in the same afternoon. It establishes that a hook *exists*. Nothing established
    that one *works*, and **fourteen of the seventeen had never been attached to by
    anything at all**: not by the lattice, not by the four worked examples, not by a
    test.

    *A hook's contract is not its name.* It is the arguments its functions are called
    with and the moment they are called, and neither had ever been executed for any of
    the fourteen. Three were wrong, and each is the kind of wrong only a consumer finds:
    ~:startup~ ran *before* the compositor connection existed, which its own docstring
    denied and which the ~:layout-restored~ docstring twelve declarations below it in the
    same file contradicted; ~:output-added~ ran at the moment the object was made, before
    the monitor's name, position, size or scale had arrived, which is everything "a
    surface or a process per screen" needs; and ~:focus-changed~, documented "run after
    the cursor moves", was skipped by two of the five places that move the cursor, one of
    them being closing a window. All three passed gates 1, 2, 7 and 12, the whole unit
    suite and the whole integration run, because nothing was listening.

    *Somebody must be listening, and there are exactly three places that can be.* Which
    one is decided by what has to exist for the event to happen at all: ~tests/~ for what
    constructing state can reach, ~tools/integration.lisp~ for what needs a real
    compositor, ~tools/hardware-check.lisp~ for what needs a real machine. The third is
    not a loophole — a headless backend runs with no input devices, so ~:input-added~
    cannot be reached by the harness that reaches everything else — and attaching them in
    the session recorder is right for that tool independently, since which devices were
    found is the first question a hardware report should answer.

    *Two halves, and neither is sufficient.* The gate is static: every hook must be named
    in the *code* of one of the three, read through ~code-of~ so a docstring cannot
    satisfy it. That catches hook nineteen being declared and nobody touching the suites,
    which is exactly how the first eighteen got where they were. The dynamic half is in
    the integration run, where it has to be: a recorder sits on every declared hook for
    the whole session, every firing is checked against the declared argument count, and a
    hook that neither fired nor is named as one a headless backend cannot produce is a
    failure. It found two things on its first run — a monitor that had no name yet when
    the fixed ~:output-added~ announced it, and the fact that nothing in the project had
    ever closed a window against a real compositor.

    *And the declaration stopped being a comment.* ~defhook~ took a lambda list and began
    ~(declare (ignore lambda-list))~, so the one statement of what a hook function
    receives was a comment that happened to be parenthesised. It is recorded now:
    ~add-hook~ complains about a function that cannot accept those arguments, and a
    compiler macro on ~run-hooks~ fails gate 1 on a call site that passes the wrong
    number. Both matter because ~run-hooks~ guards each function separately — correctly,
    since one broken hook must not stop the others — so an arity mistake signals once per
    fire, is caught, and leaves nothing but a log line.

* Packaging: both targets, neither privileged
:PROPERTIES:
:CUSTOM_ID: packaging
:END:

** Plain Linux is the primary build

Ordinary ASDF. SBCL and Quicklisp are packaged on every distribution. ~wayflan~ is not
in Quicklisp's distribution, so it is a git submodule or a ~qlot~ pin, not a curl.

#+begin_example
make          -> builds, runs the gates
make run      -> runs against the current WAYLAND_DISPLAY
make image    -> save-lisp-and-die -> ./latticewm, one executable
make install  -> ./latticewm + share/ + a sample init.lisp
#+end_example

*~save-lisp-and-die~ does not cost live redefinition.* The dumped core retains the
compiler, so SWANK connects and ~defmethod~ still works at runtime. This is StumpWM's
shipping model and it is proven. Ship the image with ASDF included so user extensions
can be ~asdf:load-system~-ed from ~~/.config/latticewm/~.

Result: a single ~40 to 60 MB executable, dependencies libc only, runs on Arch, Fedora,
Debian, Void, anything.

** Nix is a packaging target, not a dependency

~flake.nix~ exposes ~packages.default~ (the same image), ~devShells.default~ (SBCL,
Quicklisp, the pinned river), and a NixOS module. It consumes the same ~Makefile~.

*Nothing in ~src/~ may know that nix exists.* If the flake is deleted the project still
builds. That is the test.

*And there is one installer.* "It consumes the same Makefile" was true of the build and
false of the install: ~flake.nix~ had its own ~installPhase~ listing what ships, beside
~install.sh~'s list, and the two drifted apart without anything able to
see it — including the lattice sources, which is [[#gates][gate 9]]'s own artifact. The
phase runs ~install.sh --prefix $out~ now. The two flags that exist for it, ~--no-config~
and ~--river~, are the whole of what a build sandbox needs said differently: no home
directory to write a starter config into, and a compositor named by store path rather
than by whatever ~river~ resolves to at login — which is the pinning this file argues for
two sections down, applied to the launcher that actually starts the session.

** Protocol pinning, in both worlds
:PROPERTIES:
:CUSTOM_ID: pinning
:END:

~river-window-management-v1~ is *unreleased and moving*, and a pre-release protocol can
break within a version number rather than politely bumping to v2. After budget expiry a
river upgrade could break the window manager with no one available to repair it. This is
the largest threat to the "survives without AI" requirement, larger than any
decomposition risk, and DESIGN treats it as a CI check.

Three layers, and the first two work everywhere:

1. *Vendor the XML in-tree* and generate from the vendored copy, never from a URL.
2. *Assert the version at bind time.* We generate against
   ~river_window_manager_v1~ version 5. On registry bind, if the compositor advertises
   something we did not generate against, *refuse to start* and print the two version
   numbers, the river commit this build is known good against, and what to do. A clear
   refusal is repairable by a non-programmer. Silent misbehaviour is not.
3. *Nix pins river itself* in the flake, so the compositor and the window manager become
   one versioned pair upgraded deliberately or never. On plain Linux the equivalent is
   crude and works: record the known-good river commit in the DESIGN and *keep a copy of
   the working river binary*. River is Zig and builds to a single file.

  than the ones DESIGN used to reach it — and it stands *conditionally on gate 6*, since
  a Vim-shaped codebase in Common Lisp would have paid the correctness tax and received

** Deltas 1 and 2 held; Delta 3 is conditional

[[#delta-1][Delta 1]] — cells and splits share one geometry — is the strongest result here.
It was implemented as *one container protocol*, and directional motion across a
cell boundary needed zero lines: ~find-motion-target~ ascends out of a split,
asks the grid, and descends, without knowing what a grid is.

[[#delta-2][Delta 2]] — the lattice as a separate ASDF system, gated daily — worked exactly
as designed and is why the findings in [[file:FINDINGS.org][FINDINGS.org]] exist at all.

[[#delta-3][Delta 3]] — ~absolute-with-clipping~ as the shipped default — is *reversed, with
its own argument preserved*. Delta 3 is right that ~exact-fit~ makes a column's
rendered width depend on which columns are beside it, so panning resizes every
window on screen. What it does not say is that this is *conditional*: it only
bites once columns are non-uniform, and columns are uniform until somebody
resizes one. On a uniform lattice ~exact-fit~ panning resizes nothing.

So ~exact-fit~ ships as the default, it is free for anybody who never resizes a
column, and the first ~resize-column~ logs what it now costs and how to flip it.
There is a test asserting both halves. If this proves wrong in daily use the fix
is one ~setf~.

** The hole the first session left, stated plainly

M-x shipped, and it could reach *thirty-seven of sixty-seven commands* — the

is that the command registry is a *user interface* rather than an
implementation detail. It was not one yet.

It is now *71 of 72*, and the exception is ~focus-path~, whose argument is a

answered. There is a test asserting that the list of refusals is exactly that
one command, so a future command that quietly becomes unreachable fails the
build rather than going unnoticed.

** How, and why it is not Emacs's design

Emacs's ~(interactive "sPrompt: ")~ is a string DSL with about forty
single-letter codes, and nobody remembers more than four. The mechanism here is
the same idea with the hindsight applied:

- An *argument type* is a named object — a prompt, a candidate list, a parser —
  and ~define-argument-type~ adds one in three lines from a configuration file.
- The type of a parameter is *inferred from what it is called*. A parameter
  named ~direction~ holds a direction; one named ~number~ holds a number.
- ~(:interactive ...)~ after a docstring overrides that per command, and is
  needed exactly twice in the whole system: ~spawn~'s ~command~ is a shell
  command line, and ~describe-command~'s ~name~ is one of ours.

The inference sounds like a hack and is not. The parameter names were already
chosen to read well in a docstring — that is what makes ~substitute-arguments~
work on the help screen — and *a name that reads well in a docstring is a name
that says what kind of thing it is*. The convention covers every shipped
command, in the core and in the lattice, with two exceptions and no
annotations. It is a tier-0 option, so adding to it needs no code.

Two decisions inside this went to [[#the-policy-surface][the policy surface]] rather than the runtime,
and the surface count moved 40 → 42 for them:

- ~complete-candidates~ — prefix, then substring, then subsequence. This is the
  most personal decision in the whole minibuffer; Emacs ships six completion
  styles and that is the right number to ship when the answer is taste.
- ~argument-type-for~ — the naming convention itself, which is a *scheme*
  somebody may want to replace wholesale rather than entry by entry.

The test that caps the surface at forty was moved to forty-five, with the
reason written into the test rather than into a commit message.

** The bindings nobody would have found by reasoning

Reading text needs the keys bound, because river delivers keys to the focused
*window* and gives the window manager only what it asked for. The first session
bound printable ASCII with *no modifiers* — 98 bindings — and that was enough
to type a command name.

It is not enough to type ~(+ 1 2)~. River matches a binding on keysym *and*
modifiers, and the keysym xkb produces for Shift+9 on a US layout is
~parenleft~ with Shift still in the modifier set. A binding for ~parenleft~
with no modifiers never fires. So every printable keysym is now bound twice,
bare and with Shift, plus the arrows, Home, End, Delete, and twelve Ctrl
chords: *214 bindings, created once, enabled only while a prompt is up.*

Doing it by mask rather than by working out which characters are shifted on
which layout is what makes it work on a Dvorak or a German keyboard.

*Still unverified:* whether river reports Shift in the modifier set for a
shifted keysym, or masks it out. Both bindings exist, so one of them matches
either way — but which one has not been observed, because observing it needs a
human pressing a bracket, and the whole session was driven through the SWANK
bridge.

** The finding: ~#'foo~ in a hook cannot be redefined

Worth recording because it is a defect in the *live-redefinition thesis*
itself rather than in a feature.

Reloading =help.lisp= into the running window manager changed nothing on
screen. The reason: ~(add-hook :draw-overlays #'draw-help-overlay)~ stores the
function *object*. Redefining the function afterwards leaves the hook calling
the old one, and re-running the ~add-hook~ adds a second entry, because the new
object is not ~EQL~ to the old. Both generations then ran, and the older
drawing won by being second.

=echo.lisp= had the same bug in a worse form — a ~pushnew~ of an anonymous
lambda onto ~*reserve-hooks*~, which cannot dedupe at all, so every reload
would have reserved another strip of the screen.

Fixed by registering *symbols*: a symbol is looked up when the hook runs, so
redefinition takes effect, and a second ~add-hook~ of the same symbol replaces
rather than accumulates. ~add-hook~'s docstring now says so, and ~:draw-overlays~
— the one hook in the system that four things used and nothing documented — is
now declared, so it appears in the extension surface.

*The general form of this:* the mechanisms that make a live image worth having
are not automatic. They have to be used a particular way, and the way is not
the one that reads most naturally.

** The finding: twenty-four options that could not be set

The starter configuration this program writes has, on line 55:

: ;; (setf *terminal* "alacritty")

A configuration file is read in ~LATTICEWM/USER~, which inherits
~LATTICEWM/RUNTIME~ wholesale. ~*TERMINAL*~ was never exported from it. So that
line — *the line the program itself suggests* — interns a brand new symbol in
~LATTICEWM/USER~, sets that, and changes nothing whatsoever.

Twenty-four of the thirty-one runtime options were in this state, including
~*terminal*~, ~*editor*~, ~*browser*~ and ~*modifier*~ — the four values a
person is most likely to want on their first day — and every colour, scale and
column count in the entire widget layer.

*Why nothing caught it.* Each one was declared with ~define-option~, so it was
registered, documented, printed by ~--list-options~, readable through
~Super+? o~ and settable through ~Super+? s~ and ~M-x set-option~, all of which
route through the keyword registry rather than the symbol. Gate 2 checks that
options are documented. The surface tests check that they have defaults and
round-trip. Six gates and 570 checks passed over a system where the single most
common thing a user would type into a config file silently did nothing.

It is the same shape as [[file:FINDINGS.org][FINDINGS.org]] core edit 3 — /the shipped defaults were on
the class users specialise/ — and the same lesson, which §honest predicted and
which has now happened twice: *nothing verifies that the decomposition is good,
and every automated check can pass while the thing is unusable in its most
common mode.* What caught it, again, was going and looking: reading the file a
new user is handed, and asking whether each line in it actually works.

There is now a test that asserts *symbol identity* — not accessibility — for
every registered option, and it fails with the name of the offending option and
the package to export it from. It was checked against the bug rather than

** Gate 6: ruled

[[#log2][§log2]] left the question open — is gate 6 measuring the wrong pair, or is the
decomposition failing? *Ruled: neither. The widget layer should become
extensible, and the ratio should go above 1 by moving code rather than by
moving the measurement.*

The ruling matters because gate 6 counts *by directory* — ~src/wire/~ plus
~src/runtime/~ against ~src/model/~ plus ~src/policy/~ plus ~lattice/~ — so
adding a ~define-option~ inside =src/runtime/help.lisp= moves the number by
exactly zero. That is not a flaw in the gate. It is the gate insisting the
decomposition be real: a generic that lives in the runtime is still something a
user has to read the runtime to find.

The split to make is the Emacs one. The C core does redisplay primitives;
Elisp decides what is on the mode line. Here: shm buffers, the fd path, glyph
blitting and surface lifecycle stay runtime; colours, column layout, which font
at which size for which role, what the status line says, how a help page
composes, and the completion styles become generics under ~src/policy/~.

Roughly 400 lines have to cross to reach 1.0 from the 0.80 this session ends
at. The candidates, in order of how much of each is genuinely a decision:
=echo.lisp= (what a status line shows is ~mode-line-format~, and it is
hardcoded), =minibuffer.lisp=, =help.lisp=, =font.lisp= — where the PSF loader
is mechanism but *which font for which role* is policy, and making that live is
runtime font loading, which is a feature rather than an accounting exercise.

* Fourth session — 2026-07-31: the widget layer starts crossing the line

:CUSTOM_ID: log4

[[#log3][§log3]] ruled that gate 6 should move because code crosses from runtime to

** The split mechanism was half policy and half TYPEP

Every genuine *decision* about splits was already a method — ~layout-children~,
~step-address~, ~entry-address~, ~should-collapse-p~, ~insertion-weight~. The
*verbs* were not: five places asked ~(typep x 'split)~ inline, and a ~typep~
cannot be specialized.

The consequence was specific rather than theoretical. A container kind from
outside that divides space exactly the way a split does — the shipped
scrolling-columns example, or anybody's own variant — was invisible to
~resize~, ~equalize~, ~equalize-all~ and ~tab~, and ~tree-split-at~ would never
join it, so splitting three times inside one built a ladder of nested
two-child containers instead of one row of four.

~a-container-kind-the-core-never-heard-of-works-everywhere~ passed throughout,
because it exercises layout, motion and surgery, all of which do go through
generics. *The test was right and the claim it was read as supporting was
wider than the test.*

Four generics carry it now, each fallback specialized on ~T~ rather than on
~container~ so that a caller walking up a parent chain and reaching ~NIL~ gets
an answer instead of ~no-applicable-method~ — the same lesson
~layout-children~'s fallback already records. ~src/model/~ stays pure: the
decision crosses that line as a closure, exactly the way ~%simplify-upwards~
already takes ~allow-collapse~ instead of calling ~should-collapse-p~.

** Fonts are data now, and the cap on them was wrong

The window manager shipped with one font wired in as three constants and a
table. The reasoning for a bitmap font at all still holds — Pango would be a C
font stack in the way of surviving without a maintainer — but it was never an
argument for the font being *unchangeable*.

A ~font~ is now a struct, the generated Terminus table registers itself as the
default, ~load-psf~ reads any console font off the disk, and ~font-for (policy
role)~ decides which is used where. PSF rather than BDF or TTF for one reason:
*the fonts are already on the machine*, a few dozen of them, so changing the
font needs nothing found, converted or installed.

Two things only running it could find, and it found both inside a minute:

1. ~uiop:run-program~ with ~(:string :element-type (unsigned-byte 8))~ reads
   the pipe as *text* anyway and dies on the first octet that is not valid in
   the default encoding — immediately, for a font table. The failure surfaced
   as *"the font did not change"* rather than as an error, because the caller
   fell back to the built-in one. ~:external-format :latin-1~ is the fix: the
   encoding whose code points are its bytes.
2. The first version capped fonts at eight pixels wide, with a docstring
   confidently explaining that Terminus's larger sizes are taller rather than
   wider. *They are not.* ~ter-122b~ is eleven wide and ~ter-d28n~ is fourteen,
   so the cap refused every size above the smallest — which is to say every
   font somebody changing the font would be reaching for. Glyph rows are
   stride-addressed now and the leftmost pixel is the high bit at any width.

The second is the more interesting one. It was not a coding error; it was a
*stated assumption in a docstring* that was simply false, and the only thing
that could have caught it was pointing the loader at the fonts on the disk.
Third time this log has had to record that.

- The text-composition half of =help.lisp= — ~summary-of~, ~wrap-text~,
  ~truncate-text~, ~substitute-arguments~. Pure functions, and every one of
  them is a decision about how a docstring reads on a screen. Perhaps ninety
  lines, and the only obstacle is that ~substitute-arguments~ takes a command
  object and would have to take a lambda list instead.
- =echo.lisp='s content. What a status line is made of is ~mode-line-format~,
  the single most-customised variable in Emacs, and here it is hardcoded.
- *The real question: the command registry and the keymap.*
  [[#extensibility-real][§extensibility-real]] says outright that the command registry is "a user
  interface rather than an implementation detail". If that is true then
  ~defcommand~, ~define-key~ and the shipped keymap are policy, and moving
  them settles gate 6 outright — five hundred and fifty lines. If it is not
  true, then a registry is infrastructure and the number has to be earned
  somewhere else.

That is a genuine architectural call rather than an accounting one, and it is
the next thing to decide.

* Fifth session — 2026-07-31: gate 6 crosses, on a ruling about defaults

** What moved, and the trick that made it free

~log.lisp~ and ~commands.lisp~ to ~src/policy/~, plus the pure text functions
out of =help.lisp= and the five program defaults out of =config.lisp=.

~guarded~ earns its place there by its own docstring, which was written long
before this question came up: it exists "at every boundary where a *policy
method* is called — that is, at every point where user code runs inside ours."
That is a policy decision about what happens when an extension misbehaves, and
it was sitting in the runtime.

*The move cost zero edits at four hundred call sites*, and the first attempt
at it was the wrong one. Prefixing every use of ~logmsg~, ~guarded~ and
~defcommand~ with ~p:~ was a 403-substitution rewrite that also mangled
~command~ — a parameter name in half a dozen files — and prefixed words inside
comments. It was reverted whole. What replaced it is ~:import-from~ in the
runtime's ~defpackage~: the symbols live in ~LATTICEWM/POLICY~, are imported
into ~LATTICEWM/RUNTIME~, and are re-exported there so ~r:defcommand~ keeps
resolving for the lattice. Not one reference in any file changed.

The lesson is worth keeping: *a package system is the tool for moving symbols
between layers.* Rewriting call sites to do it is doing the package system's
job by hand, badly.

** The bug the move exposed

Gate 2 failed immediately: ten undocumented generics, all of them CLOS slot
readers — ~command-name~, ~command-function~, ~argument-type-prompt~ and
friends.

The cause is older than this session. ~policy-generics~ was:

: (do-external-symbols (symbol '#:latticewm/policy)
:   (when (and (fboundp symbol) (typep (fdefinition symbol) 'generic-function))
:     (pushnew symbol out)))

— *every exported generic in the package*. Meanwhile ~policy-generic-p~ sat
beside it, written, documented, and never called, saying:

#+begin_quote
The test is structural rather than a maintained list: a generic function
exported from this package whose first required argument is specialized on
POLICY somewhere. A list would drift; this cannot.
#+end_quote

The two definitions were indistinguishable for exactly as long as the only
generics in the package were the surface. The moment a class with slot readers
moved in, ten accessors became extension-surface entries, gate 2 demanded
docstrings for them, and *the sentence the surface document prints at the top
of itself* — "every generic below takes a POLICY as its first argument" —
became false.

Nothing had noticed, because nothing could: the drift needed a class to arrive
in the package, and none ever had. ~policy-generics~ walks ~policy-generic-p~
now, and the test asserts both halves — that everything in the surface passes
the structural test, *and* that the five accessors which exposed it are
excluded — because a test that only counted would have passed throughout.

** The keymap was never protocol, and neither was the modifier vocabulary

=keys.lisp= had two protocol references in three hundred lines, and they
turned out not to be protocol at all:

: (w:modifier-mask keywords)      ; (:super :shift) -> canonical keyword list
: (w:modifier-names (cdr key))    ; the reverse, for display

Both are pure keyword-list transformations. Neither reads or writes a byte.
They lived in ~src/wire/~ because river's binding requests take the canonical
names — and *nothing in wire ever called them*, which is the tell.

The thing underneath is ~*modifier-aliases*~, which decides that ~super~,
~mod4~, ~logo~, ~win~ and ~s~ all mean one key. That is not a protocol fact.
It is a judgement about what people will type, and somebody who wants ~:h~ on
hyper should not have to be told no. It is a tier-0 option now.

With the vocabulary lifted, =keys.lisp= splits cleanly at a seam that was
already drawn in the file as a banner comment:

- ~src/policy/keys.lisp~ — keysyms, key specs, the keymap tree, ~define-key~,
  ~lookup-key~. *The keymap is data*, and the most user-edited object in the
  system.
- ~src/runtime/keys.lisp~ — ~run-key-target~ and ~handle-key~, which reach
  ~mark-dirty~ and ~notify~ and therefore the server. 92 lines.

** The subtler half of the same mistake

~echo-content~ has been a generic in =protocol.lisp= since the first day, with
a docstring saying the status line's content is a decision. Its only method
lived in =src/runtime/echo.lisp=.

*So the decision was overridable in principle and on the wrong side of the
line in fact.* That is worth naming as its own failure mode, because it is
invisible to every check the project has: gate 2 sees a documented generic,
the surface document lists it, and a reader would conclude the thing is
policy. Only the file it is written in says otherwise, and only gate 6 counts
files.

A ~define-option~ in the runtime is the loud version of this and was fixed in
[[#log3][§log3]]. A ~defmethod~ on a policy generic, written in the runtime, is the quiet
version.

~echo-content~, ~keymap-choices~ (which-key) and ~pending-keymap-segments~ are
in ~policy/appearance.lisp~ now. ~echo-segments~ stays in the runtime, and
that one is a real seam rather than a leftover: it chooses between "a prompt
is up" and "ask the policy", and whether the minibuffer is currently reading
is not a decision anybody wants to override.

* Seventh session — 2026-07-31: bare metal, and the three questions close

** The three, answered

- *Does river report Shift in the modifier set for a shifted keysym?* No. It
  sends the *unshifted* keysym with Shift set. The design assumed the
  opposite, in a comment explaining that binding by mask rather than by layout
  is what makes it work on Dvorak, and bound every printable keysym twice on
  that reasoning. Typing ~(+ 1 2)~ into M-: produced ~9= 1 20~. *SHIFT-MAP* is

  and a declared US layout is wrong on a German one.
- *Does ~ate_unbound_key~ fire when the seat has no keyboard focus?* Yes.
  ~UNBOUND #\e on an empty pane~, twice, on bare metal. D19 works.
- *Bare metal.* It runs. ~output 56 is eDP-1~, 1366x768, wlroots on the DRM
  backend with the iris driver.

*And the lattice works on a real display.* A recorded session walks from cell
(0,0) to (2,0), opens an editor there with a single keypress, walks left
through (0,0) into (-1,0) and on to (-15,0), carries a window across cells and
into a split, zooms out from 1x1 to a 6x4 viewport, and the person driving it
saw a grid. That is DESIGN's central claim -- an infinite plane of cells,
motion running straight through the boundaries -- doing what it says, on
hardware, driven by hands rather than by the SWANK bridge.

and seven gates passed.*

| A submap registered its second keys globally | seven letters silently vanished; typing ~ls~ gave ~l~ |

| A ~:name~ event that river_output_v1 does not have | every output anonymous; per-output workspaces keyed on NIL |
| ~POLICY-GENERICS~ ignoring ~POLICY-GENERIC-P~ | ten slot readers became extension surface |
| ~:focus-changed~ declared and never run | a status bar hook that could not fire |
| The welcome overlay consuming the key that dismissed it | the first deliberate keypress of a first session did nothing |
| The lattice rebinding Super+/ away from ~help~ | loading an extension deleted the way out of not knowing anything |
| ~quit~ and the unwind-protect both running shutdown | every exit ran every shutdown hook twice |
| ~add-hook :relayout~ in this project's own tooling | a hook nobody runs, so the recorder recorded nothing |

The last one is the worst and the most instructive. ~tools/build.lisp~ loaded

** The gates that came out of it

Four, and each one exists because something got through:

- *Gate 1 learned to fail.* It only ever saw warnings from files that
  recompiled, so an incremental build hid everything in cached fasls -- and a
  clean build could never be green because four warnings arrive from a
  dependency. Warnings are judged by whether the file is ours now, ~.deps~
  excluded, and undefined references are captured from the compilation unit's
  printed summary rather than a condition nothing signals. A clean build is
  the normal way to run it.
- *Gate 7:* every declared hook is run, every run hook is declared.
- *~*warn-on-undeclared-hooks*~:* the runtime half, because gate 7 cannot see
  a user's config file and that is where the mistake is most likely.
- *~*warn-on-rebinding*~:* say when a binding replaces a *different* command.
  It found a second collision the same minute it was written -- the lattice
  also takes Ctrl+Super+hjkl from resize.

* Eighth session — 2026-08-06: the harness that could not grow
:PROPERTIES:
:CUSTOM_ID: log8
:END:

=tools/integration.lisp= was the project's best idea and its least-used one. It
runs a real river headlessly, receives state instead of constructing it, and
found a live bug on its first run — and then it stopped at eighteen checks
against the eight and a half thousand lines of =src/runtime/= they were meant to
cover, in a tree where the optional extension has *seven times* the test density
of the runtime every user touches.

That was not a lack of will. It was a shape problem. The file was one 250-line
=LET=: the nineteenth check meant finding the right nesting depth inside
somebody else's binding form, and one error anywhere abandoned every check after
it. *A harness whose marginal check is expensive gets exactly as many checks as
its first sitting.*

** What changed

Rebuilt around a *section*: a name and a body that catches its own errors, so a
broken section costs one section. The fixtures — a compositor, a window manager,
clients, a settled round trip, a command run the way a script runs one — are
functions rather than scope. Read in a package that =:use=​s the real ones, so a
check is written in the vocabulary the program is written in.

Eighteen checks became a hundred and sixty in twenty-one sections. =make check=
now sets =LATTICEWM_REQUIRE_INTEGRATION=1=, so a missing river or a missing
terminal emulator — which is the default state of a CI container — fails instead
of printing a paragraph and exiting 0. And there is a CI workflow, so "ten CI
gates run on every build" stopped meaning "when a human types make".

Skips are counted in two kinds, because they are not the same kind. A *missing
dependency* is a tool that should have been installed and is fatal under that
variable. A *structural skip* — libinput devices, a physically scaled output, a
layer-shell client — is something a headless backend cannot have, is printed
every run, and is never fatal, because making it fatal would only teach people
to unset the variable.

** The four it found, all live, none reachable by a unit test

- *A window that leaves the tree is never hidden.* =EMIT-RENDERING-STATE= walked
  *placements*, so it could hide a window the layout mentioned and marked
  invisible — and said nothing at all about one the layout never mentioned. Two
  ordinary things produce that: =minimize=, whose shipped =ON-MINIMIZE= takes
  the window out of the tree entirely, and *every workspace you are not on*,
  because =OUTPUT-CONTENT= hands the layout one workspace and no other. River
  went on drawing both. =MINIMIZE-WINDOW='s own comment claimed "the emitter
  hides everything it did not place", which was the specification of a function
  that did not exist; it exists now and is called =HIDE-UNPLACED-WINDOWS=.
- *=new-workspace= switched the cursor and not the screen.* The stack knows
  which child is selected; the *output* knows which one it is displaying; and
  =OUTPUT-CONTENT= reads the output. =workspace= set both and =new-workspace=
  set one, so "add a workspace and switch to it" left you looking at the one you
  came from with the status line confidently reporting the new number. Both go
  through =SHOW-WORKSPACE= now.
- *=op_start_pointer= was sent outside the only sequence that may carry it.*
  Manage-only request, event-handler caller: refused, logged, lost. River never
  entered pointer-op mode, never sent an =op_delta=, and Super+drag did nothing
  at all — for the second time in this project's life and for a different reason
  than the first. =DEFER-TO-MANAGE= is =CLOSE-WINDOW-LATER='s solution named, so
  the next one costs a =LAMBDA= rather than a slot.
- *A lost wakeup left the screen thirty seconds stale.* =WAKE-EVENT-LOOP= sets a
  flag and throws into the loop's =CATCH=; when the interrupt lands while the
  loop is *outside* it, the throw has nowhere to go, the flag stays set, and the
  loop then walks into a thirty-second wait with another thread's work sitting
  in the queue. That is the exact symptom =WAKE-EVENT-LOOP='s own docstring was
  written to fix, reached by the one path its fix did not cover. =WAIT-FOR-WORK=
  consumes the flag now: finding it set costs one extra turn of the loop.

The first three are invisible to a test that builds its own world, because in
every one of them *the model was right and the screen was wrong*. The fourth is
invisible to any test that is not driving the program from another thread — which
is what a script, the control socket and a SWANK REPL all do.

** And a fifth, which is the one the design named as the largest threat

Putting the integration suite into =flake.nix='s build phase — the only
automated path that gates a store path — made it fail immediately, and correctly.

The flake pins =nixos-unstable=, not a river version. River bumped
=river_window_manager_v1= from *4 to 5* between 0.4.5 and 0.4.6, which is a
patch release; the locked nixpkgs has 0.4.6 and the vendored XML is version 4.
So the startup check does exactly what it was written to do and refuses to
start.

*That means the flake has been building a session entry that cannot start.*
=nix build= succeeded, =installPhase= wrote a =wayland-sessions= desktop file
running =${pkgs.river}/bin/river -c $out/bin/latticewm=, and logging in got a
version-mismatch paragraph at a login screen. It succeeded because nothing in
the build phase had ever connected to the river the same derivation pins —
which is the whole argument for the change that exposed it.

=flake.nix:8-16= says this in advance, in as many words: "river-window-management-v1
is young, and a pre-release protocol can break within a version number rather
than politely bumping to v2. A flake pins the compositor and the window manager
as one versioned pair, upgraded deliberately or never." It did not pin them as a
pair. It pinned a channel.

*** Resolved: re-vendored to 0.4.6

The two ways out were to re-vendor the protocol from the pinned river and bump
=+WINDOW-MANAGEMENT-VERSION+=, or to pin a river the vendored XML matches. The
first was taken, and the argument is the diff rather than a preference — the
whole of 4 → 5 is two new events (=capture_sessions= on =river_window_v1= and
on =river_output_v1=) and five clarifications of prose. Nothing removed,
nothing renamed. The feared failure — a pre-release protocol breaking *within*
a version number — is not what this release was.

Pinning back would have frozen the pair on a superseded release that leaves
nixpkgs on a schedule nobody here controls, and the check refuses in *both*
directions: a build vendored at 4 cannot start on any river a user installs
today. That is the asymmetry that decided it. =src/protocol/PINNED= carries
the diff and the reasoning.

All six river protocols were re-vendored from 0.4.6 together, so the tree is
one vintage rather than five. The three input protocols went 1 → 2 in the same
release, each adding a =done= event; they are bound at whatever version is
offered rather than checked for equality, so they degrade against an older
river instead of refusing. Gate 5's rows moved by exactly the new event counts
and by nothing else — 42 → 44, 5 → 6, 60 → 61, 11 → 12 — which is the gate
saying, in the only vocabulary it has, that the release was additive.

=nix build= is green: the build phase now connects to river 0.4.6 and the
integration suite reports "river_window_manager_v1 is bound at version 5,
which is the version we generated against". The three structural skips are
unchanged.

*And CI was red on its first run, which nothing here had noticed.* The
workflow landed on 2026-08-06 and the commit that added it is the commit whose
=check= job failed — the =plain= job, which has no river and skips the
integration suite, passed. Four runs exist in total: that one, and the three
green ones on this work. (The commit that recorded this said CI "had been red
for a month", which is wrong and is corrected here rather than rewritten
there: the workflow is one day old.) That is the same shape as the flake: a runner whose
=nixos-unstable= channel holds 0.4.6 running a tree vendored at 4. The claim
in [[file:README.org][README]] that "=nix-shell=, =make=, =make check= and CI are unaffected and
green" was true of every path with a 0.4.5 river on it and false of the one
path that runs on a machine nobody owns. The same job passes on the
re-vendored tree, and the version is the only difference between them that
could account for it.

*And the NixOS module, which is the same bug for the one user who cannot read
a refusal.* Two things were wrong with it and neither had ever been run,
because =nix flake check= evaluates a module's options and not a system that
enables it. =programs.latticewm.river= defaulted to =pkgs.river= — the
*user's* nixpkgs, not this flake's — under a description saying "pinning this
alongside the window manager is the point of the module". And the session
entry came from the package, whose =.desktop= hardcodes the river locked at
build time, so setting the option changed which river you had installed and
not which one your session ran: an option that did nothing, silently. Worse,
=sessionPackages= requires =passthru.providedSessions= and the package has
none, so =programs.latticewm.enable = true= failed to evaluate at all. The
module now builds the session entry from =cfg.river=, defaults it to the
locked river, declares its session, and *asserts* the pair — a mismatch fails
=nixos-rebuild= with both numbers rather than a login screen with neither.
Evaluated both ways: zero failing assertions matched, the message with the two
versions when overridden with 0.4.5.

*Gate 5 grew the check that would have caught this in the first place.* It
counted interfaces, requests, events and enums, and said nothing about the one
number that actually decides whether the program starts: the version constant
beside the XML. So the copy-without-the-constant is a build that compiles,
passes every count in the gate, and refuses to start against the very river it
was just vendored from — diagnosable only by running it, which is the one
thing a gate exists to spare you. It now asserts that
=+WINDOW-MANAGEMENT-VERSION+= and =+XKB-BINDINGS-VERSION+= equal the versions
their XML declares, and it was proved to fail by setting the constant back to
4. Four steps in [[file:INSTALL.org][INSTALL.org]], and the gate names each one you have not done.

What stays true is the part that is load-bearing. The nixpkgs input is still a
channel, so a future =nix flake update= can still move the compositor under a
vendored XML. The difference is that it now fails at =nix build= rather than
at a login screen, and that is tested rather than asserted.

*And =shell.nix= pins now, which it claimed to do and never did.* Its
=<nixpkgs>= was the ambient channel, so its river was whatever the machine
held — 0.4.5 here, months behind — and the header said it pinned "the window
manager and the compositor as one versioned pair". That is the flake's own
untruth told in the other direction, and re-vendoring came due on it
immediately: =nix build= went green and =nix-shell --run 'make check'= went
red on the same tree, on the same afternoon.

It now reads =flake.lock= and fetches that revision by hash, so the three
paths — =nix-shell=, =nix develop=, =nix build= — are one river rather than
two pinned ones and a third that drifts. It costs nothing on a machine that
has already built the flake, and it falls back to =<nixpkgs>= when flake.lock
is absent, so [[#packaging][§packaging]]'s "if the flake is deleted the project still
builds" survives. A pair pinned on one path out of three was never pinned.

For the machines with no nix at all, =bootstrap.sh= reads the release out of
=src/protocol/PINNED= and warns when the river on =PATH= is a different one —
the same file =shell.nix= reads for the same warning when =pkgs= is overridden,
so no copy of the number can drift from what the program will accept.

*** And a race the re-vendor exposed

Running =make check= twice back to back failed the second time, on
"river_xkb_bindings_v1 is bound", about one run in two. The check was
*unpolled*, three lines below a comment explaining that exact race for

* Ninth session — 2026-08-06: the two events we could speak and did not
:PROPERTIES:
:CUSTOM_ID: log9
:END:

=src/protocol/PINNED= ended with a sentence that was true and was also a to-do
list: the two =capture_sessions= events river 0.4.6 added are unhandled, "which
is a feature we do not have rather than a protocol we cannot speak". The
distinction was the right one to draw — nothing was broken, and the version
check was not at stake — but it named the feature, and the feature is worth
having, because *the one thing you cannot see by looking at your own screen is
that somebody else can see it too*. A screen share you forgot to stop looks
exactly like a screen share you never started.

River sends a count of active screen capture sessions on each
=river_window_v1= and each =river_output_v1=, once at creation and again on
every change. Handling it is four things and one deliberate omission:

- The count is on the model — =c:window-capture-sessions=,
  =c:output-capture-sessions= — so a policy can read it without depending on
  the runtime, which is the same rule the app id and the scale live under.
- Starting and stopping are announced in the echo area, which is this
  program's only way to talk. =*announce-capture*= turns the line off without
  turning the fact off.
- The shipped status line carries a standing =REC= for as long as anything is
  being recorded. The announcement scrolls away after a few seconds; the fact
  does not, and the fact is the part that matters.
- =:capture-changed= is the hook for everything else: a status bar, a light on
  a keyboard, a script that mutes a microphone. =M-x captures= answers the
  next question — *what* — and it walks every window the model holds rather
  than the tree, because a minimized window goes on being recorded and that is
  exactly when you can no longer see it.

*And nothing about placement changes.* A recorded window is tiled, hidden,
minimized and closed exactly as it was. Refusing to hide a window somebody is
recording would be the window manager deciding something the user did not ask
for, on a compositor perfectly able to go on feeding the capture session; this
is information, and it is deliberately only information.

** The three-valued count, which is the only subtle part

The stored count starts at NIL — river has not said — and is an integer
afterwards. Zero would have been the obvious initial value and it makes two
different things indistinguishable.

The announcement rule needs the difference. A window created while nothing is
recording must say nothing; a window created *during* a screen share must say
so; both arrive as the same first event, and only the previous value tells them
apart. So does the integration check: the count river never sent and the count
river sent as zero look identical if the initial value is zero, and "the
handler never ran" is precisely the failure that check exists to catch. It is
the same shape as the =:name= event that never existed — a handler that does
nothing, silently, on every machine — and this is what it costs to make that
shape visible from the outside.

=c:window-captured-p= and =c:output-captured-p= collapse NIL and zero, and are
what every caller that is not checking the protocol should read.

* Tenth session — 2026-08-06: the metric that shaped the tree

Gate 6 was the runtime-to-policy line ratio for the whole life of the project. It is
gone, replaced by the question it was standing in for. This is the largest single change
to what the build asserts, so the argument is written out.

** What the ratio actually measured

Non-blank, non-comment lines: ~src/wire/~ + ~src/runtime/~ (minus ~font.lisp~) as the
denominator, ~src/model/~ + ~src/policy/~ + ~lattice/~ as the numerator, floor 0.80. At
the commit this session starts from it is 6,783 / 6,772 = *1.0016*.

It passes on two accounting choices and either one alone sinks it. All three recomputed
by hand under gate 6's own counting rule:

- move ~policy/appearance.lisp~ (510 counted lines) and ~policy/keys.lisp~ (353) back
  under ~src/runtime/~ — where both were written — and it is 5,920 / 7,635 = *0.7754*;
- drop ~lattice/~ — 1,457 counted lines of an *optional extension that gate 4 exists to
  prove the core does not need* — out of the numerator and it is 5,326 / 6,772 = *0.7865*;
- both, and it is 4,463 / 7,635 = *0.5845*.

The margin over the floor was the two files that were moved last, plus an extension in
the numerator.

** And the history says the same thing

Four commits recovered it, and the ratio reconstructed under gate 6's own rule at each
parent and child:

| commit | before → after | what moved | reproduced verbatim |

"Reproduced verbatim" is measured the blunt way, because the blunt way cannot be argued

And the part that decides it. ~4fe8811~'s message ends "back to 1.01, on a real change
rather than an accounting one." That commit *also changed the counting rule* — it added
the ~font.lisp~ skip, in the same diff, four paragraphs above that sentence. Under the
old rule its parent is 0.9740; under the new rule the *same parent*, unchanged, is
1.0091. Rule change +0.0351, code change +0.0039, total recovery +0.0390. *Ninety percent
of the recovery the message explicitly denied being accounting was accounting.*

The exclusion itself is defensible — 95 lines of vendored hex is not authored runtime —
and it was named in the output, which the commit was right to insist on. What cannot
stand is claiming the resulting number as evidence of a code change in the same breath.
(It is also filename-based rather than content-based: ~src/runtime/font.lisp~ carries
eighteen hand-authored lines that the "generated file" skip removed from the denominator
for the rest of the gate's life.)

Across all four: two new policy generics, ~echo-content~ and ~font-for~, neither with a

** The steelman, because it is real

The ratio caught something nothing else could. [[#log5][§log5]] records ~echo-content~
being a policy generic whose only method lived in the runtime — overridable in principle
and on the wrong side of the line in fact. Gate 2 sees a documented generic; the tests
never notice which package a method is in. That is a real catch and nothing else in this
project would have made it. [[#log4][§log4]] records refusing to game the metric when
~psf.lisp~ moved it the wrong way, which is the correct response and is on the record.
And ~5c3db2e~'s central move is right independent of the number: ~modifier-mask~ sat in
~src/wire/~ and nothing in ~wire~ called it.

*Most of those moves stay.* They were right for the reason
[[file:src/policy/appearance.lisp][appearance.lisp's header]] now gives — a
~define-option~ under ~src/runtime/~ is still something a user has to read the runtime to
find — and that reason does not depend on anything counting the lines. What does not
survive is the counting.

** The replacement

Gate 3 already contained the check in embryo: it counts the lattice's ~defmethod~ forms
against a floor, precisely because "an extension that answers almost no generics is going
round the protocol rather than through it". Generalise that from the lattice to the whole
surface:

1. policy generics with *at least one specialising method defined outside ~src/~*;
2. methods on policy generics defined outside ~src/~;
3. floor both.

No file can be moved to change either. A method outside ~src/~ is a method outside
~src/~, and the only way to raise these numbers is to write one. It loads ~lattice/~ and
the four files under ~examples/~ to ask — which runs *after* gate 4, whose whole job is
proving the core comes up with the lattice absent, and which is itself the first thing in
the build ever to compile the worked examples.

*The number is 15 of 65, and 22 methods.* Fifty generics have never been answered by
anything but their own shipped default. That is much less flattering than 0.99, it is the
real state of the extension surface, and it is now what the build prints.

Both floors are set *at* the number rather than below it. A floor with slack under it is
an invitation to spend the slack — which is the mistake the 0.80 floor made — and slack
is unnecessary here because the number cannot fall by accident. There is no rearrangement
of the tree that lowers it, only the deletion of a method somebody wrote on the outside.
[[#gates][§gates]] asked for exactly this shape at line 184 and never got it.

** The fifth core edit, which the ratio was hiding in plain sight

~4fe8811~'s argument for making ~echo-content~ a generic was that "a lattice policy would
sensibly add the viewport". The lattice never overrode it. Instead the *default method*
reached into the extension's private namespace:

#+begin_src lisp
;; src/policy/appearance.lisp, as it stood
(place (or (and node (c:prop node :lattice/address)
                (format nil "~d,~d"
                        (car (c:prop node :lattice/address))
                        (cdr (c:prop node :lattice/address)))))
#+end_src

The generic created to prove the boundary exists was crossed by its own default
implementation, in the same file, hard-coding both the extension's property key and its
cons representation of an address. It is a core edit, it was not on
[[file:FINDINGS.org][FINDINGS.org]]'s list, and it is the one edit for which an extension
point already existed.

Nothing could see it, and the reason is exact: it is not a core edit the *lattice* asked
for, so it never reached the list; the lattice does not touch it, so gate 3 passed; it is
documented and dispatches on a policy class, so gate 2 and the generated surface were
happy; and it *works* — with the lattice loaded the status line shows the coordinate,
achieved by the core doing the extension's job for it.

Fixed at the root rather than at the call site. ~cursor-place-name (policy world)~ is a
generic; the shipped default answers the cursor path, which every layout model has; the
lattice answers ~cell-string~, four lines, on the outside. Zero behaviour change either
way. And gate 3 gained the direction it never had — *no file under ~src/~ may name an
extension's private namespace* — which is the check that would have caught it on the day.
It is recorded as [[file:FINDINGS.org::#edit-6][core edit 6]].
