# Contributing to LatticeWM

Read this before you open a pull request, because this project has an unusual
amount of machinery and every bit of it will run on your branch.

## The short version

```sh
git clone https://github.com/SYKhayyat/LatticeWM.git
cd LatticeWM
./bootstrap.sh          # fetches the two dependencies; idempotent
make check              # build, twenty-two gates, the unit suite, integration
```

`make check` is what CI runs and what the nix build runs. If it is green on
your machine it will be green on ours. If it is red, the failure message is
meant to tell you the whole story — every gate prints why it exists before it
prints what is wrong. If one of them does not, that is a bug in the gate and
worth reporting on its own.

## What will fail your branch, up front

There are twenty-two build gates. They are not style checks; each one exists
because something silently rotted and nobody noticed. That makes them
excellent for a maintainer and a wall for a newcomer, so here is the wall,
described before you hit it.

| gate | what it refuses |
|---|---|
| 2 | a policy generic, a container generic or a command with no docstring |
| 3 | anything in `lattice/` that touches `src/`, and any mention of the lattice from the core |
| 4 | a core that cannot load, start and lay out with the lattice absent |
| 5 | generated protocol bindings that disagree with the pinned XML |
| 6 | shrinking the surface answered from outside `src/` below its floors |
| 7, 14 | a hook that is declared and never run, or run and never declared |
| 8 | an event handler for an event the interface does not have |
| 9, 21 | a second installer or a second build, beside `install.sh` and the Makefile |
| 10 | a `typecase` on a container class anywhere in `src/` — dispatch through the protocol |
| 11 | an option nothing reads |
| 12 | a document, a man page or a docstring naming an option that does not exist; a `#+CLAIM:` the program contradicts; a new `.org` or `doc/*.txt` nobody classified |
| 13 | an extension property written and never read, or read and never written |
| 16 | a published name nothing reaches — no exporting a helper before its caller, test or document exists |
| 19 | the version, the licence or the gate count disagreeing between files |
| 20 | a method in `src/policy/protocol.lisp` |
| 22 | a protocol request called from outside `src/wire/` — add an alias and call that |

Two of these bite first-time contributors in ways that feel arbitrary and are
not:

- **Gate 16.** Export a symbol in the same commit as the thing that uses it.
  An export with no reader is a promise to a stranger with nothing behind it,
  and this project has shipped three of those.
- **Gate 12.** If you add an `.org` file, say in `tools/gates.lisp` whether it
  is *current* (describes the program as it is — its sentences are checked) or
  *historical* (a dated record, frozen on purpose). Arriving unclassified is
  the one thing a document may not do.

## The documents that are frozen

`DESIGN.org`, `PLAN.org`, `ASSESSMENT.org` and `SPIKE-WEEK0.org` are records of
what was decided and when, and they are effectively append-only. Do not edit
them into agreement with what shipped — that destroys their only value.
`DESIGN.org` contains a row reading *"Overturned by D22, in this document"*,
which is what a record that has not been laundered looks like.

If one of them is wrong about the program today, the fix is a new note that
says so, or a `#+CLAIM:` line, or a change to the program.

`README.org`, `INSTALL.org`, `FINDINGS.org`, `doc/EXTENDING.org` and the two
man pages are *current* and a false sentence in one of them is a bug.

`doc/*.txt` is generated by `make surface`. Never edit those by hand; run the
target and commit what it writes.

## Writing an extension rather than a patch

Most of what people want is a method, not a change to the core. Before
proposing a patch to `src/`, check whether there is already a generic for it:

```sh
latticewm --extension-surface   # every generic, its docstring, and what reads it
latticewm --list-options        # every value you can set
latticewm --list-commands
```

`doc/EXTENDING.org` is the guide, and `examples/` has five worked extensions
that are loaded and exercised by the test suite. If the thing you want has no
generic, that is a good issue: *"there is no generic for X"* is a more useful
report than a patch that special-cases X, and it is how `capture-wanted-p`,
`border-state` and `entry-address` came to exist.

The `lattice` system is the proof this works: an infinite plane of cells,
adding a container kind the core has never heard of, in a separate ASDF system
that edits nothing under `src/`. Gates 3 and 4 hold it to that.

**Where a second extension goes.** Right now: nowhere, and that is the
project's biggest gap rather than a policy. A separate `latticewm-contrib`
repository, with a low bar and no gates, is the intended answer, in StumpWM's
model — where the core is not feature-rich and `stumpwm-contrib` is. Until it
exists, open an issue and say what you built; the shape of the second
extension is information this project does not have.

`examples/` is *not* that place and is not a substitute for it. It used to be
worse than that: gate 6's floors were set at the exact number of generics the
whole tree answered, `examples/` included, so the build did not survive
deleting any of them — an example you cannot delete is load-bearing
infrastructure with a docstring. The floors come from `lattice/` alone now and
the teaching material is free again, which removes the obstacle to a commons
without supplying one.

## Commit and PR shape

- Commits are expected to explain *why*, at length if the reason is not
  obvious. The git log here is part of the documentation; read a few before
  writing one.
- Add a `CHANGELOG.md` entry under `## Unreleased` for anything a user or a
  packager would notice.
- One concern per pull request. A branch that fixes a bug and reformats a file
  costs the reviewer the ability to see either.
- New behaviour needs a test. New behaviour on the extension surface needs a
  docstring, because gate 2 will not let it through without one.

## Reporting a bug

`latticewm --version` and the output of `make check` are worth more than a
description. If it is a layout or focus problem, `latticewm --eval
'(print (world-root *world*))'` prints the tree, and a tree is usually the
whole diagnosis. There is an issue template.
